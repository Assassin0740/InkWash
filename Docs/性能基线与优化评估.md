## 三、分档基线（`perf_baseline.txt`）

三个负载档同会话连测，档间差即"该负载的净开销"。

|---|---:|---|---:|---:|---:|---:|---:|---:|
| 静置（空场） | 161.6 fps | 6.19 / 8.31 / 8.79 ms | 0 | 5.96 KB | 0 | 195 | 76 | 649 896 |
| 跑动（空场） | 175.8 fps | 5.69 / 8.35 / 9.65 ms | 0 | 6.25 KB | 0 | 106 | 38 | 550 798 |
| 满负荷战斗 | 162.5 fps | 6.15 / 9.05 / 18.35 ms | 3（0.13 %） | 9.38 KB | 0 | 216 | 105 | 618 732 |

## 四、真实帧耗与余量（`perf_headroom.txt`）

同会话内先量 vsync 开、再量 vsync 关——这是本轮唯一可信的"竖直对比"（原因见 §五）。

| 档 | 中位帧耗 | 1% 低 | 最长帧 | >16.7ms 的帧 | draw call | setpass |
|---|---:|---:|---:|---:|---:|---:|
| 静置 · vsync 开 | 5.780 ms（173.0 fps） | 8.140 ms | 9.04 ms | 0 / 514 | 152 | 55 |
| 静置 · vsync **关** | 5.734 ms（174.4 fps） | 7.917 ms | 8.89 ms | 0 / 515 | 152 | 55 |
| 战斗 · vsync **关** | 6.158 ms（**162.4 fps**） | 8.581 ms（116.5 fps） | 10.07 ms | **0 / 1603** | 221 | 114 |

**判读**：vsync 开关读数一致 ⇒ 未受垂直同步限制，174 fps 是真实能力。
按毕设设计判据（战斗档中位 ≥120 fps）：中位 162 fps **达标**；1% 低帧 116.5 fps 略低于 120，属可接受。

## 五、★ 两个被推翻的假设，与一个被推翻的尺子

这一节比数据表更重要——它记录的是**避免把错结论写进论文**的过程。

### 5.1 被推翻：帧率被垂直同步钉死

`perf_baseline` 报告里 `vSyncCount=1`，中位帧耗 6.19 ms 与 165 Hz 的 6.06 ms 近乎相等，
一度判断"读数在 vsync 天花板上，不是能力的度量"。
**对照实验直接否掉了它**：关掉 vsync 后中位帧耗 5.734 ms，与开着时的 5.780 ms 无差异。

### 5.2 被推翻：瓶颈在"每次挥砍新建弧光对象"

`SwordVfx` 每次挥砍都 `new GameObject("SlashArc")` + `MeshRenderer` + `mr.material`（材质实例）
+ `Destroy`，`InkProjectile` 每次射击 `Instantiate` + `Destroy` —— 静态看这是教科书级的热点。
**但量级对不上**：

| 项 | 量级 |
|---|---|
| 空场地板（无任何战斗） | ≈ 1.0 MB/s（6 KB/帧 × 165 fps） |
| 实战挥砍频率下弧光带来的分配 | ≈ 1~3 KB/s（按 1~2 次/秒 × 约 1 KB/次估） |
| 差额 | **约三个数量级** |

⇒ **对象池优化在当前频率下不可测、无收益。** 做它是为了"看起来做了优化"，不是因为有证据。
（`InkHitVfx` 溅墨池本来就已经是有池的——40 个面片惰性创建，注释里写着"战斗最激烈时也不该产生 GC"。）

### 5.3 被推翻：`GC.Alloc` 可以跨会话比较

这一条是方法论层面的，也是本轮最值钱的发现。

起因：`perf_baseline` 量"静置"得 **5.96 KB/帧**，`perf_alloc_ab` 量同一个静置得 **12.99 KB/帧** ——
**同状态两次差 2.2 倍**，那么基于它做的"逐子系统归因表"（只解释出全部差额的 18%）就不可信。
于是做了一次专门的对账实验（`perf_alloc_ab2.cs`）：

| 检查 | 结果 | 判读 |
|---|---|---|
| 同一档重复测两次的差 | **0.15 KB/帧** | 尺子本身很准 |
| RunManager 主菜单 OnGUI 的净成本 | ≈ 0（-0.15 KB/帧） | 不是它 |
| 同一会话内的漂移 | ≈ 0（-0.49 KB/帧） | 不是时间效应 |
| **同一状态、跨会话** | 5.96 → 12.99 → **18.07 KB/帧** | **跨会话差 3 倍** |

**结论**：

> 编辑器内 `GC.Alloc` 的绝对值被编辑器自身开销（窗口重绘、bridge 轮询、日志捕获）主导。
> 它**只在同一会话内**做相对比较时才有效；跨会话不可比，小于 1 KB/帧 的差额不能当结论。
> 想要可信的分配基线，必须在**构建版**里测（或用 Profiler 二进制日志 + 分配调用栈）。

**因此上一轮那张"逐子系统归因表"（V0~V6）整体撤回**，不作为结论使用。

## 六、工具与复跑

| 文件 | 作用 |
|---|---|
| `Tools/cs/perf_open.cs` | 切到 `Main.unity` 并进 Play。★ 先查 `isDirty`，脏场景直接放弃——`OpenScene` 的模态弹窗会把 bridge 卡死 |
| `Tools/cs/perf_baseline.cs` | 三档基线（静置/跑动/战斗），逐帧采样，输出 `Tools/reports/perf_baseline.txt` |
| `Tools/cs/perf_alloc_ab.cs` | 逐子系统关停归因（**结论已撤回**，脚本保留供构建版复测） |
| `Tools/cs/perf_alloc_ab2.cs` | 度量可靠性对账：重复测量噪声 / 主菜单成本 / 会话漂移 / 跨会话对账 |
| `Tools/cs/perf_headroom.cs` | 真实帧耗与余量（同会话内 vsync 开↔关对照） |
| `Tools/cs_lint.py` | 探针 .cs 的低级错误体检，几毫秒，跑探针前先过一遍 |

复跑步骤：

```bash
python Tools/cs_lint.py                        # 先体检
python Tools/exec_cs.py cs/perf_open.cs        # 切场景 + 进 Play
python Tools/exec_cs.py cs/perf_headroom.cs --runtime --timeout 120
# 报告落盘 Tools/reports/perf_headroom.txt
```

> ★ `exec_cs.py` 的 `--timeout` 默认只有 15 秒，而这类探针要跑 20~60 秒 —— 必须显式加大，
> 否则 TCP 等待超时（探针其实还在跑，报告照样落盘，但命令行会抛 `TimeoutError`）。

## 七、下一步（若要继续 F3）

按证据，应该做的是**先拿到可信的分配剖面**，而不是先写池：

1. 在**构建版**（Development Build + Autoconnect Profiler）里测 `GC.Alloc`；
2. 或用 `Profiler.enableAllocationCallstacks = true` + 二进制日志抓一段 `.raw`，
   在 Profiler 窗口的 Hierarchy 视图里看**分配调用栈**，定位真正的地板来源；
3. 只有当某个调用点被证实占 >10 % 的总分配、且在实战频率下可复现时，才为它做池。

当前已确认**不值得做**的：弧光池、弹丸池（量级见 §5.2）。
