## 2. 敏捷框架设计（PMP 映射）

因为是 7 天极限工期，**不套用标准 Scrum 的 2 周 Sprint**，而是压缩成 **1 天 = 1 个 Sprint，共 7 个 Sprint**。理由：反馈周期越短，越能在当天就发现方向错误。

| PMP 知识领域 | 在本项目中的落地形式 |
|---|---|
| 整合管理 | 本计划书即整合基线；每日站会用一条消息汇报，变更走 MoSCoW |
| 范围管理 | 第 4 节 Product Backlog（含故事点）；**范围冻结**，新增需求一律进"Won't" |
| 进度管理 | 1 天 1 Sprint；每日燃尽（见 Excel `燃尽图` 表） |
| 成本（时间）管理 | 故事点即时间成本；每日目标 16 点，超支次日砍 Should 项 |
| 质量管理 | 第 9 节 DoD：编译零错误、Console 无红字、1080p≥60fps |
| 资源管理 | AI = 主要劳动力；人 = 决策/账号/验收三类不可替代动作 |
| 沟通管理 | 每 Sprint 结束输出「截图 + 状态 + 阻塞」三件套 |
| 风险管理 | 第 8 节风险登记册，R3/R5 为高优先级 |
| 采购管理 | 素材获取走 CC0 优先策略（第 6 节） |
| 干系人管理 | 导师 = 关键干系人；每 2 天准备一次可展示的进度快照 |
| 变更管理 | 需求冻结；确需变更须砍掉等量故事点（等价交换） |

**角色分工（关键：把人的时间花在 AI 做不到的事上）**

| 只有你能做的 | AI 做的 |
|---|---|
| 开/关 Unity 编辑器 | 写全部 C# 脚本与 HLSL Shader |
| 注册并登录 Mixamo / Asset Store（需账号） | 通过 Bridge 建场景、挂组件、连引用 |
| 下载素材并放进工程 | 改材质参数、调光照、布点 |
| 看效果做主观判断（"墨味够不够"） | 进 Play 模式、截图、读 Console 排错 |
| 论文里的表述、创新点定位、导师沟通 | 论文素材整理、图表数据、初稿撰写 |
| 最终验收与录屏确认 | 性能分析、优化、测试用例 |

## 3. 游戏设计范围（Demo 版）

**定名**：`墨刃 · InkWash`　**类型**：3D 第三人称水墨动作 Roguelike（单局制）

**核心玩法循环**（对应大纲 4.1）

```
主菜单 → 进入「墨境」一局 → 
  房间①：清怪 → 三选一技能 → 
  房间②：清怪 → 三选一技能 → 
  房间③：精英怪 → 三选一技能 → 
  BOSS → 通关结算 / 死亡结算 → 回主菜单
```
单局目标时长 **5–8 分钟**。

**角色能力**（对应 4.2）

| 动作 | 说明 |
|---|---|
| 轻攻击三段连击 | 第 3 段带前冲位移，可取消后摇接闪避 |
| 蓄力重击 | 破防、高伤害、长后摇 |
| 闪避翻滚 | 含无敌帧（i-frame），可穿身位 |
| 拔刀斩（技能位） | 居合式突进斩，消耗墨气 |

**敌人 3 种**（对应 4.3）

| 敌人 | 行为 |
|---|---|
| 墨徒（近战） | 追击 → 挥砍 → 硬直 → 循环 |
| 墨偶（远程） | 保持距离 → 投掷墨弹 → 被贴近则后撤 |
| 墨魇（精英） | 范围横扫 + 冲锋，有可弹反窗口 |

**局内成长**（对应 4.4）：以 ScriptableObject 定义技能池，升级时加权随机三选一。候选池示例：攻击力↑ / 攻速↑ / 暴击率↑ / 连段扩展至四段 / 墨刃投影（远程剑气）/ 命中吸血 / 闪避距离↑ / 背水一战（低血量增伤）等 **10–14 条**。

#### Sprint 2.1 · Day 2 增量 — 动画与手感返工（用户看片后反馈 6 项）

用户看完 S2 验收录屏后逐条反馈：①走路仰着身子 ②攻击第一下动作奇怪 ③跑步的动作呢 ④右键是什么鬼动作 ⑤刀光在刀还没速度时出现 ⑥攻击时脚陷下去。
**出口**：6 项全部有可量化证据，且 S1/S2 全量回归零未通过。

| 反馈 | 根因 | 处理 |
|---|---|---|
| ① 走路仰着身子 | 沿用 UAL2 `Walk_Carry_Loop`（搬东西的姿势，上身后仰） | 换 UAL1（CC0）`Walk_Loop` / `Jog_Fwd_Loop`，新建 `Walk`/`Run` 两态；实测躯干 Walk +10.2°、Run +12.1°（前倾） |

| ⑥ 攻击时脚陷下去 | FootIK 读的是脚踝 IK 锚点，不是真实脚底；且两套动画髋部基准不一致 | 重写 `Player/FootIK.cs`：**逐帧 BakeMesh 取真实网格最低点** + 9 条静态基准偏移（压动画自带浮空）+ 只抬不压的动态夹地。姿态体检 4/4 |

**过程中发现的两个"看不见的"真实缺陷**（都不是用户直接点名的）：

1. **动画被攻击前冲"抢走"** —— `Speed` 参数原本直接吃 `DesiredSpeed`（= `_velocity.magnitude`），
   而攻击前冲就是往 `_velocity` 赋值（峰值 ~11 m/s）。状态机里 Idle→Walk(>0.15)/Walk→Run(>3.0)
   排在「攻击触发器」转移**之前**，于是发招那一帧速度参数瞬间冲过 Run 门槛，
   动画被拽去走路/跑步、攻击触发器迟迟不落地；0.35s 后逻辑判定"没进攻击态"直接退回移动 →
   **取消窗口永远打不开、连击推不到第 3 段**。
   修法：新增 `_blendSpeed`（**移动意图**速度）驱动混合树 —— 移动阶段=输入目标速度，
   攻击/冲刺=0，仅后摇取消窗口里真按了方向才交回。这同时解释了②"第一下很怪"的体感。
2. **音频的 NRE 会静默打断刀光** —— `PlayerController.SwingStarted` 是**多播**，
   `AudioDirector` 是第一个订阅者；当 `AudioKit` 处于半初始化（`Settings.IsSoundOn == null`，
   编辑器 Play 会话跨脚本重载时会出现）时它抛 NRE → **C# 多播遇异常即中断** →
   排在后面的 `SwordVfx` 一次都收不到事件 → 现象是"完全没有刀光"，而日志里只有一条与刀光无关的音频报错。
   修法：`GameAudio` 改为防御式门面（检测到半初始化先补跑 `OnInit`，补不上就静默降级），
   并用反射人为置空 `IsSoundOn` 的回归脚本 `Tools/cs/s2_probe_audioguard.cs` 验证自愈。

**验收结果**：**S1 31/31 + S2 54/54 + 姿态体检 4/4 + 音频 6/6，合计 0 未通过** → **M2 保持达成**
证据视频：`Tools/screenshots/GameView_2026-09-13_21-55-10-611.mp4`（战斗）、`GameView_2026-09-13_21-55-32-419.mp4`（移动）

#### Sprint 2.1 · Day 2 增量（二）— 跑步动作返工：把"游戏速度"降到动画能支撑的范围

用户第二轮反馈：跑步动作抽象，"两条腿在原地倒腾，不像往前迈步"。

**先纠正一个沿用两版、其实是错的判断**：一直拿「播放倍率落在 1.0~1.8 是健康区间」衡量脚步是否自然。
倍率只说明片段被拉伸了多少，**真正的观感指标是步频**（= 2 步/循环 ÷ 循环时长）。
1.81× 摊在一段 0.933s 的慢跑上就是 **3.9 步/秒** —— 已经超过真人冲刺（4.0~4.4），腿当然像在原地倒腾。

**实测各移动片段的原生地面速度**（新增 `Tools/cs/s2_probe_refspeed.cs`）：

| 片段 | 循环 | 原生地面速度 | 单步位移 |
|---|---|---|---|
| `Walk_Loop` | 1.333s | **1.15 m/s** | 0.77m |
| `Jog_Fwd_Loop` | 0.933s | **≈2.9 m/s** | 1.34m |
| `Sprint_Loop` | 0.667s | **≈3.7 m/s** | 1.24m |

方法可信度：同一套量法在 Walk 上算出 1.15 m/s、单步 0.77m，与真人走路吻合。
（量法本身踩了 6 个坑；正确判据 —— **在角色根节点局部空间量、锁接触点、只取竖直速度≈0 的帧** ——
已沉淀进 `unity-codely-bridge` skill，下次别重蹈。）

**核心矛盾**：UAL1 这套素材最快只有 ≈3.7 m/s（13 km/h），而原 `runSpeed = 5.6`（20 km/h）。
**跑速超出素材设计范围 50% 以上，腿不可能不倒腾**。而且换片段解决不了：换成更快的 `Sprint_Loop` 之后
步频反而从 3.87 升到 4.54 —— 因为 Sprint 的步幅（1.24m）比 Jog（1.45m）还短。
**能降步频的只有降 runSpeed。**

**处理**：

| 项 | 改动 |
|---|---|
| `Run` 片段 | `Jog_Fwd_Loop` → **`Sprint_Loop`**（动作幅度本来就是按高速画的） |
| `runSpeed` | **5.6 → 4.2 m/s**：倍率 1.14×、步频 **3.40 步/秒**、单步 1.22m，落在人类跑步区间 |
| `runRefSpeed` | 3.10 → **3.70**（实测值；虚高会让脚打滑） |
| `walkRefSpeed` | **故意保留 1.55**（实测只有 1.15）：`walkSpeed 2.2` 本身也超出素材范围，取实测值步频会变 1.91×。这是"拿一点滑步换腿速"的折中，根治要降 `walkSpeed`（本轮用户决定先不动走路） |

**顺手修掉两条自欺欺人的验收断言**（这才是虚高值能活到现在的真正原因）：

1. 「疾跑步频明显快于步行」原来比的是**播放倍率**（1.14 vs 1.42）—— 两段片段长度不同（1.33s vs 0.67s），
   比倍率是拿苹果比橘子。改成比**真实步频**（`CombatSample.clipLen` + `stepsPerSecAvg`），
   并加上界断言（走路 ≤3.0、跑步 ≤4.4 步/秒）防止以后再退化。
2. 「播放速度 = 实际速度 / 参考速度」那条断言是**同义反复**：它反推的"片段速度"就是拿 `refSpeed` 除出来的，
   `refSpeed` 写错也永远测不出来。要真正校验，必须把"独立实测的原生速度"写进断言做对比。

#### Sprint 2.1 · Day 2 增量（三）— 跑步「扭腰」：换成成品片段 + 按片段重量参考速度

用户第三轮反馈：「这个跑步还是扭腰啊，你能不能直接网上找对应的成品啊？……你自己验收自己录屏，自己检查然后提交吧，有问题就再改」

**关键结论：这个指标不能单独当质量判据。** 它等于「髋线偏航 + 肩线偏航」直接相加，对**摆臂幅度**同样敏感——

**落地清单**：

| 项 | 改动 |
|---|---|

| 代码 | **零改动** —— 全工程无硬编码骨骼路径，`SwordVfx` 走 `GetBoneTransform(RightHand)` |

**顺手挖出并修掉的两个真缺陷（都在 `FootIK.cs`，都是"换模型才暴露"的隐性问题）**：

1. **竖直偏移走错了空间**：`stateOffsets` 是世界米，却写进 `anim.bodyPosition`（Animator 局部空间）。
   模型整体缩放 2.213 时世界效果被放大 **4.90 倍 = 2.213²**（实测写 0.0257 抬了 0.1260），
   `BodyLift` 反馈增益同样 ×4.9 → 必然过冲。**改法**：输出通道改为**模型容器的 `localPosition.y`**
   （父节点无缩放 → 局部 Y 就是世界米，1:1），与模型缩放彻底解耦。
   *KayKit 时代缩放为 1，两个空间数值恰好相等，所以这个错一直藏着。*
2. **静态偏移与帧内抬升重复补偿**：`BodyLift` 的 `need` 按原始姿态算，没扣掉已施加的 `BodyBase`，
   同一个穿地量被补两遍。KayKit 时代 9 段偏移全负、原始最低点恒为正 → `need` 恒 ≤ 0 → 代码路径没被走到；
   Feng 有负的原始最低点，立刻显形。**改法**：`need = (地面 + clearance) − 最低点 − BodyBase`。

**方法论修正三处**：
- `FootIK.stateOffsets` 绑的是「**片段 × 骨架**」而不只是片段 —— 脚位取决于**腿长比例**，
  换骨架必须整表重测（上一节曾判断"片段不变就不用重标"，**该判断是错的，已纠正**）。
- `SkinnedMeshRenderer.bounds` **不可靠、会严重虚高**（把 3 头身 Q 版量成 2.35 m 高）；
  量真实身高/网格最低点必须 `BakeMesh()` 取顶点。
- 编辑期 `Object.Destroy` **不生效**（会报错并保留对象），临时相机/贴图要用 `DestroyImmediate`。

### 一、认知修正：剑身不该对齐"手指方向"

上一版把剑身对齐到**手骨 +Y（手指伸出方向）**。实测数据说明这是**引错了类比**：

| 量 | 值（Idle 期世界） | 含义 |
|---|---|---|
| `fingerDir` | (0.430, −0.869, 0.247) | 手指伸出方向（几乎朝下） |
| `spreadDir`（食指根→小指根） | (0.457, −0.031, −0.889) | **拳头铰链轴 = 拳头隧道轴** |
| `palmNormal` | (0.779, 0.495, 0.384) | 掌面法向 |

与 `+spreadDir` 差 152.6° ⇒ **取 −spreadDir**。副产品：与角色 `forward` 只差 **27.3°**，
待机时剑自然指向前方。

### 二、修掉上一版漏掉的挂点项

**上一版写成了 `P = s·Gm·d`**，等于假设"腕关节就是握持点"。

### 3. 换片段炸出的 FootIK 真缺陷：**探地正反馈**

换完立刻 S2_pose 报 `Atk2Rec -0.878 m`。`q_footdiag.cs` 打出这些帧 **`HasGroundInfo = false`**：

> `ProbeGround` 射线起点 = `网格最低点 + probeUp(0.5)`。
> UAL2 的收招段把角色压到地下 **0.5~0.9 m**（比 KayKit 的直立挥砍激进得多），
> 起点随之落到**地面之下**，而射线**向下**发 ⇒ 永远打不到地面
> ⇒ `HasGroundInfo=false` ⇒ `BodyLift` 归零不修 ⇒ **沉得更深、更探不到**。正反馈。

修法三条（前两条是通用缺陷，换任何「大幅下蹲」的片段都会撞上）：

1. 起点改用 **`max(网格最低点, 角色根 Y) + probeUp`** —— 角色根由 `CharacterController`
   保持在地面附近，才是可靠锚点；网格最低点会被动画压得很低，不能单独作锚。
2. **`maxLift` 0.8 → 1.3**：最深需要一次性抬 0.89 m，卡上限会永远差一截。
3. `stateOffsets` 的 `Atk1/Atk1Rec/Atk2/Atk2Rec/Atk3` 重标，**取「最浅穿地量」作基准**
   （不是最深）：这样每帧 `need = 地面 − 最低点 − 基准 ≥ 0` 恒成立、帧内抬升全程有效；
   取最深值会让浅的帧 `need < 0`，而**帧内抬升只能向上、压不下去** ⇒ 那些帧反而浮空。

## Sprint 2.1 · Day 3 增量（十二）— 移动片段去 Q 版化 + 攻击提速

**这次的收获不在「换了什么片段」，而在标定方法与验收窗口两处硬伤。**

### 1. 参考速度绑的是「片段 × 骨架」，换骨架后连旧片段的值都作废

`walkRefSpeed = 0.69` 是 KayKit 模型时代标的。主角换成 Feng 后腿变长，重定向把步伐一起放大
—— **同一个 `Walking_A` 在 Feng 上实测 1.32 m/s**。旧值让 `MotionSpeed = 1.0 / 0.69 = 1.45`，
比正确值高 1.9 倍 ⇒ 腿倒腾得比真人快 50%（步频 2.72 步/秒，真人走路 1.5~2.0）。

> 与增量（五）的 `FootIK.stateOffsets` 同一条规矩：**绑「片段 × 骨架」的量，两个维度任一变化都要重标。**

### 2. 标定方法：改用量**脚踝骨骼** —— 网格最低点会被脚掌滚动骗

v1 用「网格最低点」量 Feng Walk 得到 **2.25 m/s / 单步 1.50 m**。对 1.78 m 身高而言
单步 1.5 m 是跨步跳，常识校验一眼就不对。真因：真人比例模型走路时脚掌会「脚跟→脚尖」滚动，
**最低点在着地相内部平移了约一个脚掌长（0.25 m）**，被当成了「脚相对根的后移」⇒ 速度虚高近一倍。

改用 `LeftFoot / RightFoot` 骨骼、逐脚判着地相（脚踝进入「该脚最低点 + 4 cm」）后：

| 片段 | 时长 | 原生地面速度 | 步频 | 单步位移 |
|---|---|---|---|---|
| KayKit `Walking_A` | 1.067 s | 1.32 m/s | 1.88 | 0.70 m |
| **Feng `Walk`** | 1.333 s | **0.91 m/s** | 1.50 | 0.61 m |
| KI `Walk01_Forward` | 0.800 s | 1.80 m/s | 2.50 | 0.72 m |
| KayKit `Running_A` | 0.800 s | 5.48 m/s | 2.50 | 2.19 m ← 不合理 |
| **KI `Run01_Forward`** | 0.600 s | **4.12 m/s** | 3.33 | 1.24 m ✓ |

脚本 `Tools/cs/q_refspeed2.cs`；候选对比与连拍 `Tools/cs/q_movecand.cs`。

## Sprint 2.1 · Day 3 增量（十三）：走路不循环 / 鼠标视角失效 / 廉价感

把「僵硬」变成一个可比的米数。（对照：先逐项排除了遮罩层、步伐同步、腿没动三项，
每一步都留了数据。）

**排除法用到的三组数据**：

| 怀疑对象 | 实测 | 结论 |
|---|---|---|
| 遮罩层锁死手臂 | 控制器**只有 Base Layer**、无 AvatarMask | 排除 |
| 步伐没同步 | `MotionSpeed ≈ 0.97`、步频 3.2 步/秒 | 排除 |
| 腿没动 | `Run01_Forward` 0.6 s 腰 72° / 肩 242° / **肘 305°** | 排除 |

**为什么不能直接换 UAL1 的跑**：`Jog_Fwd_Loop` 单步 2.547 m、参考速度 5.457，
换 `runSpeed 4.0` 后倍率 0.73× ⇒ 被拖成慢动作反而更怪。KI 的**腿**本来就对
（单步 1.25 m ≈ 真人慢跑、步频 3.33），错的只是**右臂**。

**方法：按肌肉通道名烘焙**

humanoid 片段的曲线是 **130 条肌肉通道**（PropertyName 形如 `"Right Arm Down-Up"`、
`"Right Shoulder Front-Back"`），于是可以按名字筛选、只替换右臂那 **36 条**：

- 腿 / 躯干 / 左臂 → 原样保留 KI 的跑步数据；
- 右臂 → 整段替换为 UAL1 `Rig|Idle_Loop` 在 `t = 0.50 × 长度` 处的定值；
- 补 `loopTime = true`。

工具 `Tools/cs/q_bake_run.cs`。**必留对照** `Run01_Ctrl`（`keep = 1.0`，行为应与原片段
完全一致），用来证明烘焙器本身没引入退化 —— 实测剑尖行程 7.611 m 逐位相同。

**同一个坑第二次发作：「按名字匹配」是单点故障**

首版烘焙片段叫 `Run01_IdleArm`，名字里含 `Idle`
⇒ `CombatStance` 的 `Contains("Idle")` 把 **Run 状态的槽位**误认成 Idle 槽位
⇒ **Run 被覆盖成待机、跑步时角色在待机，零报错**
（与增量（十三）末尾同一个坑，上次的 `==` → `Contains` 只是把触发面放大了）。

修法：**三级匹配** ——
1. 新增显式字段 `CombatStance.idleSlotClip`（= 控制器里 Idle 状态本来的片段）精确优先；
2. 没配置才按名字猜，且**加动作关键词黑名单**（`Run/Walk/Atk/Sword/Dash/Dodge/Jump/Hit/Death/Roll/Cast`）；
3. 再找不到才放宽。

> **规矩**：凡「用字符串近似匹配资产身份」处，都必须（a）给显式配置入口、
> （b）把模糊匹配降级为兜底、（c）失配要吵不要静默。

**`FootIK.stateOffsets` 的键要从「状态名」换成「片段名」**

Idle 状态的片段运行期会在 `Rig|Idle_Loop`（非战斗）与 `Sword_Idle_Loop`（战斗）之间切换，
而偏移表只按状态名查 ⇒ **一个数值不可能同时正确**。
改为 `ResolveStateOffset` **片段名优先、状态名兜底**，
并新增只读探针 `CurrentOffsetKey` 把「这一帧用的是哪把钥匙」打出来。

| 片段 | 无IK最低 min~max | 建议偏移 | 原值 | 后果 |
|---|---|---|---|---|
| `Sword_Idle_Loop` | −0.0542 ~ −0.0427 | **0.0477** | 套用 Idle 的 0.0307 | **恒定下沉 2.35 cm**，全靠 IK 一直往上拽 |
| `Run01_Carry` | −0.1757 ~ +0.4020 | 0.1807 | 0.1735 | 按「IK 只上抬、基准宁小勿大」**保留 0.1735**（贴地后 +0.031 m ✓） |

落地 `Tools/cs/q_apply_offsets.cs`：9 条状态名 + **4 条片段名**
（`Rig|Idle_Loop` / `Sword_Idle_Loop` / `Feng_Walk_Loop` / `Run01_Carry`）——
片段名条目既让两段各拿各的值，也防止下次换片段时静默套用旧值。

**最阴的一条：左手握拳度被静默反向标定**

改完上面这些，验收只剩一项：

```
[未通过] 攻击全程两手都握着（不是五指摊开）  攻击帧握拳度峰值 右 1.547 / 左 2.601
```

HEAD 同一项是 `右 1.547 / 左 1.582` —— **右手完全没变，只有左手退化**。

逐帧取证（`Tools/cs/q_fist.cs`）先否掉第一直觉「峰值出在 Idle→Atk1 的交叉淡化帧」：
峰值落在 `Atk1Rec nt=0.75` 的**纯攻击姿态稳定帧**。
真异常是左手**全程 2.1~2.6**（比「五指摊开≈2.2」还开），右手恒定 1.55
—— 左手不是没卷，是**被反着卷了**。

横向比对早前报告即锁定 `LeftCurlSign` 由 **−1 翻转成 +1**：

| 出处 | `LeftCurlSign` | 左握拳度 |
|---|---|---|
| `q_fist2`（11:14） | **−1** | 1.50 |
| `q_fist3`（12:44）手动验证 | 左手 −70°→0.114 m 收拢 / +70°→0.214 m 掰开 ⇒ 正确符号 = **−1** | — |
| `q_fist`（本轮） | **+1** ← 反了 | 1.87 ~ 2.60 |

**根因**：`WeaponHandPose.CalibrateSign` 是**一次性**标定（`Resolve()` 里只跑一次），
且兜底 `if (|after − before| < 0.001f) return 1f` —— 而**测量手段依赖当时的姿态**，
某些姿态下 ±40° 引起的「指尖到腕」变化量会小到接近 0，于是落到兜底、
**左手被定成正号**。换一个待机片段就足以改变那一瞬的姿态。

**修法：`CalibrateSign` → `MeasureSign`，每帧当场实测**

- 每帧拿食指链当探针，±60° 各拧一次，取「指尖离腕更近」那个方向；
- 两方向差别 < 0.5 mm ⇒ **沿用上一帧**（不瞎翻）；
- 换符号需另一个方向明显更优（> 2 mm，**迟滞**），避免逐帧横跳把手指抖花；
- 探针改完**原样还原**（`Curl` 随后会重新施加真正的卷曲）。

**并加一道「失效要吵」的守卫**：Armed 超 12 帧后若握拳度 > **2.05**
（比五指张开还开），打一条 `Debug.LogWarning`；恢复时再打一条。
这类失效**不会自己报错**，本项目已因此吃过两次亏。

⇒ 左峰值 **2.601 → 1.463**，验收回到 `右 1.547 / 左 1.582`，与 HEAD **逐位一致**。

**Blender 路线的评估**（回答用户的询问）

技术上可行：Blender 有官方 MCP（`blender-mcp`），接入后等价于拿到一个 **Python 执行口**
（`bpy`），可程序化建骨 / 改权重 / 生成关键帧 / 批量导出 FBX。
「操控 Blender」本身没有障碍。

但**不该现在接**：

| 环节 | 实情 |
|---|---|
| 动作好不好看 | `bpy` 能写「手臂摆 30°」，写不出「打起来有魂」。手感来自关键帧的**节奏与缓动**，要人反复看反复调 |
| 与现成的比 | 已接入 UAL1/UAL2（剑术）、KI（跑步）、Feng（主角带 10 段）**4 套免费库**，覆盖移动/攻击/待机/受击全部需求；自制的只会更差 |

**什么时候值得上**：需要现成库里没有的专属动作（如与水墨刀光强绑定的「收刀入鞘」「蓄力重击」），
且已接受「要反复看反复调」。那时再装 MCP，用它做批量导入导出 / 重定向 / 程序化修数据，
把审美判断留给人。

## Sprint 2.1 · Day 3 增量（十五）：持剑待机跨立 / 跑步脚被拧 90° / 跑步整体偏高

**触发**：用户看过增量（十四）的录屏后提了三条观感 + 一个指令：

> 「你帮我装上mcp，然后后面再说做不做，这个跨立太丑了吧，拿剑静止不动的时候；然后跑步的时候，脚都90度旋转了，神了」
> 「跑步的时候高出来一格」

**这三条不是三件事**：第 2、3 条同源 —— 脚被拧到生理极限之外，触地面从「脚掌」变成「鞋的侧面」，触地质量必然崩。

### 一、跨立：拿错的待机片段本身是「出剑姿势」

判据：**自然站姿 = 双脚横距 ≈ 0.52 m 且纵距 ≈ 0.29 m**（非战斗待机实测 0.526 / 0.289）。

| | 横距 | 纵距 | 脚自身偏角 L/R |
|---|---|---|---|
| 旧 `Sword_Idle_Loop` | 0.599 | **0.090** | **18.5° / 22.9°** |
| 新 `Baked/Idle_Carry_A` | **0.524** | **0.294** | **0.4° / 0.4°** |

旧片段纵距只有 0.090 m —— 双脚几乎落在同一条横线上各自外撇，这就是「跨立 + 外八」的几何定义。

**处置**：`Idle_Carry_A` = `Rig|Idle_Loop` 底座 + 按肌肉通道分组只替换右臂 9 条（取 `Rig|Sword_Idle`@0.35 定值）。腿和躯干一条没动，站姿天然就是用户认可的那个。

### 二、跑步「脚 90 度」：源片段右脚通道超出生理极限 4 倍

| 通道 | KI `Run01_Forward` 右脚 | 真实角度 | 界限 | 同片段左脚 | 同作者 `Walk01` |
|---|---|---|---|---|---|
| `Foot Twist In-Out` | [−4.012, −0.876] | **[−120.4°, −26.3°]** | ±30° | [0.5°, 8.4°] ✅ | ✅ |
| `Foot Up-Down` | [−1.802, 2.122] | [−90.1°, +106.1°] | ±50° | [13.1°, 77.8°] ✅ | ✅ |
| `Lower Leg Twist In-Out` | [0.647, 1.892] | [58.2°, 170.3°] | ±90° | [−10.3°, 2.0°] ✅ | ✅ |

**三个对照实验锁死范围**（这一节的方法论价值比结论更高）：

1. 同片段的**左脚**正常 ⇒ 不是「跑步这条通道本来就该这么大」；
2. **同作者、同骨架的 `Walk01_Forward` 右脚也正常** ⇒ 不是「KI 的导出习惯」「KI 的 avatar」；
3. 两个 FBX 的 **importer 设置逐字段相同**（`animationType: 3` / `animationCompression: 0` / `resampleCurves: 1`）⇒ 不是导入精度。

⇒ 只剩「**这一份 FBX 的右脚数据**」。也顺带排除本项目烘焙脚本（`q_bake_run.cs` 只替换右臂 36 条）。

**T-pose 层根因**：KI 的 `B-foot.R` 局部四元数 **w=0.1**、`B-toe.R` **w=0.0**（接近 180° 的奇异姿态），而 Feng 的 `CC_Base_R_Foot` w=0.8、`ToeBase` w=1.0。**插值经过奇异点会绕远路**，把肌肉值炸到 −4.0 量级。

### 三、修法：锚点要按通道性质区分（第一版就栽在这）

公式 `newVal(t) = anchor + (leftSpan / rightSpan) × (oldVal(t) − rightMean)`，参照系用**同片段左脚**（同动作同刻，左右腿统计上应镜像）。

**`anchor` 取谁，取决于「均值差」是错误还是相位**：

- **`Twist` 类 → 取 `leftMean`（对齐）**：右脚均值 −2.623 本身就是错的（= 脚外翻 78.7°）；
- **`Up-Down` 类 → 取 `rightMean`（保留）**：左右均值差 0.253（= 12.7°）只是**相位差**。

> **第一版 `Run03_KI_Carry` 把 `Up-Down` 也对齐了，结果全循环最低点从 −0.142 恶化到 −0.241** —— 脚被整体压低、更穿地。这说明**判据要成对看**：修「脚朝向」不能牺牲「触地质量」。

`Run04_KI_Carry`（`q_bake_run5.cs`）：`Twist` 右 [0.6°, 8.5°] vs 左 [0.5°, 8.4°] ✓；`Up-Down` [9.7°, 74.4°]（均值保留）。右臂同时统一接 `Rig|Sword_Idle`@0.35 —— 与 `Idle_Carry_A` 同源，修掉旧版「待机右臂下垂 / 跑步右臂持剑」的跳变。

**活体左右差：55.4° → 17.2°**（剩余的 17.2° 来自脚踝 pitch，左右腿相位不同属正常）。

### 四、跑步「高出来一格」：静态基准与动态 IK 的分工

```
AppliedBodyOffset = BodyBase + BodyLift
need = (groundY + groundClearance) − low.y − BodyBase
BodyLift = need > 0 ? smooth(need) : 0        // ← 负值被丢弃：只上抬，不下降
```

⇒ **浮空多少完全由静态 `BodyBase` 决定**，IK 只管「补穿地」。

**一维扫描 → 「贴地」与「不飘」不可兼得**：

| `BodyBase` | 实测最低 | 中位（= 飘） |
|---|---|---|
| 0.04 | −0.127 | **0.120** |
| 0.25 | **+0.001** ✓ | **0.313** ❌ |

各档「中位 − 最低 ≈ 0.31 m」恒定 —— 这就是**动画本体鞋底高度的分布跨度**，无法靠挪 `BodyBase` 消掉。

**破局点：`BodyLift` 的平滑跟不上落地。** `liftSmooth = 14` ⇒ τ ≈ 71 ms；跑步落地在 ≈100 ms 内最低点突变 0.2 m —— 平滑还没走完，脚已经穿过去了（`BodyBase=0.04` 档 `BodyLift` 冲到 0.261 仍有 −0.127 漏穿，实证）。

**二维扫描 → 提速平滑后可两者兼得**：

| (`BodyBase`, `liftSmooth`) | 实测最低 | 中位 | 穿地帧% |
|---|---|---|---|
| (0.24, 14) 旧 | −0.010 | **0.164** | 0.0% |
| **(0.12, 150) 采用** | **−0.015** ✓ | **0.048** | **0.0%** |

**中位浮空 17.4 cm → 4.7 cm。** `liftSmooth` 是全局量，因此跑全套体检确认 Idle/Walk/Dash/Atk1-3 **零回归**（全部仍 0.003~0.005 m）。

> 「抖动」（相邻帧 `BodyLift` 差分的 RMS）从 0.0012 涨到 0.0107 m/帧 ≈ 0.64 m/s —— 但它**不是噪声**，是「跟随支撑脚落地」必需的竖直运动。真实噪声要看 `LowestMeshY`，而它由 `BakeMesh` 逐顶点算出，确定性无噪声。

### 一、`Time.timeScale` 的第三次发作（震屏）

震屏**逐帧直接写 `transform`**（不走 `SmoothDamp`），所以 `_shakeTimer` 减不到 0 就每帧都在抖；
`timeScale = 0` 时 `deltaTime == 0` ⇒ 一次命中触发的震屏会抖到玩家选完技能为止。

**三层处置，且刻意三层都留**：① 相机内递减改 `unscaledDeltaTime`；② `timeScale <= 0` 时**直接把震动结清**
（暂停时画面上任何东西都不该动，哪怕用 unscaled 自然衰减）；③ 新增 `ThirdPersonCamera.StopShake()`，
由 `RunManager.TakeOverTimeScale()` 在进 Reward / 结算前主动调 —— 并把 §9.15 的 `HitStop.ForceEnd()`
一起捆进这个入口，以后再加吃 timeScale 的系统也不必改四处调用点。

> `StopShake()` 必须**连幅度一起清零**：只清 timer 的话，残留大幅度会挡掉下一次小震动
> （`Shake()` 第一行是"更强的不打断"判据）。

### 二、「走路太慢」的真相：档位语义

| 档位 | 触发 | 速度 | 播放倍率 | 步频 |
|---|---|---|---|---|
| 默认（跑） | 不按修饰键 | 4.0 m/s | 0.97× | 3.23 步/秒 |
| 慢走 | 按住 Shift | 1.25 m/s | 1.37× | 2.06 步/秒 |

走档片段原生 0.91 m/s，倍率留在 1.0~1.6 才自然 ⇒ **物理上限约 1.5 m/s**；
曾把 `walkSpeed` 提到 1.4（倍率 1.54）得到**竞走级小碎步**（步频 2.31），已回退（§9.10）。
而跑档原生 4.12 m/s、取 4.0 的倍率是 0.97 —— **它本来就该是默认档**。
44 m 场地里以 1.25 m/s 从中心走到外墙要十几秒，这就是用户说的"太慢"。
处置：**Shift 语义改成「按住 = 慢走，不按 = 跑」**，两档都落在各自片段的舒适区。
（`SetInjectedMove` 的注入路径不做 Shift 反转，验收脚本按字面理解即可。）

（墙 / 地 / 柱 / 台的纸白、淡墨、阶数、飞白都差一点 —— 共用一份会让全场景像一张贴图）：

| 材质 | 纸白 RGB | 淡墨 RGB | 阶数 | 飞白 |
|---|---|---|---|---|
| `M_Whitebox_Wall` | (0.952, 0.947, 0.928) | (0.47, 0.492, 0.53) | 3 | 0.52 |
| `M_Whitebox_Ground` | (0.925, 0.919, 0.899) | (0.52, 0.535, 0.56) | 3 | 0.46 |
| `M_Whitebox_Pillar` | (0.905, 0.9, 0.88) | (0.44, 0.46, 0.5) | 4 | 0.55 |
| `M_Whitebox_Platform` | (0.958, 0.953, 0.934) | (0.5, 0.518, 0.552) | 3 | 0.48 |

另新增 **`InkWash/InkSky`** 天空盒（默认天空盒是渐变蓝，与宣纸白放一起就是"积木玩偶放在塑料底座上"的来源）。

**"发灰"是四处同时拽，逐项松开**：环境光 sky 0.62→**0.885** / equator 0.5→**0.815** / ground 0.3→**0.64**、
Sun 1.15→**1.30**、Fill 0.28→**0.45**、角色 `_PaperColor` 暖灰 (0.847, 0.812, 0.741)→**纸白 (0.96, 0.951, 0.925)**、
宣纸 `paperStrength` 0.45→0.26 / `vignette` 0.32→0.14 / `tintStrength` 0.30→0.12 / `paperTint`→(0.98, 0.972, 0.95)。
**唯一没往亮处调的是 `inkDeepen` 0.25→0.20** —— 水墨的张力来自"纸白 ↔ 墨黑"的跨度，
把暗部也抬起来就只剩一片灰。**提亮 ≠ 全部调亮。**

**顺带修掉一个"注释骗人"的老 bug**（本项目第二次，第一次见 §9.1.2 三·3）。`InkEdge.shader` 注释声称
`abs(dL−dR)` 是"Roberts 式二阶差分，能把掠射角地面的斜坡减掉" —— **它是错的**，那是一阶中心差分：
线性斜坡上 `dL = dC − s·h`、`dR = dC + s·h` ⇒ `abs(dL−dR) = 2·s·h`，**正比于斜率**，只在平坦平台才为 0。
后果：透视下斜率很大的掠射角墙面 / 地面整片被判成轮廓 ⇒ 画面出现**贯穿并指向灭点的斜线**（像工程图的三角剖分线）。
**不改成真正的二阶差分**（拉普拉斯在阶跃边缘中心过零 ⇒ 每条边画成**双线**，靠飞白遮不住），
改为**大幅抬高死区**：`_DepthBias` 0.30 → **2.0**（`Range` 上限 1 → 6）。
本场景物体边界几乎都有法线差（走 `nEdge`）、天空剪影有 `sEdge`，深度项只兜"同一物体自遮挡"这一小块。

### 四、挥墨：三个假设连环证伪后，真凶是三角剖分 ★

| # | 假设 | 实验 | 结论 |
|---|---|---|---|
| 1 | shader 里的 `clip(a − 0.004)` 阈值线 | 早已拿掉 | 锯齿仍在 ⇒ 证伪 |
| 2 | 高频拉丝噪声（`_StreakScale`） | 44 → 7 | 锯齿仍在 ⇒ 证伪 |
| 3 | 背面剔除（绕序交替，一半被剔掉） | 把全部绕序统一 | 锯齿不变 ⇒ 证伪 |

**决定性动作是逐层关掉后处理**（`04_nopost` 三层全关，锯齿依然存在 ⇒ 与后处理无关，归属几何 / shader）。
再把齿数变成可控变量：顶点色统一成不透明白 → 齿更明显（⇒ 与浓淡无关）；段数 28→200 → **齿变成 199 个**
（⇒ **齿 = 网格的四边形段**）。

**放弃"从渲染图反推几何"**，直接导出运行时真实网格（顶点 + 顶点色 alpha + 三角形 + 有符号面积），
在 Python 里按**重心坐标离线光栅化**与截图对拍。前 4 个三角形的**有符号面积正负交替**就是病灶指纹：

```
修复前：t0  0 1 3  −0.004176    t1  0 3 4  +0.006018   ← 交替
修复后：t0  0 1 4  −0.004475    t1  0 4 3  −0.006018   ← 一致（对角线正确）
```

病因：四边形共享的是**同一环上的边**而不是**对角线** ⇒ 两个三角形第三个顶点同侧 ⇒
**重叠的蝴蝶结 + 四边形靠中脊侧留下三角形空洞**。画线框后一眼可见**每个四边形只画出了一半**。

**修法**：沿真对角线 `p0→q1` 剖分｜**三环 → 五环**（`kU = 0/0.26/0.5/0.74/1`，三环的"满浓"只落在一条线上，
屏幕上是一道细灰线）｜**粗细与浓淡解耦**（`kA = 0.10/0.82/1/0.82/0.10 × pow(taper, 0.6)`，
共用一条曲线会让整笔只有正中一小段满浓度）｜收笔下限 0.22→0.10｜四条环带**共用一个循环**
（那段"内带外带各写一遍"正是 bug 来源）。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 网格 | verts=84 / tris=108 / rings=3 | **verts=140 / tris=216 / rings=5** |
| 三角形绕序 | 逆 54 / 顺 54（**交替**） | **逆 0 / 顺 216（一致）** |
| 观感 | 内缘一排等距三角齿、齿间有缺口 | **中间浓、两侧化开、两端收尖的一笔平滑墨** |

**环数三次教训**：两条环 = 剪影式硬边色块 ／ 三条环 = 一道细灰线 ／ 五条环 = 有宽度的浓墨。

另一条元凶级发现：**`InkWash/InkSlash` 长期不存在**（`Shader.Find` 静默失败）⇒ 刀光退回**不吃顶点色**的
`URP/Unlit`，而顶点色是这套笔锋的**全部**表达手段。凡"特效参数怎么调都没反应"，先查 shader 资产是否真的取到了。

### 五、连招卡帧：两个入口，同一个根因

| 变体 | 路径 | 表现 |
|---|---|---|
| C | 逻辑判"取消窗口还开着" ⇒ `AdvanceCombo` ⇒ `SetTrigger(Attack2)` | 状态机正跑 `Atk1Rec → Idle` 退出混合，该出边 `interruptionSource = None` ⇒ **已开始的过渡无法被打断**，触发器挂着没人消费 |
| E | 按住前进（跑）的同一帧按攻击 | 动画正跑 `Walk → Run` 过渡（同样 `None`）⇒ `Attack1` 被卡住；实测按下后 **12 帧仍停在 `Walk→Run`**，"按了攻击却在跑步" |

**危害不在当下而在下一次**：残留的 `Attack2` 会在**下一次**攻击播到 `Atk1Rec` 的瞬间突然生效，
动画从半途直接跳进第二段 —— 这就是"卡在中间一个奇怪的动作"。

**三处处置**：

1. **资产层**：出边 `interruptionSource` 设 **`Source`**（不是 `SourceThenDestination` —— 后者会让目标状态侧也能打断，
   例如 `Idle→Walk` 被 `Walk→Idle` 打断 ⇒ 原地来回抖）。覆盖两组：`Idle/Walk/Run/Dash` 之间的移动过渡、
   `Atk1Rec/Atk2Rec/Atk3 → Idle/Walk/Run/Dash` 的后摇退出。
2. **转移顺序**：Unity 的转移**按列表顺序求值、先满足者胜**。原列表里移动类排在攻击类前面，
   而 `PushAnimatorState` 写 `Speed` 用**阻尼**（`SetFloat(..., 0.10f, dt)`），攻击开始后 `Speed` 还要 0.1~0.3 s 才落到 0
   ⇒ 这段窗口里 `Run→Walk` 一直成立、攻击触发器永远抢不到。重排规则：**条件里带 `Trigger` 的转移排前面**
   （稳定分区，同组内相对顺序不变）。用"是不是 Trigger"当判据而非"目标是不是攻击态" —— Trigger 就是"玩家按了一下"，
   天然比"当前速度是多少"这种持续状态优先级更高；这条规则也自动覆盖 `Dash`。
3. **代码层（第二道保险）**：新增 `_restartQueued`，并在回到移动态时把三个攻击触发器一律 `ResetTrigger`。

**`_restartQueued` 为什么不能复用 `_attackQueued`**：

| 字段 | 含义 | 有效期 |
|---|---|---|
| `_attackQueued` | "我还想接**下一段**连击" | 只在取消窗口打开**之前**有意义，窗口一开就消费；有效期 = `attackInputBuffer` **0.25 s** |
| `_restartQueued` | "这一段接不上下一段了（后摇已过 / 第 3 段不可取消），我只想**再打一遍**" | 从按下一直保留到阶段回到移动态再消费 |

复用会让玩家这次按键**静默消失** —— 0.25 s 撑不过"第 3 段收招 + 后摇混合"（实测 **0.5 s 以上**）。
`TryAttack()` 因此从"接不了就 `return false`"改成三分支：①取消窗口开着 → 立刻接；②还有下一段但窗口没开 → 进输入缓冲；
③**接不了也不丢**，记成"收完重新起手"，由 `EnterLocomotion` 兑现。
立下约定：**接不上下一段时绝不能丢玩家的按键。**

### 一、地板「随视角变化」的灰面：真因是**材质色差**，不是光照

不要下猜。用 `Tools/cs/r8_facts.cs` 做**四变体同帧对照**（每变体渲 16×10 亮度网格，逐格差分）：

| 变体 | 受影响格数 / 160 | 结论 |
|---|---|---|
| ① 关方向光阴影 | 30 | 只解释斜向灰带 |
| ② 高台改用地面同参数 | **98** | ← 主因 |
| ③ 关积墨 | 11 | 次要 |
| ④ 墙改用地面同参数 | 9 | 无关 |

`M_Whitebox_Platform._BandBias = -0.06` 而 `M_Whitebox_Ground = +0.18` —— 两者并排必然显出一道灰台，
且 0.24 的差被墨阶量化器放大成整阶。修：高台 `_BandBias → +0.18` 与地面统一；
斜向灰带（方向光阴影硬边）用已有的笔触噪声揉开（幅度挂现有 `_StrokeAmp`，**不新增 uniform**）。

### 二、「没有纹理效果」再犯：参数全部超过屏幕 Nyquist

逐参数查 Nyquist 频率：`_GrainScale = 96`（周期 ≈ 1 cm）、`_StrokeScale = 7` —— 在 1080p 下全部超标，
噪声每个像素都在跳 ⇒ `InkNyquistFade` 把它们**全部淡出**；而积墨走 `_BrushTex`，被 mip 平均成常数
⇒ 遮罩恒 0（关掉 `_InkMottle` 全屏只变 0.0024，等于没接）。

修法三件：
1. 新增 `InkDetail2()` —— **LOD 退级**而非归零：高频 `Fbm2(q)` 与 0.25× `Fbm2(q*0.25)` 按足迹淡入淡出。
   ★ 第一版写成"淡出到 0.5 常数"是错的：视觉上等于**删掉纹理**，大平面会退化成一块光板。
2. 积墨改**程序化**（去掉 `_BrushTex`）。
3. 尺度落到 `_GrainScale 18 / _StrokeScale 1.5 / _MottleScale 2.2`。

★ 这四个属性在 `M_Whitebox_Ground / Platform / Wall / Pillar` 的 `.mat` 里**根本没有被序列化过**
 ⇒ 只改 shader 默认值必然不生效，必须两处都补（项目硬规矩 #6）。

### 三、「怪物太丑」的真根因：运行时生成的敌人**从未被水墨化**

`InkMaterialForcer.ForceAll()` 只在 `AfterSceneLoad` 跑一次，只覆盖**当时已存在**的对象；
而 `WaveSpawner` 是运行时产怪 ⇒ 后生成的怪一直穿着 KayKit 原始材质
（亮蓝灰骨头 + 橙斗篷 + 发光眼），是满屏水墨里**唯一的高饱和色**，最抢视线。
修：`SpawnOne` 里补一次 `InkMaterialForcer.ForceInk(go, go.name, true)`。
（`InkMaterialForcer` 自己的文档注释早就把这种状态写成"像普通积木玩偶"，只是没覆盖运行时这条路。）

### 四、★ 事故：被中断的 `git rebase` 摧毁了本地对象库

`push` 被拒（远程有那边的新提交）⇒ 走 `git rebase origin/main` ⇒ **被 SIGTERM 打断**。
之后 `.git/objects` 只剩 **497 个 loose object、无任何 pack**，连刚 fetch 下来的
`origin/main` 都读不出 —— 引用还在、对象没了。**工作区文件完好**（这类损坏从不动工作区），
故处置是**重建**而非抢救：

1. 损坏的 `.git` **改名保留**并移出项目目录（`.git_corrupt_InkWash_20260917`），
   免得被后续的 `git add -A` 当成待提交内容；
2. `git init -b main` + `remote add` + `fetch` —— 拿到 **3265 对象 / 566 MB** 的完整历史；
3. `git reset --mixed origin/main`：**只对齐索引、不动工作区**，先看清"工作区 vs 远程"的
   真实差异（920 条）。确认关键文件 `WaveSpawner.cs` / `PlaytestHarness.cs` / `Main.unity`
   在远程**都停留在我修复之前**（那边没动过）⇒ 我的修复可以直接叠上去，不会覆盖别人的工作；
4. `git checkout origin/main -- .` 取远程全部文件，再从备份把本机那 14 个文件叠回来；
5. 清掉 `Tools/cs` 下 **378 个已归档的重复副本** —— 那边 `889de56` 把 408 个历史脚本归到
   `Tools/cs_archive/`，本机因仓库损坏停留在归档之前、旧位置还留着一份。判据是
   「未被 git 跟踪 + 归档目录有同名 + **忽略行尾后内容等价**」：直接逐字节比会把 407 个
   文件全判成不同，**实际只是 LF vs CRLF**（抽样 `diff --strip-trailing-cr` 差异 0 行）；
6. 重新提交（`a351909`）并 push。

**教训四条**：

- **rebase 不是"安全操作"**：它要重写工作区与索引，中断后可能留下不一致状态。两台机器
  交替提交时，**`merge` 比 `rebase` 稳妥**（两边文件不重叠就能干净合并，本轮即如此）。
- **中断之后第一件事是查对象库完整性**，而不是接着跑 git 命令：
  `git count-objects -v` 一眼就能定性（`in-pack: 0` + `pack/` 目录为空 = 坏了）。
- 仓库损坏**不会**动工作区 ⇒ 源码在就不慌，重建成本 = 一次 clone + 重放改动；但动手前
  **必须先备份工作区的独有改动**（本轮先把 3 个修复文件 + 整个 `Tools/` 复制到项目外）。
- 早先那次 `git diff HEAD...origin/main` 还能正常输出 4 个文件差异 —— **这就是"当时对象
  还好好的"的时间锚点**，破坏就发生在它之后的唯一一步。
