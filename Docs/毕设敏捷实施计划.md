## 2. 敏捷框架设计（PMP 映射）

因为是 7 天极限工期，**不套用标准 Scrum 的 2 周 Sprint**，而是压缩成 **1 天 = 1 个 Sprint，共 7 个 Sprint**。理由：反馈周期越短，越能在当天就发现方向错误。

| PMP 知识领域 | 在本项目中的落地形式 |
|---|---|
| 整合管理 | 本计划书即整合基线；每日站会用一条消息汇报，变更走 MoSCoW |
| 范围管理 | 第 4 节 Product Backlog（含故事点）；**范围冻结**，新增需求一律进"Won't" |
| 进度管理 | 1 天 1 Sprint；每日燃尽（见 Excel `燃尽图` 表） |
| 成本（时间）管理 | 故事点即时间成本；每日目标 16 点，超支次日砍 Should 项 |
| 质量管理 | 第 9 节 DoD：编译零错误、Console 无红字、1080p≥60fps |
| 资源管理 | AI = 主要劳动力；人 = 决策/账号/验收三类不可替代动作 |
| 沟通管理 | 每 Sprint 结束输出「截图 + 状态 + 阻塞」三件套 |
| 风险管理 | 第 8 节风险登记册，R3/R5 为高优先级 |
| 采购管理 | 素材获取走 CC0 优先策略（第 6 节） |
| 干系人管理 | 导师 = 关键干系人；每 2 天准备一次可展示的进度快照 |
| 变更管理 | 需求冻结；确需变更须砍掉等量故事点（等价交换） |

**角色分工（关键：把人的时间花在 AI 做不到的事上）**

| 只有你能做的 | AI 做的 |
|---|---|
| 开/关 Unity 编辑器 | 写全部 C# 脚本与 HLSL Shader |
| 注册并登录 Mixamo / Asset Store（需账号） | 通过 Bridge 建场景、挂组件、连引用 |
| 下载素材并放进工程 | 改材质参数、调光照、布点 |
| 看效果做主观判断（"墨味够不够"） | 进 Play 模式、截图、读 Console 排错 |
| 论文里的表述、创新点定位、导师沟通 | 论文素材整理、图表数据、初稿撰写 |
| 最终验收与录屏确认 | 性能分析、优化、测试用例 |

## 3. 游戏设计范围（Demo 版）

**定名**：`墨刃 · InkWash`　**类型**：3D 第三人称水墨动作 Roguelike（单局制）

**核心玩法循环**（对应大纲 4.1）

```
主菜单 → 进入「墨境」一局 → 
  房间①：清怪 → 三选一技能 → 
  房间②：清怪 → 三选一技能 → 
  房间③：精英怪 → 三选一技能 → 
  BOSS → 通关结算 / 死亡结算 → 回主菜单
```
单局目标时长 **5–8 分钟**。

**角色能力**（对应 4.2）

| 动作 | 说明 |
|---|---|
| 轻攻击三段连击 | 第 3 段带前冲位移，可取消后摇接闪避 |
| 蓄力重击 | 破防、高伤害、长后摇 |
| 闪避翻滚 | 含无敌帧（i-frame），可穿身位 |
| 拔刀斩（技能位） | 居合式突进斩，消耗墨气 |

**敌人 3 种**（对应 4.3）

| 敌人 | 行为 |
|---|---|
| 墨徒（近战） | 追击 → 挥砍 → 硬直 → 循环 |
| 墨偶（远程） | 保持距离 → 投掷墨弹 → 被贴近则后撤 |
| 墨魇（精英） | 范围横扫 + 冲锋，有可弹反窗口 |

**局内成长**（对应 4.4）：以 ScriptableObject 定义技能池，升级时加权随机三选一。候选池示例：攻击力↑ / 攻速↑ / 暴击率↑ / 连段扩展至四段 / 墨刃投影（远程剑气）/ 命中吸血 / 闪避距离↑ / 背水一战（低血量增伤）等 **10–14 条**。

#### Sprint 2.1 · Day 2 增量 — 动画与手感返工（用户看片后反馈 6 项）

用户看完 S2 验收录屏后逐条反馈：①走路仰着身子 ②攻击第一下动作奇怪 ③跑步的动作呢 ④右键是什么鬼动作 ⑤刀光在刀还没速度时出现 ⑥攻击时脚陷下去。
**出口**：6 项全部有可量化证据，且 S1/S2 全量回归零未通过。

| 反馈 | 根因 | 处理 |
|---|---|---|
| ① 走路仰着身子 | 沿用 UAL2 `Walk_Carry_Loop`（搬东西的姿势，上身后仰） | 换 UAL1（CC0）`Walk_Loop` / `Jog_Fwd_Loop`，新建 `Walk`/`Run` 两态；实测躯干 Walk +10.2°、Run +12.1°（前倾） |
| ② 攻击第一下动作奇怪 | 上半身遮罩层（UpperBody）把攻击的上半身锁死在待机抱臂姿势 | **删除遮罩层**（Animator 只剩 layer 0）。同时发现第二个元凶：见下方「动画被前冲抢走」 |
| ③ 跑步的动作 | 控制器的 Run 状态没有独立片段 | 落地 `Run` 状态 + `RunEnterSpeed 3.0 / RunExitSpeed 2.5` 迟滞转移 |
| ④ 右键是什么鬼动作 | 右键=冲刺（翻滚）；`Dash` 复用 UAL1 `Roll` | 保留语义（闪避=翻滚），并用姿态体检 + 状态断言把它纳入验收 |
| ⑤ 刀光过早 | 挥砍事件一到就开拖尾，此时刀还在抬手、几乎没速度 | 拖尾改为**按刀刃线速度门控**（进入 3.0 / 维持 1.6 迟滞 + 0.05s 起手静默）；实测起播刀刃速度 11.3 m/s ≫ 阈值 |
| ⑥ 攻击时脚陷下去 | FootIK 读的是脚踝 IK 锚点，不是真实脚底；且两套动画髋部基准不一致 | 重写 `Player/FootIK.cs`：**逐帧 BakeMesh 取真实网格最低点** + 9 条静态基准偏移（压动画自带浮空）+ 只抬不压的动态夹地。姿态体检 4/4 |

**过程中发现的两个"看不见的"真实缺陷**（都不是用户直接点名的）：

1. **动画被攻击前冲"抢走"** —— `Speed` 参数原本直接吃 `DesiredSpeed`（= `_velocity.magnitude`），
   而攻击前冲就是往 `_velocity` 赋值（峰值 ~11 m/s）。状态机里 Idle→Walk(>0.15)/Walk→Run(>3.0)
   排在「攻击触发器」转移**之前**，于是发招那一帧速度参数瞬间冲过 Run 门槛，
   动画被拽去走路/跑步、攻击触发器迟迟不落地；0.35s 后逻辑判定"没进攻击态"直接退回移动 →
   **取消窗口永远打不开、连击推不到第 3 段**。
   修法：新增 `_blendSpeed`（**移动意图**速度）驱动混合树 —— 移动阶段=输入目标速度，
   攻击/冲刺=0，仅后摇取消窗口里真按了方向才交回。这同时解释了②"第一下很怪"的体感。
2. **音频的 NRE 会静默打断刀光** —— `PlayerController.SwingStarted` 是**多播**，
   `AudioDirector` 是第一个订阅者；当 `AudioKit` 处于半初始化（`Settings.IsSoundOn == null`，
   编辑器 Play 会话跨脚本重载时会出现）时它抛 NRE → **C# 多播遇异常即中断** →
   排在后面的 `SwordVfx` 一次都收不到事件 → 现象是"完全没有刀光"，而日志里只有一条与刀光无关的音频报错。
   修法：`GameAudio` 改为防御式门面（检测到半初始化先补跑 `OnInit`，补不上就静默降级），
   并用反射人为置空 `IsSoundOn` 的回归脚本 `Tools/cs/s2_probe_audioguard.cs` 验证自愈。

**验收结果**：**S1 31/31 + S2 54/54 + 姿态体检 4/4 + 音频 6/6，合计 0 未通过** → **M2 保持达成**
证据视频：`Tools/screenshots/GameView_2026-09-13_21-55-10-611.mp4`（战斗）、`GameView_2026-09-13_21-55-32-419.mp4`（移动）

#### Sprint 2.1 · Day 2 增量（二）— 跑步动作返工：把"游戏速度"降到动画能支撑的范围

用户第二轮反馈：跑步动作抽象，"两条腿在原地倒腾，不像往前迈步"。

**先纠正一个沿用两版、其实是错的判断**：一直拿「播放倍率落在 1.0~1.8 是健康区间」衡量脚步是否自然。
倍率只说明片段被拉伸了多少，**真正的观感指标是步频**（= 2 步/循环 ÷ 循环时长）。
1.81× 摊在一段 0.933s 的慢跑上就是 **3.9 步/秒** —— 已经超过真人冲刺（4.0~4.4），腿当然像在原地倒腾。

**实测各移动片段的原生地面速度**（新增 `Tools/cs/s2_probe_refspeed.cs`）：

| 片段 | 循环 | 原生地面速度 | 单步位移 |
|---|---|---|---|
| `Walk_Loop` | 1.333s | **1.15 m/s** | 0.77m |
| `Jog_Fwd_Loop` | 0.933s | **≈2.9 m/s** | 1.34m |
| `Sprint_Loop` | 0.667s | **≈3.7 m/s** | 1.24m |

方法可信度：同一套量法在 Walk 上算出 1.15 m/s、单步 0.77m，与真人走路吻合。
（量法本身踩了 6 个坑；正确判据 —— **在角色根节点局部空间量、锁接触点、只取竖直速度≈0 的帧** ——
已沉淀进 `unity-codely-bridge` skill，下次别重蹈。）

**核心矛盾**：UAL1 这套素材最快只有 ≈3.7 m/s（13 km/h），而原 `runSpeed = 5.6`（20 km/h）。
**跑速超出素材设计范围 50% 以上，腿不可能不倒腾**。而且换片段解决不了：换成更快的 `Sprint_Loop` 之后
步频反而从 3.87 升到 4.54 —— 因为 Sprint 的步幅（1.24m）比 Jog（1.45m）还短。
**能降步频的只有降 runSpeed。**

**处理**：

| 项 | 改动 |
|---|---|
| `Run` 片段 | `Jog_Fwd_Loop` → **`Sprint_Loop`**（动作幅度本来就是按高速画的） |
| `runSpeed` | **5.6 → 4.2 m/s**：倍率 1.14×、步频 **3.40 步/秒**、单步 1.22m，落在人类跑步区间 |
| `runRefSpeed` | 3.10 → **3.70**（实测值；虚高会让脚打滑） |
| `walkRefSpeed` | **故意保留 1.55**（实测只有 1.15）：`walkSpeed 2.2` 本身也超出素材范围，取实测值步频会变 1.91×。这是"拿一点滑步换腿速"的折中，根治要降 `walkSpeed`（本轮用户决定先不动走路） |

**顺手修掉两条自欺欺人的验收断言**（这才是虚高值能活到现在的真正原因）：

1. 「疾跑步频明显快于步行」原来比的是**播放倍率**（1.14 vs 1.42）—— 两段片段长度不同（1.33s vs 0.67s），
   比倍率是拿苹果比橘子。改成比**真实步频**（`CombatSample.clipLen` + `stepsPerSecAvg`），
   并加上界断言（走路 ≤3.0、跑步 ≤4.4 步/秒）防止以后再退化。
2. 「播放速度 = 实际速度 / 参考速度」那条断言是**同义反复**：它反推的"片段速度"就是拿 `refSpeed` 除出来的，
   `refSpeed` 写错也永远测不出来。要真正校验，必须把"独立实测的原生速度"写进断言做对比。

#### Sprint 2.1 · Day 2 增量（三）— 跑步「扭腰」：换成成品片段 + 按片段重量参考速度

用户第三轮反馈：「这个跑步还是扭腰啊，你能不能直接网上找对应的成品啊？……你自己验收自己录屏，自己检查然后提交吧，有问题就再改」

**先量化，再决定换什么**（新增 `Tools/cs/s2_probe_runpose.cs`、`s2_probe_ab.cs`）。
度量方式：在角色根节点局部空间里取「髋线偏航（左/右大腿根连线）」与「肩线偏航（左/右上臂根连线）」，
用 `DeltaAngle(肩, 髋)` 的峰峰值当扭转；并交叉校验 **Hips 骨骼自身偏航**（排除投影伪影：
髋线三维长度恒定 0.2286m、水平/三维投影比 0.996，说明读数可信）。

同条件（同角色 / 同 Avatar / MotionSpeed=1 / 同机位）横比：

| 片段 | 骨盆(Hips)偏航 p-p | 胸腔偏航 p-p | 扭转(髋+肩) | 原生地面速度 | 单步位移 |
|---|---|---|---|---|---|
| Quaternius `Sprint_Loop` | 42.7° | 15.6° | 61.1° | 7.20 m/s | 2.40m |
| Quaternius `Jog_Fwd_Loop` | 55.3° | 27.5° | 85.9° | 6.21 m/s | 2.90m |
| **Kevin Iglesias `Run01_Forward`** | 50.5° | 16.7° | 73.6° | **4.49 m/s** | **1.35m** |

**关键结论：这个指标不能单独当质量判据。** 它等于「髋线偏航 + 肩线偏航」直接相加，对**摆臂幅度**同样敏感——
KI 片段读数反而更大（73.6° > 61.1°），但连拍图（`Tools/screenshots/ab/`）里明显更收、更稳。
真正决定观感的是三件事：**步频是否落在人类区间、脚是否打滑、四肢是否同相位**。
所以换片段时以**连拍图**为准，指标只做辅助（这条已写进 `Tools/install_kianim.py` 的文档注释）。

**为什么最终选 KI `Run01_Forward`**：实测原生 4.49 m/s、单步 1.35m、200 步/分，全部落在真人跑步区间；
Quaternius 那两段反推单步 2.4~2.9m，是"跨大步"式的夸张跑，速度再被拉高就必然倒腾。

**处理**：

| 项 | 改动 |
|---|---|
| `Run` 片段 | Quaternius `Sprint_Loop` → **Kevin Iglesias `Run01_Forward`**（本机 Asset Store 缓存提取；新增 `Tools/install_kianim.py`，因为 `Assets/ThirdParty/` 不入库） |
| `runRefSpeed` | 3.70 → **4.49**（按**新片段**实测；不换参考值，脚会以 ≈0.9 m/s 往后滑） |
| `runSpeed` 脚本默认值 | **5.6 → 4.2**（补上一轮的漏改：上一轮只把预制体改成 4.2，脚本默认值还写着 5.6，两边不一致，事后无法判断哪个生效） |
| FootIK `Run` 基准偏移 | -0.155 → **-0.046**（偏移是**绑在片段上**的：新片段「无 IK 最低」只有 +0.049，不跟着改就穿地 10.6cm） |
| 步频断言 | 把上一轮**只在文档里写过、代码里没改**的两条真正落地：改为比 `stepsPerSecAvg`，并补**上界**（走路 ≤3.0、跑步 ≤4.4 步/秒） |

**触发**：用户看片后反馈——① 动作与披风有穿模；② 人物"太卡通"，要求**中国传统古风 + 飒**；③ 明确**只要免费素材**。

**根因诊断（先定性再动手）**：

| 现象 | 真实原因 | 说明 |
|---|---|---|
| "太卡通" | **比例问题，不是渲染问题** | KayKit `Rogue_Hooded` 是 **3 头身 Q 版大头娃娃**，水墨 Shader 调得再好也救不回来 |
| "披风穿模" | **绑定结构问题，不是动画问题** | 兜帽披肩是**一整块刚性网格**、只蒙皮到 Spine/Clavicle，不感知手臂 → 摆臂必然扫过静态体积。**调动画参数永远修不好** |

**素材寻源结论**：**免费 + CC0 + Unity 可用 + 中国古风 + 正常比例 + Humanoid** 的角色在海外渠道**不存在**
（Quaternius / Kenney 全是卡通低模；OGA / Poly Pizza 只有 `.max` + 非商用；Sketchfab 下载要 OAuth；
itch.io 在本机网络不可达）。**但 Unity 中国资源商店是不同的池子，那里有 ¥0 的古风角色** —— 项目用团结引擎，
可直接用。选定 **F1「武侠风格角色-锋」**（`assetstore.u3d.cn/…/assetstore-package-20005749`，¥0）。
检索路径已固化为技能 `unity-asset-sourcing`。

**素材体检（编辑器直接读 Unity 资产，不看宣传图）**：46 606 三角面 / `URP/Lit` / `FengAvatar` 有效且
**52 根 Humanoid 骨全映射** / `CC_Base_*` **Reallusion 专业骨架** / 自带 10 段 `.anim` 全部 `isHumanMotion=True` /
面部朝 +Z / 原生身高 0.9819。作者自述"面数很低、短发"**经实测不成立**（比付费对照款 26.7k 面还高）。

**落地清单**：

| 项 | 改动 |
|---|---|
| `Player.prefab` | `Visual` 子树整体替换（KayKit 9 个节点 → Feng 单网格 + CC 骨架） |
| `Animator.avatar` | `Rogue_HoodedAvatar` → **`FengAvatar`** |
| `Visual.localScale` | 1 → **2.213**（= 目标身高 2.1730 ÷ Feng 原生 0.9819，对齐旧主角以冻结相机取景） |
| `Visual.localPosition.y` | 0.088 → **0**（Feng 原点就在脚底，与 KayKit 不同） |
| `FootIK.stateOffsets` | **9 段整表重测**（Idle −0.0003 / Walk +0.0569 / Run −0.2294 / Dash −0.0041 / Atk1 +0.0446 / Atk1Rec −0.0030 / Atk2 +0.0494 / Atk2Rec +0.0022 / Atk3 +0.0129） |
| `SwordVfx` | `bladeLength / bladeLocalOffset.y / trailStartWidth` 同除 2.213（刀身挂在右手骨下会继承缩放） |
| 代码 | **零改动** —— 全工程无硬编码骨骼路径，`SwordVfx` 走 `GetBoneTransform(RightHand)` |

**顺手挖出并修掉的两个真缺陷（都在 `FootIK.cs`，都是"换模型才暴露"的隐性问题）**：

1. **竖直偏移走错了空间**：`stateOffsets` 是世界米，却写进 `anim.bodyPosition`（Animator 局部空间）。
   模型整体缩放 2.213 时世界效果被放大 **4.90 倍 = 2.213²**（实测写 0.0257 抬了 0.1260），
   `BodyLift` 反馈增益同样 ×4.9 → 必然过冲。**改法**：输出通道改为**模型容器的 `localPosition.y`**
   （父节点无缩放 → 局部 Y 就是世界米，1:1），与模型缩放彻底解耦。
   *KayKit 时代缩放为 1，两个空间数值恰好相等，所以这个错一直藏着。*
2. **静态偏移与帧内抬升重复补偿**：`BodyLift` 的 `need` 按原始姿态算，没扣掉已施加的 `BodyBase`，
   同一个穿地量被补两遍。KayKit 时代 9 段偏移全负、原始最低点恒为正 → `need` 恒 ≤ 0 → 代码路径没被走到；
   Feng 有负的原始最低点，立刻显形。**改法**：`need = (地面 + clearance) − 最低点 − BodyBase`。

**方法论修正三处**：
- `FootIK.stateOffsets` 绑的是「**片段 × 骨架**」而不只是片段 —— 脚位取决于**腿长比例**，
  换骨架必须整表重测（上一节曾判断"片段不变就不用重标"，**该判断是错的，已纠正**）。
- `SkinnedMeshRenderer.bounds` **不可靠、会严重虚高**（把 3 头身 Q 版量成 2.35 m 高）；
  量真实身高/网格最低点必须 `BakeMesh()` 取顶点。
- 编辑期 `Object.Destroy` **不生效**（会报错并保留对象），临时相机/贴图要用 `DestroyImmediate`。

**验收（全绿，未通过 0）**：S1 **31/0**（M1 保持达成）、S2 **51/0** + 姿态体检 **4/0**（M2 保持达成）、
音频 **6/0**；9 状态贴地后最低点 **0.003~0.005 m**；Console **error 0 / warning 0**。

**交付物**：移动段 + 战斗段录屏（960×540 / 20 fps / **0 丢帧**）与三视图/动作剧照，
均在 `Tools/screenshots/feng_ingame/`。

**未决（不阻塞）**：占位刀身仍是 `SwordVfx` 程序化生成的两片正交面片，正面看会露"平板"本质
（`play_atk2.png`）—— 中国商店有 ¥0 的 F3「古代宝剑」可替，正式武器与刀光水墨化排在 Sprint 4/5；
模型只有漫反射贴图、无 normal/mask；身高 2.17 m 偏高（对齐旧主角的代价，改则需连带复核相机取景）。

### 7.5 必须知道的约束

1. **Unity 必须处于打开状态**，且桥未被手动停止；脚本不会替你启动 Unity
2 . **Play/Pause 模式下的写命令会被 WriteGuard 拒绝**，返回 `Command blocked by write guard` —— 这是设计行为，先 `stop` 再写
3. **协议**：连上后先读一行 banner 丢弃 → `8字节大端长度头 + UTF-8 JSON` 收发 → 单帧上限 64 MiB
4. **多开 Unity 时** Editor.log 只有一份，可能发现到别的项目端口 → 用 `UNITY_BRIDGE_PORT` 钉死
