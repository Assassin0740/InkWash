# 敌人「实渲 0 像素」诊断记录（MoShan / MoGuai）—— ★ 已定位

> **根因（已确认）**：这两个 prefab 的 `SkinnedMeshRenderer` 里，**骨骼引用数组 `m_Bones` 全部丢失**
> （元素全为 null、`rootBone` 也为 null）⇒ 蒙皮结果退化、三角形不被光栅化 ⇒ **一个像素都不画**。
>
> **网格、材质、shader、bindposes、取景、可见性、剔除设置全部无罪**（逐项实测排除，见第二节）。
> 同一份网格 + 同一个材质，**只把渲染器换成普通 `MeshRenderer` 就完整显示**。
>
> 起点：`Z_Enemy_MoShan`（14/14 网格齐全）与 `Z_Enemy_MoGuai`（10/10）实渲 0 像素，
> 而 `Tools/cs/chk_enemy_vis.cs` 判它们 ✅（它只查 `sharedMesh != null`）。

---

## 一、根因证据链

### 1. 普查：骨骼引用与「能否渲染」完全对应

`Tools/cs/dg_ab_shot.cs` 遍历 `Assets/_Project/Prefabs/` 下所有敌人/龙 prefab：

| prefab | SMR | 有骨骼的 SMR | 骨骼元素总数 | 非 null | 实渲 |
|---|---|---|---|---|---|
| `Enemy_MoOu` | 8 | 8/8 | 184 | **184** | ✅ |
| `Enemy_MoTu` | 9 | 9/9 | 207 | **207** | ✅ |
| `Enemy_MoYan` | 8 | 8/8 | 184 | **184** | ✅ |
| `Z_Dragon` | 2 | 2/2 | 546 | **546** | ✅ |
| `Z_Enemy_MoLong` | 2 | 2/2 | 546 | **546** | ✅ |
| **`Z_Enemy_MoShan`** | 14 | **0/14** | 364 | **0** | ❌ |
| **`Z_Enemy_MoGuai`** | 10 | **0/10** | 970 | **0** | ❌ |
| `Z_Enemy_MoGu` | 3 | 0/3 | 240 | 0 | ✅ ⚠️ 唯一例外 |

**规律：非 null 骨骼数 > 0 ⇒ 渲染正常；= 0 ⇒ 不渲染。**
`Z_Enemy_MoGu` 是唯一反例（全 null 却仍渲染），第五节单列。

### 2. 三档对照实验（`Tools/cs/dg_smr_rebuild.cs`）

在 MoShan 实例旁新建三个测试对象，轮流单独拍摄：

| 测试 | 构造 | 非背景 |
|---|---|---|
| **T1** | 全新 SMR + MoShan 的 mesh + 材质，**不给骨骼** | **0.00%** |
| **T2** | 全新 SMR + MoGu 的 mesh + 材质，**不给骨骼**（对照） | **0.00%** |
| **T3** | 全新 SMR + **同一份** MoShan mesh + **26 个有效骨骼引用**（都指向自身） | **1.37%** ✅ |

- **T2=0** ⇒「新建 SMR 不给骨骼就画不出来」是 Unity 的正常行为，实验有效；
- **T3 出现模型** ⇒ **只补上有效骨骼引用，同一份网格立刻能画** ⇒ 根因就是骨骼引用。

### 3. 同取景 A/B（`Tools/cs/dg_ab_shot.cs`，给用户看的证据图）

同一个实例、同一台相机、**同一视野 9.43 m**，唯一变量是渲染路径：

| | 渲染路径 | 非背景 | 量化色数 |
|---|---|---|---|
| A | 原样 `SkinnedMeshRenderer` | **0.00%** | 2（全是蓝底抖动值） |
| B | 同一网格 + 同一材质挂 `MeshRenderer` | **1.56%** | 37（完整山怪 + 黑墨轮廓） |

## 二、排除清单（都已实测，别再重复）

| 假设 | 证伪方式 | 结果 |
|---|---|---|
| 取景太紧 / 太远 | 包围盒 ×1.5（9.5 m）、固定 6 m、正交 5→5000 m 扫描 | 全 0，非取景 |
| 几何跑到别的尺度 | 同上（跨 1000 倍读数不变） | 排除 |
| `localBounds` 撒谎 | 改用 `mesh.bounds` 世界化取景（B 档） | 仍 0，排除 |
| 视锥剔除 | `updateWhenOffscreen=true` + `localBounds` 设超大，三档对照 | 三档全 0，且**三档图字节数完全相同** |
| 材质丢了 | `chk_mat_state.cs`：材质槽 null 数 = 0（14/10/3/2） | 材质都在 |
| 材质属性异常 | 全量 dump shader 属性（`_BaseMap`/`_BaseColor`/renderQueue/…） | 三个材质几乎一致，无 null、无 alpha=0、非 Transparent |
| 材质本身 | **交叉互换**：MoShan 换成 MoGu 材质副本后重拍 | 仍 0.00%，材质无罪 |
| 贴图 | `_BaseMap` 均 2048² DXT1 有内容 | 正常 |
| 网格缺面 | `subMeshCount` / `GetIndexCount` | MoShan 合计 51921、MoGuai 64734，**索引齐全** |
| 网格数据本身 | **把同一 mesh 挂普通 `MeshRenderer`** | **完整山怪显示出来**，网格无罪 |
| `bindposes` 把顶点搬走 | 复制 mesh、`bindposes` 全设单位矩阵后重拍 | 仍 0.00%，排除 |
| blendShape 权重异常 | `m_BlendShapeWeights` 全量 dump + 清空实验 | 三家都是 size=0，排除 |
| SMR 其他序列化字段 | 完整展开（`NextVisible(true)`）后 diff | 除 `m_Mesh`/`m_Materials`/`m_AABB` 外**零差异** |
| `quality` / `forceMatrixRecalculation` | 直接读 | 三家同为 `Auto` / `False` |

> **★ 方法论教训**：第一轮 `SerializedObject` dump 用了 `NextVisible(enter: false)`，
> **数组子元素根本没被展开** —— `m_Bones` / `m_Materials` / `m_BlendShapeWeights` 全是盲区，
> 所以当时"字段零差异"的结论是**假的**。**dump 结构化对象必须 `Next(true)` 展开数组。**

## 三、两个度量坑（本轮的副产物，比结论更通用）

### 坑 1：**8-bit RenderTexture 有 dithering** —— 哨兵色要选「抖动 < 阈值」的

| 哨兵色 | 抖动后的实际取值 | 最大偏差 | 阈值 24 下 |
|---|---|---|---|
| 绿 `(0,255,0)` | `(0,240,0)` … `(44,240,44)` | **62** | ❌ 恒定 **25.63% 假「非背景」** |
| 蓝 `(0,0,255)` | `(0,0,234)` / `(0,0,240)` | 21 | ✅ 干净 |
| 红 `(255,0,0)` | `(240,0,0)` / `(236,0,0)` | 19 | ✅ 干净 |

**识别指纹：换取景尺度、换模型，读数一模一样 ⇒ 那是噪声。**

### 坑 2：**哨兵色绝不能用洋红 `(255,0,255)`**

**那正是 Unity「材质丢失」时渲染的颜色。** 用它当画布 ⇒ 看图的任何人（包括我自己）
都无法区分「我铺的底」与「真的缺材质」。实测代价：用户看到一片洋红直接问「为什么会材质丢失」，
我自己也据此误判过一轮。**哨兵色一律用纯蓝；需要第二底色时用纯红。**

> 连带纪律：**给临时物选色前，先问「这个颜色在 Unity 里是不是有既定含义」。**

### 坑 3：**「零像素 / 零差异」这类结论天然需要对照物**

单张全空图是零信息量 —— 用户看不到「这儿本该有东西」。
做法：**并排放一个「正常的」**（同底色、同口径），顶部叠状态带与读数，底部一句话说清哪块是模型。
参考 `Tools/make_compare_ab.py`（Pillow 拼图）。
附带小坑：**微软雅黑没有 ✅/❌ 字形**（渲成空心方块），状态标记要用 `ImageDraw.rectangle` 画色块。

### 附带硬事实

1. **`mesh.vertices` 在本工程返回空数组**（`isReadable=false`；`vertexCount`/`bindposes` 仍可读）
   ⇒「读顶点真值」这条手段不可用。`mesh.triangles.Length` 也因此为 0（但渲染不受影响）。
2. **`renderer.bounds` = `localBounds` × `lossyScale`**（推的，非蒙皮真值）；
   且 `localBounds` 与 `mesh.bounds` 不一致（被显式设置过）。
3. **「`bones` 长度对、元素全 null」这种状态，`sharedMesh != null` 类判据完全查不出。**

## 四、修复方案（待拍板）

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A（推荐）** | 把这两个 prefab 的 `SkinnedMeshRenderer` 换成 `MeshFilter` + `MeshRenderer` | 小；A/B 实验已证明可行 | 它们本来就是**静态敌人**（骨骼引用已丢、没有骨骼动画） |
| B | 修回骨骼引用（重导 FBX / 重建 prefab，像龙那样） | 大 | 将来要给它们加骨骼动画时 |
| C | 运行时兜底：给 SMR 填有效骨骼引用 | 中；且会改变几何（T3 已证明可行但形状可疑） | 不想动资产时的临时手段 |

**⚠️ 方案 A 的前置检查**：确认没有代码只按 `SkinnedMeshRenderer` 查找这两个敌人
（例如墨色换材质 `InkMaterialSwap`、验收脚本 `chk_enemy_vis.cs`），否则换了渲染器会静默漏掉。

**⚠️ 顺带**：`Z_Enemy_MoGu` 也是 0/3 骨骼（只是暂时还能画），**建议一并处理**，
否则将来换个网格 / 加个动画就会突然「消失」。

## 五、待查（唯一的未解项）
