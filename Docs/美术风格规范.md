# 美术风格规范（Art Style Guide）

> 项目：**《墨刃 · InkWash》** —— 基于 Unity 的 3D 水墨动作游戏
> 版本：v1.0　｜　制定日期：2026-09-14　｜　状态：**风格已定，主角素材待拍板**
> 关联文档：`Docs/素材来源与授权清单.md`、`Docs/毕设敏捷实施计划.md`

---

## 0. 一句话定位

> **写实比例的中国古风武者，在水墨写意的世界里挥刀。**
> 造型是"东方、古风、飒"，质感是"宣纸、墨迹、飞白"——造型不做卡通化，风格化全部交给渲染承担。

---

## 1. 为什么现在必须定这份规范

用户反馈（原话）：

> 「这个动作跟披风有点穿模，而且这个人物有点太卡通了吧，我们好像还没有确定美术风格，我希望是传统人物，就是东方一点的，比较飒的人物，中国传统古风」

暴露了两个层面的问题，混在一起会互相掩盖：

| 层面 | 具体问题 | 归属 |
|---|---|---|
| **美术方向** | 主角是 KayKit 的 **3 头身 Q 版大头娃娃**，西式游侠装束（绿色兜帽 + 披肩 + 皮护腕），高饱和卡通配色 | 本文档第 2–6 节 |
| **技术实现** | 披风是**蒙皮到脊柱的刚性网格**，手臂摆动时直接穿进去 | 本文档第 8 节 |

**关键判断**：这两件事必须分开处理。换模型不能自动解决穿模（新角色的长袍/披风照样会穿），
而只修穿模也解决不了"太卡通"。所以本文档同时给出**美术判据**与**布料技术方案**。

## 2. 风格定位（Definition）

### 2.1 三条主轴

| 轴 | 取值 | 反面（禁止） |
|---|---|---|
| **文化取向** | 中国传统古风（汉／唐／宋气象） | 西式奇幻、日式和风、仙侠网游堆料风 |
| **写实度** | **写实比例**（7～7.5 头身），半写实材质 | Q 版、大头娃娃、三头身、乐高块面 |
| **气质** | **飒** —— 利落、冷峻、有锋刃感 | 萌、圆润、憨态、玩具感 |

### 2.2 参考坐标（仅取"感觉"，不抄具体作品）

- **形体**：东方武侠影视里的武者体态——肩背挺拔、腰线收束、动作开合大
- **色彩**：国画颜料谱系（墨、朱砂、石青、赭石），忌荧光色
- **质感**：宣纸的粗糙颗粒 + 墨的浓淡层次，边缘有飞白
- **运动**：刀意先于刀身，动作要有"留白"（这一点由 Sprint 4/5 的水墨特效承载）

> ⚠️ **风格化的重心在渲染，不在模型**。用户明确「我主要做的是风格化渲染」——
> 因此选角的硬指标是**比例正常 + 服饰结构正确 + 绑定可用**，
> 而不是"贴图有多精细"（高分辨率 PBR 贴图会被水墨 Shader 覆盖，属于浪费项）。

## 3. 比例与形体规范

| 项 | 规范值 | 说明 |
|---|---|---|
| 头身比（主角） | **7.0 ～ 7.5 头身** | 低于 6 头身即判"卡通化"，不予采用 |
| 总身高（世界单位） | 1.70 m ± 0.05 | 与现有相机（距离 4.3 m）、碰撞胶囊一致 |
| 角色占屏高 | **30% ～ 60%**（现状 43%） | 已有验收项，直接沿用 |
| 剪影要求 | 侧面能一眼分辨"交领 + 束腰 + 下摆"三段结构 | 剪影不清 → 水墨描边糊成一团 |
| 裙摆／披风长度 | 站姿不触地（离地 ≥ 0.05 m） | 贴合现有 FootIK 的贴地窗口 `[-0.02, +0.05]` |

> **现状对照**：KayKit `Rogue_Hooded` 是 3 头身，头部约占全身 1/3 —— 这是用户观感上
> "太卡通"的**唯一主因**，与渲染无关。换掉它必须换成正常头身比。

## 4. 角色设定规范

### 4.1 主角形象基准

**首选形象：古风侠客（汉服体系）**

| 部件 | 规范 | 禁止 |
|---|---|---|
| 上衣 | **交领右衽**，衣襟交叠方向必须正确（右衽是华夏服饰的核心识别特征） | 左衽（丧服／异族误用）、圆领套头 |
| 腰部 | 束腰（腰带／革带），腰线明显收束 | 松垮无腰身 |
| 下装 | 长裤 + 外罩开衩下摆（便于腿部动作不被布料锁死） | 一整片裹裙（必然穿模，见第 8 节） |
| 外披（可选） | 披风／半臂／云肩，**必须带独立布料骨骼** | 刚性披风 |
| 发型 | 发髻／束发 + 发带或发簪 | 散发遮脸（挡水墨描边）、西式短发 |
| 武器 | **单刃直刀（唐刀制式）** 或长剑，佩于腰侧或持于手 | 西式阔剑、日式太刀鞘制 |

### 4.2 形态变体（NPC／敌人，供 M3 之后使用）

同一套规范下可放宽到：道士、僧人、游侠、弓手、官差、农人、老幼。
**共同约束不变**：写实比例、华夏服饰结构、正常色彩。

### 4.3 明确禁止项（含现状违规）

| 禁止 | 现状是否违规 |
|---|---|
| 西式兜帽 / 兜帽斗篷 | ❌ **违规**（KayKit Rogue 的绿色兜帽） |
| 高饱和卡通配色（荧光绿、艳橙） | ❌ **违规**（现状配色） |
| 三头身 / 大头娃娃比例 | ❌ **违规**（现状主体） |
| 裸露的现代／科幻元素 | ✅ 未违规 |
| 日式甲胄与华夏甲胄混搭 | ✅ 未违规（当前无甲胄） |

## 5. 色彩规范

以国画颜料谱系为基准，**角色身上不超过 3 个主色 + 1 个点睛色**。

| 角色 | 色值（参考） | 用途 |
|---|---|---|
| **墨** | `#1C1C1A` ～ `#3A3A36` | 主服色、发色、描边基准 |
| **宣**（米白） | `#E8E2D4` | 内衬、袷衣、下摆 |
| **朱砂** | `#B33A2B` | **点睛色**：腰带／披风里子／发带（全身占比 ≤ 10%，多了就俗） |
| **石青** | `#4A6B7C` | 次要点缀（护腕、滚边） |
| **赭石** | `#8A5A3B` | 皮革／木质配件 |
| **金属** | `#9AA0A6`（低粗糙度） | 兵器、甲片 |

**约束**：
1. 饱和度上限 —— **HSV 的 S 值 ≤ 60%**（现状 KayKit 绿约 S=70~80%，属违规）。
2. 主角不得使用大面积纯色；单一色块面积 ≤ 全身 40%。
3. 点晴色（朱砂）是视觉锚点，用于让玩家在墨色画面里一眼找到自己——**这是玩法需求，不只是审美**。

## 6. 材质与渲染规范

角色材质必须能被现有水墨管线接管。规范如下：

| 项 | 要求 |
|---|---|
| 承载 Shader | 导入后由 `InkWash/*` 系列 Shader 覆盖；源素材保留 URP/Lit 或 Standard 材质作备份 |
| 贴图分辨率 | ≥ 1024×1024；**推荐 2048 或 4K**（角色占屏 43%，近景对贴图敏感） |
| 贴图通道 | 至少含 BaseColor + Normal；Roughness／Metallic 可选（水墨渲染下权重低） |
| 描边 | 依赖法线外扩，因此**模型法线必须干净**（无翻转面、无硬边断裂） |
| UV | 无重叠（重叠会导致墨色错位） |
| 透明度 | 布料边缘尽量走 Alpha Clip 而非 Alpha Blend（避免排序问题） |

> **反过来说**：低模 + 1024 单张贴图的素材（如低模中国风包）在水墨渲染下**并非不可用**，
> 但角色占屏 43% 时棱角会明显外露。面数建议 **≥ 20k triangles**。

## 7. 绑定与动画约束（硬性）

这是本项目最关键的选型门槛 —— 直接决定能不能沿用已经验收通过的移动与连击系统。

| 约束 | 要求 | 为什么 |
|---|---|---|
| **骨架类型** | **必须 Humanoid** | 现有 `Player.controller` 的 9 个状态、`FootIK`、步伐同步（`walkRefSpeed` / `runRefSpeed`）全部建立在 Humanoid 上。Generic 骨架会直接废掉 FootIK |
| **自带动画** | 非必需 | Humanoid 可重定向现有片段。但自带动画可作为动作参考 |
| **布料骨骼** | **强烈建议具备** | 见第 8 节。没有布料骨的长袍角色，穿模只能靠隐藏或重绑解决 |
| **附加骨骼** | 可接受 | 额外的布料／头发／配饰骨骼不影响 Humanoid 映射 |
| **T-Pose / A-Pose** | 记录基准姿态 | 重定向后需校对肩部；现有 `Tools/cs/s3_probe_refspeed_ki.cs` 套路可复用 |

## 8. 披风 / 布料穿模 —— 问题机理与解决方案

### 8.1 机理（为什么现在的披风必然穿）

KayKit `Rogue_Hooded` 的兜帽与披肩是**一整块刚性网格**，蒙皮权重挂在**脊柱与锁骨**上：

```
肩披网格  ──蒙皮权重──>  Spine / Clavicle
手臂摆动  ──>  UpperArm 旋转  ──>  手臂扫过披肩的静态体积  ──>  穿模
```

因为披风**完全不感知手臂**，只要摆臂幅度超过披肩包围盒就必然穿插。
这不是动画问题，**是绑定结构问题**——所以调动画参数永远修不好。

### 8.2 三个方案（按推荐度排序）

| 方案 | 做法 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| **A. 布料骨骼 + 轻量弹簧求解** ⭐推荐 | 素材自带布料骨链时，写一个 `InkWash/SpringBoneSolver`：逐节做惯性 + 阻尼 + 角度限制，并加一条"手臂排斥"约束 | 可控、可调、性能好、跨角色复用 | 需自研组件（约 150 行） | **新角色自带布料骨**（首选候选即具备） |
| **B. Unity Cloth 组件（PhysX）** | 给披风网格挂 `Cloth`，绑定胶囊碰撞体 | 开箱即用 | 需网格够密；布线与性能开销大；对角色动画（非根运动）支持一般 | 披风面数高的写实素材 |
| **C. 战斗期间隐藏披风**（兜底） | 进入攻击/冲刺状态时把披风 Renderer 淡出 | 一行逻辑，零风险 | 视觉上"披风凭空消失" | 工期紧或 A/B 都不满足时 |

**决策**：优先选**自带布料骨骼**的素材（直接可用方案 A），
若是写实高面数披风则用方案 B，方案 C 仅作兜底并需在论文中说明为降级处理。

### 8.3 验收判据（可测量，写进 PlaytestHarness）

| 指标 | 阈值 | 度量方式 |
|---|---|---|
| 穿模帧占比 | **< 5%** | 逐帧取"披风网格顶点"与"上臂/前臂骨骼胶囊"的最短距离，< 0 判穿模 |
| 最坏穿透深度 | **< 0.02 m** | 同上，取最小值 |
| 布料骨骼跟随延迟 | 甩动后 ≤ 0.25 s 回稳 | 记录骨骼角速度衰减 |
| 帧率影响 | 1080p 仍 **≥ 55 fps** | 沿用现有 DoD |

> ⚠️ 该度量与现有姿态体检（`S2_pose_latest.txt`）同属"几何体检"，需并入
> `Tools/cs/` 下的自动化流程，报告落 `Tools/reports/`。

**三、顺手挖出并修掉的真缺陷**（两个在 `FootIK.cs`、一个在 `SwordVfx.cs`，**都是换模型才暴露**的）

1. **竖直偏移的单位错配 —— 走错了空间**
   `stateOffsets` 是**世界米**（标定脚本量的就是世界量），却写进了 `anim.bodyPosition`——那是
   **Animator 局部空间**。模型带整体缩放（`Visual.localScale = 2.213`）时，世界效果被放大
   **4.90 倍 = 2.213²**（实测：写 0.0257 抬了 0.1260）。
   同一通道上的 `BodyLift` 反馈增益也被放大 4.9 倍 → 必然过冲。现象：Walk 名义抬 0.057 结果飘
   +0.134；Run 名义压 0.229 结果沉 −0.274。
   **修法**：输出通道改为**模型容器的 `localPosition.y`**（`bodyOffsetTarget`，自动解析为 Animator 的
   直系子节点 = `Visual`）。它的父节点无缩放 → 局部 Y **就是世界米，1:1**，从此与模型缩放彻底解耦。
   *KayKit 时代缩放为 1，两个空间数值恰好相等，所以这个错一直没暴露。*

2. **静态偏移与帧内抬升重复补偿 —— `need` 没扣掉 `BodyBase`**
   `BodyLift` 的 `need` 原本按**原始姿态**算；但静态偏移 `BodyBase` 已经抬过一次了，于是同一个
   穿地量被补偿两遍。KayKit 时代 9 段偏移全为负、原始最低点恒为正 → `need` 恒 ≤ 0 →
   `BodyLift` 恒为 0 → 这条路根本没被走到。Feng 有负的原始最低点，立刻显形。
   **修法**：`need = (地面 + clearance) − 最低点 − BodyBase`，`BodyLift` 只补**静态偏移之后的残差**。

### 二、挂点：**"剑身对齐手指方向"是错的**（本轮最大的认知修正）

上一版把剑身对齐到**手骨 +Y（手指伸出的方向）**，理由是"骨骼沿自身 +Y 延伸"。
实测数据说明这个理由**引错了类比**：

| 量 | 值（Idle 期，世界） | 说明 |
|---|---|---|
| `fingerDir`（手骨 +Y） | (0.430, −0.869, 0.247) | 手指伸出的方向，几乎朝下 |
| `spreadDir`（食指根 → 小指根） | (0.457, −0.031, −0.889) | **拳头的铰链轴 = 拳头隧道轴** |
| `palmNormal` = `fingerDir × spreadDir` | (0.779, 0.495, 0.384) | 掌面法向 |

**握剑时剑柄穿过的是"拳头隧道"，它的轴 = `spreadDir`，不是 `fingerDir`。**
用 `fingerDir` 会把剑摆成"从指缝里长出来"；用 `spreadDir` 才是"握在手里"。

方向的正负号由**掌根 → 虎口**的对角线定：剑刃从**拇指与食指之间**穿出。
实测该对角线 `heel→web` 与 `−spreadDir` 夹角仅 **27.4°**（与 `+spreadDir` 是 152.6°），
所以取 **剑身方向 = −spreadDir**。副产品：这个方向与角色 `forward` 夹角只有 **27.3°**
⇒ 待机时剑自然指向**身前**，不用额外调姿势。

**挂点公式**（`P` = Align 局部位移，`R` = Align 局部旋转，`s` = Align 缩放，`v` = 模型空间点）：

```
p_root = P + R·(s·v)                        # 模型点 → 根（= 手骨）空间
要求：① R·(0,−1,0) = d（d = 根空间里的剑身方向；模型尖端在模型 −Y）
      ② 模型上的握持点 v0 = (0, Gm, 0) 落到拳心 f
⇒  P = f + s·Gm·d            （Gm = 剑柄中点 0.4050，f = 拳心在根空间的坐标）
```

> **⚠ 上一版就是漏了 ②**：写成 `P = s·Gm·d`，等于假设"根原点（= 腕关节）就是握持点"。
> 实测腕→拳心 **0.141 m**，于是剑柄中点被摆在了**腕**上，拳头正好卡在**护手**上
> （护手在腕前 0.1475 m，与拳心 0.141 m 吻合 —— 数据早就摆在那儿，是我没去核对）。

**最终序列化值**（全部在**手骨局部空间**，与姿势无关）：

| 字段 | 值 |
|---|---|
| `Align.localPosition` | `(−0.005492450, 0.062623090, 0.204533600)` |
| `Align.localRotation` | `(−0.499112900, −0.500882100, 0.499116400, 0.500885400)` |
| `Align.localScale` | `(0.49, 0.49, 0.49)`（不变） |
| `SwordVfx.bladeLocalOffset` | `(−0.005491800, 0.062286160, 0.299759600)` |
| 拳心 `f` | `(−0.005494, 0.063325, 0.006085)`（根空间单位，×2.213 = 0.141 m） |

`roll` 的选法：让**剑的刃面法向（模型 Z）= 掌法向**（`flatN` 方案）。
理由：挥砍时刃线落在斩击平面内、刃面朝掌面外 —— 这是锤握的自然姿态。
（两候选 `flatN` / `flatN_neg` 都渲染过：`sword_solve/solve_flatN*.png`。）

### 三、握拳补丁 `WeaponHandPose`

**问题**：本项目的动画包**全是徒手动作**（Quaternius UAL1/UAL2 + Kevin Iglesias 只有
`Idle01` / `Walk01_Forward` / `Run01_Forward` 三个片段），手一直是张开的"放松手"。
挂剑后看着像把剑**搁**在手心 —— 这是**换真模型才暴露**的问题，占位剑阶段看不出来。

**做法**：`LateUpdate`（`DefaultExecutionOrder(20000)`）里把持剑手的指骨绕 `spreadDir` 卷起来。

三条硬约束（都踩过）：
1. **必须在 `LateUpdate`**：`Update` 里改会被 Animator 当帧写回，白改。
2. **局部轴要"卷之前"一次性取好，再统一卷**：等价于真实指关节的铰链。
   边卷边取轴 → 各节各绕一个世界轴 → 指头散开。实测卷指后近节转 **68.7°**（请求 70°），
   中指指尖到腕从 0.141 m 收到 **0.111 m**。
3. **`CC_Base` 骨架把脚趾也叫 `Index/Mid/Ring/PinkyToe1`** —— 按名字抓指骨必须
   `if (name.Contains("Toe")) continue;`。本轮就是漏了这句，"拳心"被 4 根脚趾骨
   拖到 y = 0.93（离腕 **0.69 m**），差点据此把挂点算到膝盖上。

**自检**：`Tools/cs/w_shot_play2.cs` 会实测锚点
**到剑轴垂距 = 0.0000 m、在剑身 66.2% 处（= 刀刃段的 55%）**，判据 `[通过] 锚点落在剑身上`。

### 五、材质的一处反直觉实测

场景**没有任何反射探针**（`defaultReflectionResolution = 128`，走默认天空盒）。

最终取 `_Metallic 0.30 / _Smoothness 0.38`。
另外 `texture_pbr_20250901_roughness.png` 是**数据贴图**，导入必须
`sRGBTexture = false`（已修，是个潜在陷阱）。

### 六、本轮踩坑清单（下次接武器直接照做）

1. **别用节点 `TransformDirection(up)` 判剑身方向** —— 本模型尖端在网格空间 −Y，
   节点轴天然反向，会误报"夹角 180°，朝向错了"（假警报，害我多查一轮）。

2. **节点轴/注释都会撒谎**，先量再说（这条已在 S2.1 总结过，本轮又验证一次）。
3. **换挂点方向 = 换一套数值**：`Align` 的 pos + rot、`bladeLocalOffset`
   三处必须一起改，只改一处等于没改。
4. **Play 态写资产会被 WriteGuard 拦**：先 `stop` 再改，再 `play` 验。
5. **新加的 `.cs` 不在 `Assembly-CSharp`**：`ImportAsset(ForceUpdate)` →

## 9.5 待机动作「持剑而立」—— 2026-09-15 修正

### 一、现象与根因

用户反馈：待机姿态「奇葩」—— 手臂自然下垂，剑**水平横戳**向体侧。拆开看是**两个独立问题**叠加。

**（1）控制器没跟着角色换（表层）**

`Player.controller` 最后一次改动是 `5278fd0`（换 KayKit 那一步）。之后角色换成 `Char_Feng`，
控制器却没动 —— 实测 **9 个状态全是 KayKit 的 Q 版片段**（`Idle_A` / `Walking_A` / `Running_A` /
`Melee_1H_*`）。`Idle_A` 是给三头身小人做的「立正」待机，套在写实古风角色上自然别扭。

**（2）徒手动画 + 刚性握持 = 剑必然横着（本质，这条更重要）**

剑身方向**固死**在手骨上（手骨局部 `+Z`，物理上正确 —— 拳头握剑的几何关系是常量）。
而「手臂自然下垂」时**前臂是竖直的**，剑身与前臂近似**垂直** ⇒ 剑只能**水平**伸出。

绕前臂轴做腕部旋前 / 旋后**救不了**。实测扫描（扭转 0° / 45° / 90° / 135°）：

| 扭转角 | 0° | 45° | 90° | 135° |
|---|---|---|---|---|
| 剑与「竖直向下」夹角 | 109.9° | 99.9° | 83.0° | 68.3° |

即剑只是在**绕前臂画圈**，收敛在水平附近，**永远指不到正下方**。

> **推论（选持剑待机片段的判据）**：任何「手臂垂下」的待机片段都**不适合持剑角色**。
> 持剑待机必须是**屈肘**姿态 —— 肘一屈、前臂转成水平，与它垂直的剑身就自然立起来了。

### 二、处置

`Idle` 状态片段由 `KayKit/Rig_Medium_General.fbx::Idle_A` 换成
**`Assets/Char_Feng/Animation/Idle.anim`**（同作者、同骨架、**零下载**）。
它是**真正的持剑待机**：左手收袖、右手屈肘竖剑于肩前。
实测剑与「竖直向下」夹角 **144.9°**（即立起来、指向斜前上方），换之前是 **91.6°**（水平）。

按规范，换片段**必须**重测 `FootIK.stateOffsets`（它绑「片段 × 骨架」）。
实测 Feng 的 Idle 让网格最低点沉到地面下 **0.0277 m** ⇒ `Idle` 偏移由 `-0.0003` 改为 **`+0.0307`**
（其余 8 段保持不变）。

**验收**：S1 31/0 · S2 51/0 · 姿态 4/0 · 音频 6/0，Console 无红字。
刀光锚点复核：换算到武器网格局部空间后为 `(0.0000, -0.1943, 0.0000)`，
**离剑轴 0.0000 m**（Idle / Walk / Atk1 / Atk3 四态一致）。

### 三、新增可量化判据

| 指标 | 怎么量 | 判据 |
|---|---|---|
| 剑是否立起来 | `weapon.TransformDirection(Vector3.down)` 与 `Vector3.down` 的夹角 | 越接近 0°（朝下）或 180°（朝上）越好；**90° = 水平横戳，不合格** |
| 刀光锚点是否贴合 | 锚点换算到**武器网格局部空间**后的 `sqrt(x² + z²)` | 必须 = 0.0000 m |
| 待机脚部贴地 | 网格最低点（`BakeMesh` 逐顶点，按归一化时间扫） | 落在 `[-0.02, +0.05]` m |

> ⚠ **「剑身 X%」有两个分母，别混**：从**剑首端**算是 **66.2%**，从**护手到剑尖**（真正的「剑身」）算是 **53.4%**。
> 本项目的刀光锚点是同一个点，两处都写过（§9.4 四 与验收表）。

### 四、遗留：控制器整体仍是 Q 版时代

`Walk` / `Run` / `Dash` / 三段攻击**仍是 KayKit 片段**（Feng 自带 10 段里只有 `Idle` / `Walk` / `Roll` /
`Death` 等，**没有 Run、没有挥剑**）。所以目前存在**风格断裂**：待机是写实古风，一动起来又切回 Q 版节奏。
建议按「移动优先」重排：`Walk` → `Feng/Walk`，`Run` → `KevinIglesias/Run01_Forward`，攻击段暂留待换。

## 9.6 平时站立 vs 战斗待机 —— 双姿态（2026-09-15）

### 一、需求

用户反馈：不只是拿剑的待机，**平时站着也应该是自然双手下垂**的动作。

### 二、根因：与 §9.5 是同一个

「垂手站立」与「手里握着剑」**在几何上冲突**：剑身方向固死在手骨上，手臂自然下垂时前臂竖直，
与它近似垂直的剑身只能水平横伸（实测与「竖直向下」夹角 88.4°）。

所以**换片段救不了** —— 把 Idle 换成垂手片段，剑照样横在身侧。
证据在同一张对比图里：`stand_cand/A_UAL1_IdleLoop_front.png` 与 `E_反例_垂手但剑在手_front.png`
**姿态完全相同、只差剑显不显示**，前者干净、后者剑横在身前。

> **结论：非战斗时必须把剑收起来，而不是只换动画。**

### 三、方案：战斗 / 非战斗 双姿态

新增 `Assets/_Project/Scripts/Player/CombatStance.cs`。

| | 非战斗（默认） | 战斗 |
|---|---|---|
| Idle 片段 | `UAL1/Rig\|Idle_Loop`（自然双手下垂） | `Char_Feng/Idle.anim`（持剑待机） |
| 武器挂点 | `BackSocket`（背部） | `CC_Base_R_Hand`（右手） |
| 握拳补丁 | 关闭 | 开启 |

- **进入战斗**：`SwingStarted`（攻击）或 `DashStarted`（冲刺）
- **退出战斗**：连续 `combatExitDelay`（默认 6 s）既没攻击也没冲刺，且已回到 `Locomotion`

**实现选择**：用 `AnimatorOverrideController` 只覆盖 **Idle 这一个片段**的映射，
**不动 `Player.controller` 资产**。理由是新增状态要牵动所有进出转移的条件（回归面太大），
而这里要变的只有「Idle 播哪段」。

### 四、背部挂点：沿用 socket 约定 + 轴向自动探明

`BackSocket` 建在 `CC_Base_Spine02` 下，局部位姿：

```
pos = (-0.041672, 0.196906, -0.055625)   euler = (62.475, 92.689, 180.269)   scale = 1
```

剑尖方向取 `down + 0.55·right`（右肩柄 → 左腰尖），刃厚法向取 `back`（宽面贴背）。
效果：剑柄露在**右肩上方**（右手可过肩拔剑），剑尖到左小腿，**正面完全看不到剑**。

三条踩过的坑：

1. **轴向必须实测，不能凭记忆。** `Align` 节点上**还留着 FBX 的原生旋转**
   （实测 `euler = (0, 270, 89.8)`，不是之前以为的 `(180, 0, 0)`），于是
   「武器根局部 +Y 指向剑尖」这个假设**是错的** —— 实测剑尖方向 = 根局部 **+Z**。
   正确做法：把「网格节点的 −Y（剑尖）/ +Z（刃厚）」用 `InverseTransformDirection`
   换算到武器根局部空间，再 `FromToRotation` 对齐（实测对齐残差 **0.05°**）。
2. **位置锚点必须说清是「根原点」还是「网格中心」**——两者相差 **0.47 m**。
   直接摆根原点，整把剑明显偏低：剑柄落到腰侧而不是肩上方，右手没法过肩拔剑。
3. **socket 原点 = 挂载点**（同 §9.4 的武器约定）。因此运行时搬运武器只要
   `SetParent(socket, false)` + 局部归零即可，组件**不需要存任何「挂点偏移 / 缩放」字段**。

### 五、验收

- **S1 31/0 · S2 51/0 · 姿态 4/0 · 音频 6/0**，Console error 0。
  姿态验收「最飘 Idle 0.005 m」—— 换成 UAL1 垂手后脚部贴地依然达标，`FootIK` 不用重标。

## 9.7 攻击时左手五指摊开 —— 左右手的铰链轴是**镜像**的（2026-09-15）

### 一、现象

用户拿战斗截图反馈：「为什么他的这个手还是会打开，太奇怪了，**在攻击的时候，待机动作没问题**」。

把截图放大（裁切 + 5 倍插值）后看清了两件事：持剑的**右手是握住的**（正常），
**左（空）手五指完全摊开**。

### 二、先量后判：定义「握拳度」

写 `Tools/cs/q_fist2.cs`，对 `Idle` / `Atk1` / `Atk2` / `Atk3` 逐状态打印四指的关节夹角与
「中指指尖到腕」距离，并定义**尺度无关**的握拳度：

> **握拳度 = 中指指尖到腕的距离 ÷ 食指根到小指根的距离**
> 五指摊开 ≈ 2.2 ～ 2.4；握成拳 ≈ 1.2 ～ 1.4。
> 分母选「指根展开宽度」是因为它在卷指过程中几乎不变（转轴就在指根上），
> 于是这个比值天然**不随模型缩放漂移**。

| 状态 | 右手（持剑） | 左手（空手） |
|---|---|---|
| Idle（Feng 持剑待机） | 1.55 | 1.50 |
| Atk1 / Atk2 / Atk3 | 1.34 | **2.33 ← 摊开** |

两个结论：

1. **右手一直是握着的**（补丁生效）—— 用户看到的确实是左手。
2. **「待机没问题」不是巧合**：Feng 自带的 `Idle` 本来就把左手做成半握（1.50），
   而 KayKit 的攻击片段把左手摊到 2.33。而 `WeaponHandPose` 的 `leftHand` 默认 **false**，
   `CombatStance` 只负责整开关（`handPose.enabled = combat`）—— **根本没人管左手**。

### 三、真因：`spreadDir` 是**镜像轴**

顺手把 `leftHand` 打开，数值**几乎不动**（近节 36.6° → 48.1°、指尖到腕 0.193 → 0.189 m），
而且「满力 70/85/55」与「六成力 48/58/38」给出**完全相同**的结果 —— 说明不是力度问题，
是**方向反了**。

写 `Tools/cs/q_fist3.cs` 关掉组件、自己按同样的公式对左右手各试三个候选轴：

| 试法 | 右手 中指指尖到腕 | 左手 中指指尖到腕 |
|---|---|---|
| 基线（不卷） | 0.128 m | 0.124 m |
| **+70° 绕 spreadDir** | **0.108 m ← 屈 ✓** | **0.214 m ← 伸 ✗** |
| −70° 绕 spreadDir | 0.125 m | **0.114 m ← 屈 ✓** |
| +70° 绕 palmN（掌法向） | 0.119 m | 0.174 m |

> **`spreadDir = 小指根 − 食指根` 在左右手上是镜像的，人手本身也是镜像的。**
> 沿同一个正角度旋转，一侧是「屈」、另一侧是「伸」（等于反向掰直）。
> 这就是「左手照抄右手的角度只会把手掰得更开」的原因。
>
> 顺带否掉了一个更直觉的猜测：**不是轴不正交**。自检 `|cos(骨向, spreadDir)|` 左右手都是
> 0.001 ～ 0.117，横竖都接近垂直 —— 轴是对的，**符号是错的**。

### 四、处置：符号必须**实测**，不能写死

在 `WeaponHandPose.Resolve()` 里给每只手做一次**当场试转**（`CalibrateSign`）：
沿 `+spreadDir` 把食指链三节各转 40°，**若中指指尖离腕更远就取反**。

- 实测 `RightCurlSign = +1`、`LeftCurlSign = −1`
- 写死「左手取负」也能过，但**换骨架 / 换手性就又错**；试一次的成本只有几行 `localRotation` 赋值。
  与 §9.4 / §9.6 同一套原则：**能用一次实测换掉的假设就别留着**（轴向、挂点、符号……）
- 给左手单独一组更松的角度（`leftFingerCurl = 58/70/45`）：空手握拳不必像握剑那么死
- 轴仍然「在卷之前一次性取好」（卷了父骨之后子骨的局部轴会变，见 §9.4）

**修复前后**

| | 修复前 | 修复后 |
|---|---|---|
| 左手握拳度（攻击中） | 2.33 | **1.29** |
| 左手 中指指尖到腕 | 0.193 m | **0.107 m** |
| `RightFistRatio` / `LeftFistRatio`（运行时探针） | 无 | 已暴露 |

### 五、新增验收项

`PlaytestHarness` 在战斗采样里记录**握拳度峰值**，S2 增一行（51 → 52 项）：

```
[通过] 攻击全程两手都握着（不是五指摊开）   握拳度峰值 右 1.547 / 左 1.356（五指摊开≈2.2，握成拳≈1.2）
```

阈值取 1.7 —— 距「握拳 1.4」与「摊开 2.2」两侧各留 ≈ 0.5 的余量。
**只在「补丁这一帧确实跑过」时采信**（`pose.enabled && CurledBoneCount > 0`）：
探针都是 `LateUpdate` 末尾写的，刚进战斗那一帧读到的是**上一帧的陈旧值**。

> ⚠ **探针的陈旧帧陷阱**：组件被 `disabled` 时 `LateUpdate` 不再跑，
> 但 `Armed` / `CurledBoneCount` / 握拳度**全都停在最后一次的值上**。
> 外部代码读这些探针必须**同时看 `enabled`**，否则会把「上一次战斗」的残留当成当前状态。
> （同类问题在 §9.6 的 `FootIK` 上也出现过。）

### 六、遗留

`Walk` / `Run` / 三段攻击**仍是 KayKit 的 Q 版片段**（Feng 自带 10 段里没有 Run、没有挥剑），
所以**风格断裂**依旧存在：待机是写实古风，一动起来切回 Q 版节奏。
攻击段的**握持**问题已由本补丁兜住，但动作本身仍是 Q 版。

## 9.8 三段攻击换成 UAL2 剑术库 —— 并炸出 FootIK 的「探地正反馈」（2026-09-15）

### 一、现象

**`HasGroundInfo = false`** —— 链条如下：

> `ProbeGround` 的射线起点 = `网格最低点 + probeUp(0.5)`。
> UAL2 的收招段把角色压到地下 **0.5~0.9 m**（它比 KayKit 的直立挥砍激进得多），
> 起点随之落到**地面之下**，而射线是**向下**发的 ⇒ 永远打不到地面
> ⇒ `HasGroundInfo = false` ⇒ `BodyLift` 归零不修 ⇒ **沉得更深，更探不到**。**正反馈**。

修法三条（前两条是通用缺陷，换任何"大幅下蹲"的片段都会撞上）：

1. **探测起点改用 `max(网格最低点, 角色根 Y) + probeUp`** —— 角色根由 `CharacterController`
   保持在地面附近，是可靠锚点；网格最低点会被动画压得很低，不能单独作锚。
2. **`maxLift` 0.8 → 1.3** —— 最深需要一次性抬 0.89 m，卡上限会永远差一截。
3. `stateOffsets` 的 `Atk1 / Atk1Rec / Atk2 / Atk2Rec / Atk3` 重标。
   **取「最浅穿地量」作基准**（而不是最深）：这样每帧 `need = 地面 − 最低点 − 基准 ≥ 0` 恒成立，
   帧内抬升全程有效；取最深值会让浅的帧 `need < 0` 而浮空（抬升只能向上、压不下去）。

### 四、`FootIK.stateOffsets` 重标：两种口径要对号入座

换 `Walk` / `Run` 片段必须重测（§9.1.2）。重标脚本 `Tools/cs/q_footik2.cs` 同时打印**最深 / 最浅**：

| 状态 | 无IK最深 | 无IK最浅 | 新值 | 口径 |
|---|---|---|---|---|
| `Walk` | −0.1053 | +0.0604 | **−0.0554** | 取**最浅**：脚全程该踩地 ⇒ BodyLift 逐帧把其余帧压回地面 |
| `Run` | −0.1685 | +0.3632 | **+0.1735** | 取**最深**：有腾空相 ⇒ 支撑相贴地、腾空相自然离地 |

判据（读 `FootIK.ApplyBodyOffset` + `s2_acc_pose`）：`need = (ground + clearance) − low.y − BodyBase`，

- **基准 ≤ `clearance − min(rel)` 就不穿地**（验收 6 只看这一条 ⇒ 基准取到那个上界也能过）
- 但基准越大，越会**整段固定抬高**（浮空）；越小，BodyLift 逐帧抬得越多（且受 `liftSmooth` 滞后限制）

⇒ 按「**哪些帧应该贴地**」选口径，不能一律取最深、也不能一律取最浅。

## 9.10 走路不循环 / 鼠标视角失效 / 动作廉价感（2026-09-15）

### 一、现象

> 「走路的动作没有循环，然后为什么鼠标转动视角没了，然后这个动作能不能再优化一下，
>   现在看起来很不连贯，攻击也是，走路也是，都看起来很廉价」

四条诉求里其实混着**两类**问题：一条是**我自己弄出来的环境事故**，三条是**动画本体的缺陷**。

### 二、逐条定位真因

#### 1. 「走路没有循环」——片段本身是单次播放

`Assets/Char_Feng/Animation/*.anim` 的 `m_LoopTime` **全是 0**（Walk / Idle / Roll 一个不落）。

判据不能靠眼睛：`.anim` 文本里 `m_AnimationClipSettings.m_LoopTime: 0`，
运行时读 `AnimationClip.isLooping` 也是 `False`。作为对照，UAL1 的 `Rig|Idle_Loop`
与 KI 的 `Run01_Forward` 都是 `True`。

**后果**：走路播一遍（1.333 s）就**停在末帧**，角色保持"迈完一步"的姿势不动，
直到 `Speed` 变化把状态切走 —— 观感就是「走一下、顿一下」。

#### 2. 「鼠标转动视角没了」——不是代码问题，是我留下的 Play 会话

编辑态探针直接读到现场：

```
EditorApplication.isPlaying             = True        ← Play 还开着
ThirdPersonCamera.mouseLookEnabled      = False       ← 鼠标被脚本关了
```

上一轮录屏用的 `Tools/cs/q_demo_fix.cs` 第 20 行有 `rig.SetMouseLookEnabled(false)`
（自动化录屏期间屏蔽鼠标干扰用），**跑完没有退出 Play**，
于是 Unity 里留下一个「鼠标被禁用」的会话，用户回来自然转不了视角。

**自证清白的对照实验**：脚本里手动把 `rig.yaw` 加 30°，下一帧相机 `eulerAngles.y`
确实变成 30.0 —— **相机链路本身完全通畅**，`Input.GetAxis("Mouse X")` 也正常返回、
四个轴都没抛异常、工程是旧版 Input Manager（`activeInputHandler: 0`，没装 Input System 包）。

**处置**：① `stop` 退出残留会话；② 演示脚本在 `EndInputOverride()` 之后
**补上 `rig.SetMouseLookEnabled(true)`**；③ 录屏收工一律 `stop`（这条本来就写在工程的坑表里，
是我自己的操作纪律没守住）。

#### 3. 「不连贯 / 很廉价」——拆成两个可以量的东西

**（a）走路步频 2.31 步/秒（竞走级）**

`walkSpeed 1.4 ÷ walkRefSpeed 0.91 = 1.54×`。真人走路 1.5~2.0 步/秒，
**2.31 已经进入竞走区间** —— 腿倒腾得比人快，看起来就是「小碎步快走」。

根子在 **Feng Walk 的原生速度太低**：0.91 m/s、步幅 **0.61 m**（对 2.45 m 的身高，
步幅/身高 = 0.25，而真人约 0.43）。要它跑出 1.4 m/s，只能靠倍率硬拉。

**（b）攻击收招段占一轮连击 60%+**

三段连击里「斩击本体」只占 31%，其余全是收招（`AtkNRec` 0.967 s / 1.033 s）。
挥出去很快、收回来很慢 —— 这是「廉价」的另一个直接来源。

### 三、关键方法：换片段**不能只看步频**，要看「脚位波动」

第一反应是换片段解决步频。**KI `Walk01_Forward`** 看起来完美：

| | 原生速度 | 步幅 | 用 1.4 m/s 播放时 |
|---|---|---|---|
| Feng `Walk` | 0.91 m/s | 0.61 m | **1.54×** → 步频 2.31 |
| KI `Walk01_Forward` | 1.80 m/s | 0.72 m | **0.78×** → 步频 1.94 ✓ |

于是我真把它换上去跑了一轮全套验收（全绿），**但录屏后的侧视连拍把我拦住了**。

新增判据：**原地走路动画的「网格最低点」应长期贴近地面**（任何时刻总有一只脚在支撑）。
跨度大 → 为了让它贴地，身体就必须跟着上下浮动同等幅度 → 走路一颠一颠。

| 候选 | 时长 | 最低点区间 | **跨度** | 脚踝抬升 |
|---|---|---|---|---|
| **Feng `Walk`** | 1.333 s | [-0.105, +0.060] | **0.166 m** | 0.12 → 0.34 |
| KI `Walk01_Forward` | 0.800 s | [-0.100, +0.227] | 0.327 m | 0.15 → 0.35 |
| KayKit `Walking_A` | 1.067 s | [-0.006, +0.256] | 0.262 m | 0.12 → **0.65** |

侧视连拍（`Tools/screenshots/walk_cmp/_sheet.png`）一眼可辨：
**KI 那一段第 4~6 帧大腿抬得像跨步/跑步**，而 Feng 是平稳的正常走路。

⇒ **回退到 Feng `Walk`**，转而用「降速让步频落回合理区间」来解决，
而不是「换一个步幅更大的片段」。

**这条判据的适用面**：任何「原地播放 + 脚本位移」的循环动画（走、跑、游、爬）都适用。
脚位波动是**片段可用性**的硬指标，和「张臂占比」（§9.8/§9.9）一样属于
**先量后选**、避免凭观感挑片段的那类判据。

### 四、处置

| 项 | 改动 | 理由 |
|---|---|---|
| 循环 | 生成 `Assets/_Project/Animations/Feng_Walk_Loop.anim`、`Feng_Idle_Loop.anim` | 源片段 `m_LoopTime=0` |
| `Walk` 片段 | 回退 Feng `Walk`（用循环副本） | 脚位波动最小（0.166 m） |
| `walkSpeed` | 1.4 → **1.25** | 倍率 1.37× → 步频 **2.06 步/秒**（124 步/分） |
| 攻击收招 speed | 1.40 → **1.70** | 收招占 60%+，是「廉价」主因 |
| `comboSwingDuration` | `{0.916, 1.032, 1.152}` → **`{0.813, 0.922, 1.152}`** | 按新速度重算（主段不变，故 `comboHitTime` 不动） |

**为什么用「副本」而不是直接改片段**：`/Assets/Char_Feng/` 受商店 EULA 约束
**不入库**（`.gitignore` 第 66 行），靠 `Tools/install_feng.py` 复原。
直接改它的 `.anim` 既不进 git、也会被复原脚本重新导入覆盖 —— 改了个寂寞。

**副本同样适用于 Idle**：`CombatStance` 战斗姿态播的是控制器的 `Idle` 槽位，
换名字会连带炸出下面这条隐患。

### 五、顺带挖出的一处「静默失效」

`CombatStance.TryReady()` 原来靠**片段名**认槽位：

```csharp
if (kv.Key != null && kv.Key.name == "Idle") { _combatIdleClip = kv.Key; break; }
```

把控制器 `Idle` 换成循环副本后名字变成 `Feng_Idle_Loop`，**这个匹配必然失效** ——
而它失效的后果是**整套战斗姿态静默失效**：武器不挂手、不握拳、不切片段，
**控制台一条报错都没有**（`TryReady()` 返回 false，下一帧再试，永远试不上）。

**处置**：① 匹配改为 `Contains("Idle")`（比 `==` 健壮，且控制器里只有这一个含 "Idle" 的槽位）；
② 新增显式字段 `combatIdleClip`，**显式配置优先**，不再依赖任何命名约定；
③ 内部字段拆成 `_idleSlot`（OverrideController 的 key）与 `_combatIdleClip`（实际播的片段）
—— 原来一个字段兼两个身份，改一处就会连带出错。

> **通用教训**：**「靠字符串名匹配来找资产」是脆性设计的典型**。
> 名字是给人看的，不是给代码认的。要么显式配置（`public AnimationClip`），
> 要么用**结构位置**（第 N 个槽位 / 组件类型），别用名字。
> 而且它**静默** —— 没有异常、没有红字，只有表现不对。

### 六、两个方法学坑（都是本轮踩的）

#### 1. `normalizedTime` **不会回绕**

循环动画的 `AnimatorStateInfo.normalizedTime` 是**持续累加**的（1.0 → 2.0 → 3.0），
**不会**回到 0。第一版判据写成「数值变小就计一次循环」，结果 4 s 走路只报「回绕 1 次」，
差点误判成「循环没生效」。

**正确判据**：看**终值**或**增量**。片段 1.333 s ÷ 倍率 1.374 = 0.97 s 一循环，
走 (2.5 − 0.3) s 应得增量 ≈ 2.3，实测 **2.29** ✓。

#### 2. 演示脚本要用**时间驱动**，不能按帧数等

编辑器里**边录屏边跑**，帧率会从 137 fps 掉到 **20~35 fps**（MP4 编码开销）。
按帧数等段长会被放大多倍：上一版「走路 240 帧」实际跑了 **11.3 s ≈ 14 m**，
**直接撞墙** —— 撞墙后 `CurrentSpeed` 变 0，报告里出现「跑步段 速度 = 0.00」。

> 顺带澄清：**游戏本身不卡**。S1/S2 验收同机实测平均帧率 **138.9 / 136.8 fps**
> （1920×1080），「不连贯」不是性能问题。

修法：`while (Time.time - t < 段长) yield return null;`，并在移动段之间
**用 CharacterController 开关把角色复位**（走路 + 跑步的位移会超出 Arena）。

## 9.11 持剑待机的剑插在脸上 / 跑步僵硬 / 左手握拳度反弹（2026-09-15）

### 一、现象

用户提了两条观感问题 + 一个技术询问：

1. **持剑待机时「剑插在脑门上面」**（附截图，剑竖直穿过面部）；
2. **「跑步的动作太僵硬了」**；
3. 询问能否自己操控 Blender 做动作（见「六、Blender 路线的评估」）。

### 二、「剑插在脸上」的真因：拿错了待机片段

先量后判。第一次量的结果是「剑身到头部 0.32 m，安全」——**那是错的**：
我拿 `SwordVfx.bladeLocalOffset` 当剑轴锚点，而实测 `bladeAnchor` **就是手骨本身**
（`localPos (0, 0.113, 0)`），轴取错了，量出的距离自然不对。
改用 `weapon.transform.up` 也只得到 55.5°，仍然不是真相。

**正确的量法**：取**武器渲染体世界 AABB 的最长边**当剑轴，
并用 `Distance(p1, grip) >= Distance(p2, grip)` 判哪一头是剑尖（端点轴会撒谎，见 §9.6 的教训）。

改正后数据一目了然：

| 待机片段 | 剑身线段 → 面部最近距离 |
|---|---|
| `Feng_Idle_Loop`（原用） | **0.045 m** ← 贴在脸上 |
| `Rig|Sword_Idle`（UAL1，改用） | **0.856 m** |

`Feng_Idle_Loop` 的姿势是「双手抱剑于身前、剑身竖直」，剑正好从下巴划到额头。
改用 UAL1 自带的 `Rig|Sword_Idle`（**剑客预备式**）即可，零下载。

> 顺带记一条工程习惯：**渲染体包围盒 > 节点轴 > 组件字段注释**。
> 端点轴会撒谎、字段注释会撒谎（§9.1 已记「注释会撒谎」），
> 只有渲染体的实际几何不自洽不了。

### 三、「跑步僵硬」的真因：不是腿，是**右臂把剑抡起来了**

逐项排除，每项都留了数据：

| 怀疑对象 | 实测 | 结论 |
|---|---|---|
| 有遮罩层锁死了手臂 | `q_pose3`：控制器**只有 Base Layer**、无 AvatarMask | 排除 |
| 步伐没和速度同步 | `MotionSpeed ≈ 0.97`、步频 3.2 步/秒 | 排除 |
| 腿没动 | 逐骨角度行程：`Run01_Forward` 0.6 s 腰 72° / 肩 242° / **肘 305°** | 排除（腿动得够） |
| **右臂摆幅把剑抡出去** | **剑尖总行程 7.611 m**、剑轴扫过 **20°~170°** | ★ 真因 |

**新立判据：「剑尖总行程」** —— 一个循环内剑尖在**角色自身坐标系**里的累计路径长度。
它把「剑甩得有多厉害」变成一个可比的米数，比目测「僵不僵」靠谱得多。

为什么不能直接换 UAL1 的跑：

| 候选 | 单步距离 | 参考速度 | 换成 `runSpeed 4.0` 后 |
|---|---|---|---|
| KI `Run01_Forward` | 1.250 m | 4.167 | 1.00× ✓ |
| UAL1 `Jog_Fwd_Loop` | 2.547 m | 5.457 | 0.73× ⇒ **被拖成慢动作，更怪** |
| UAL1 `Sprint_Loop` | 2.106 m | 6.319 | 0.63× ⇒ 同上 |

KI 的**腿**本来就是对的（单步 1.25 m ≈ 真人慢跑、步频 3.33），错的只是**右臂**。

### 四、处置：用 humanoid「肌肉通道」烘焙，只换右臂

humanoid 片段的曲线是 **130 条肌肉通道**（PropertyName 形如 `"Right Arm Down-Up"`、
`"Right Shoulder Front-Back"`、`"Right Hand In-Out"`），
于是可以**按通道名筛选**、只替换右臂那 36 条：

- 腿 / 躯干 / 左臂：**原样保留** KI 的跑步数据；
- 右臂：整段替换为 UAL1 `Rig|Idle_Loop` 在 `t = 0.50 × 长度` 处的**定值**（持剑稳定架势）；
- 补 `loopTime = true`。

工具 `Tools/cs/q_bake_run.cs`，产物 `Assets/_Project/Animations/Baked/Run01_Carry.anim`。

| 指标 | 原 `Run01_Forward` | 烘焙 `Run01_Carry` |
|---|---|---|
| 剑尖总行程 | 7.611 m | **0.585 m（−92%）** |
| 剑 → 面部 | 0.210 m | **0.722 m** |

**必留对照**：同一批次还烘了 `Run01_Ctrl`（`keep = 1.0`，行为应与原片段**完全一致**），
用来证明「烘焙器本身没引入退化」。实测 `Run01_Ctrl` 剑尖行程 7.611 m 与原片段逐位相同。

> 命名时**刻意避开 `Idle` 字样** —— 原因见下一节。

### 五、同一个坑**第二次**发作：「按名字匹配」是个单点故障

烘焙的第一个版本叫 `Run01_IdleArm`。名字里有 `Idle`。
而 `CombatStance.TryReady()` 当时是靠 `kv.Key.name.Contains("Idle")` 认
`AnimatorOverrideController` 的 **Idle 槽位**的钥匙 —— 于是它把
**Run 状态的槽位**当成了 Idle 槽位 ⇒ **Run 状态被覆盖成待机片段**，
跑步时角色在待机。**零报错。**

这是和 §9.10 末尾「`CombatStance` 靠 `name == "Idle"` 匹配槽位」**完全同一个坑**，
上一次的修法（`name == "Idle"` → `Contains("Idle")`）只是把触发面放大了。

**这次的修法（三级匹配，把"猜"降级为兜底）**：

1. **显式配置优先**：新增序列化字段 `CombatStance.idleSlotClip`
   （= 控制器里 Idle 状态本来的片段，本项目 `Feng_Idle_Loop`），按引用/名字精确定位；
2. 没有配置才按名字猜，且**加动作关键词黑名单**
   （`Run / Walk / Atk / Sword / Dash / Dodge / Jump / Hit / Death / Roll / Cast`）——
   名字里同时含 `Idle` 和任一动作词的一律不认；
3. 再找不到才放宽（基本不该走到）。

> **规矩**：凡是「用字符串近似匹配资产身份」的地方，都必须（a）提供显式配置入口、
> （b）把模糊匹配降级为兜底、（c）失配时**要吵**不要静默。同一类坑踩两次说明第一次只治了症。

### 六、`FootIK.stateOffsets`：键要从「状态名」换成「片段名」

Idle 状态的片段会在运行期被 `CombatStance` 在两段之间切换
（`Rig|Idle_Loop` 非战斗 / `Sword_Idle_Loop` 战斗），而偏移表只按**状态名**查 ——
**一个状态存一个数值，必然有一段是错的**。

改为 **`ResolveStateOffset` 片段名优先、状态名兜底**
（`Animator.GetCurrentAnimatorClipInfo(0, buf)` 会反映 OverrideController 的替换），
并新增只读探针 `CurrentOffsetKey`，把「这一帧用的是哪把钥匙」打出来。

| 片段 | 无IK最低 min~max | 口径 | 建议偏移 | 现值 |
|---|---|---|---|---|
| `Rig\|Idle_Loop` | — | 取最浅 | 0.0271 | Idle 状态名 0.0307 |
| `Sword_Idle_Loop` | −0.0542 ~ −0.0427 | 取最浅 | **0.0477** | ★ 原来套用 Idle 的 0.0307 ⇒ **恒定下沉 2.35 cm** |
| `Run01_Carry` | −0.1757 ~ +0.4020 | 取最深 | 0.1807 | Run 状态名 0.1735（见下） |

**两条口径的取舍**（承接 §9.9「两种口径要对号入座」）：
`BodyLift = Clamp(need, 0, maxLift)` **只会往上抬**，所以静态基准**宁小勿大** ——
小一点让 IK 去贴地、大一点会把整段跑步抬成悬空（`6b 不浮空` 判据 ≤ +0.05 m）。
`Run01_Carry` 因此**不采用公式值 0.1807，保留 0.1735**（实测贴地后最低点 **+0.031 m**，判据内）。

落地：`Tools/cs/q_apply_offsets.cs`（编辑态）写入 9 条状态名 + 4 条片段名
（`Rig|Idle_Loop` / `Sword_Idle_Loop` / `Feng_Walk_Loop` / `Run01_Carry`）——
片段名条目让两段各拿各的值，也防止下次换片段时静默套用旧值。

### 七、最阴的一条：左手握拳度被**静默反向标定**

改完上面这些，验收只剩一项未通过：

```
[未通过] 攻击全程两手都握着（不是五指摊开）  攻击帧握拳度峰值 右 1.547 / 左 2.601
```

上一版（HEAD）同一项是 `右 1.547 / 左 1.582`，**右手完全没变、只有左手退化**。

逐帧取证（`Tools/cs/q_fist.cs`）否掉了第一直觉「峰值出在 Idle→Atk1 的交叉淡化帧」：
峰值落在 `Atk1Rec nt=0.75` 的**纯攻击姿态稳定帧**。
真正异常的是：左手在整个攻击过程都是 **2.1~2.6**（比「五指摊开≈2.2」还高），
而右手恒定 1.55。**左手不是没卷，是被反着卷了**——手指被掰开。

横向对比早前的报告即锁定：

| 出处 | `LeftCurlSign` | 左握拳度 |
|---|---|---|
| `q_fist2`（11:14） | **−1** | 1.50 |
| `q_fist3`（12:44）手动验证 | 左手 −70° → 0.114 m（收拢）／ +70° → 0.214 m（掰开）⇒ 正确符号 = **−1** | — |
| `q_fist`（本轮） | **+1** ← 反了 | 1.87 ~ 2.60 |

**根因在 `WeaponHandPose.CalibrateSign` 的三行**：

```csharp
float before = (tip.position - hand.position).magnitude;
... 卷 40° ...
if (Mathf.Abs(after - before) < 0.001f) return 1f;   // ← 判不出来就默认「正号」
return after > before ? -1f : 1f;
```

它是**一次性**标定（`Resolve()` 里只跑一次），而**测量手段依赖当时的姿态** ——
某些姿态下 ±40° 引起的「指尖到腕」变化量会小到接近 0，
于是落到 `return 1f` 兜底，**左手被定成正号**。换一个待机片段就足以改变那一瞬的姿态。

**修法：`CalibrateSign` → `MeasureSign`，每帧当场实测。**

- 每帧拿食指链当探针，±60° 各拧一次，取「指尖离腕更近」那个方向；
- 两方向差别 < 0.5 mm = 这一帧判不出来 ⇒ **沿用上一帧**（不瞎翻）；
- 换符号需要另一个方向明显更优（> 2 mm，**迟滞**），避免逐帧横跳把手指抖花；
- 探针改完**必须原样还原**（`Curl` 随后会重新施加真正的卷曲）。

**再加一道「失效要吵」的守卫**：连续 Armed 超过 12 帧后，若握拳度 > **2.05**
（即「比五指张开还开」），打一条 `Debug.LogWarning` 说明卷曲方向可能反了；
恢复时再打一条。这类失效**不会自己报错**，本项目已经因此吃过两次亏。

修复后：`LeftCurlSign = −1`，左握拳度峰值 **2.601 → 1.463**（`q_fist.txt`），
验收回到 `右 1.547 / 左 1.582`——与 HEAD 基线**逐位一致**。

### 八、Blender 路线的评估

结论先给：**能接，但不该现在接；"让 AI 做全部动作"不是这个毕设的正确投入方向。**

**技术上可行**：Blender 有官方 MCP（`blender-mcp`），接入后等价于拿到一个
**Python 执行口**（`bpy`），可以做程序化建骨/改权重/生成关键帧/批量导出 FBX。
所以「操控 Blender」这件事本身没有障碍。

**真正的代价在别处**：

| 环节 | 实情 |
|---|---|
| 动作**好不好看** | `bpy` 能写出「手臂摆 30°」，写不出「打起来有魂」。手感来自关键帧的**节奏与缓动**，需要人反复看、反复调 |
| 与现成的比 | 本项目已接入 UAL1/UAL2（剑术库）、KI（跑步）、Feng（主角带 10 段）**共 4 套 CC0/免费库**，覆盖了移动/攻击/待机/受击的全部需求；自己做的动作大概率更差 |
| 与骨架对接 | 自己做的动作要**重定向**到 CC_Base 骨架，等于把「换骨架要重标什么」的账再付一遍（见 §9.5 换模型清单） |
| 毕设收益 | 论文写的是「全流程设计与实现」；**接入 + 改造第三方动作（本轮做的肌肉通道烘焙）本身就是更有分量的工程内容**——它证明了「按通道拆解 humanoid 片段、只替换需要换的肢体」这套方法 |

**什么时候值得上 Blender**：需要**现成库里没有**的专属动作（例如与水墨刀光强绑定的
「收刀入鞘」「蓄力重击」），且已经接受「要反复看反复调」。那时再装 MCP，
用它做「批量导入导出 / 重定向 / 程序化修数据」，把审美判断留给人。

S1 **31/0** · S2 **54/0** · 姿态 **4/0**，Console **0 红字**。

## 9.12 持剑待机跨立 / 跑步脚 90° 旋转 / 跑步高出来一格（2026-09-15）

### 一、现象

2. 跑步时「**脚都 90 度旋转了，神了**」；

4. 「**你帮我装上 mcp**，然后后面再说做不做」——否决了 §9.11 末尾「不该现在接」的建议，要求先装。

### 二、「跨立太丑」= 现用待机片段其实是**出剑姿势**

现用 `Sword_Idle_Loop`（= UAL1 `Rig|Sword_Idle`）实测：

| 指标 | 现用 `Sword_Idle_Loop` | 新 `Baked/Idle_Carry_A` | 非战斗待机（参照） |
|---|---|---|---|
| 双脚横距 | 0.599 m | **0.524 m** | 0.526 m |
| 双脚纵距 | **0.090 m** | **0.294 m** | 0.289 m |
| 脚自身偏角 L/R | **18.5° / 22.9°** | **0.4° / 0.4°** | — |

**判据定下来**：自然站姿 = **横距 ≈ 0.52 m 且纵距 ≈ 0.29 m**。旧片段的纵距只有 0.090 m —— 双脚几乎落在同一条横线上、各自向外撇，这正是「跨立 + 外八」的几何定义。

**处置**：`Baked/Idle_Carry_A` = UAL1 `Rig|Idle_Loop`（用户已认可的自然站姿）作底座，**按 humanoid 肌肉通道分组只替换右臂 9 条**，右臂取自 `Rig|Sword_Idle` 在 0.35×长度的定值。腿与躯干完全不动，所以站姿天然就是用户认可的那个。

### 三、「跑步脚 90° 旋转」的真因：源片段右脚通道**严重超出生理极限**

先看曲线层（humanoid 肌肉值 × `HumanTrait` 界限 = 真实角度）：

| 通道 | KI `Run01_Forward` 右脚 | 换算角度 | 界限 | 同片段**左脚** | 同作者 `Walk01` 右脚 |
|---|---|---|---|---|---|
| `Foot Twist In-Out` | [−4.012, −0.876] | **[−120.4°, −26.3°]** | ±30° | [0.5°, 8.4°] ✅ | [−0.015, 0.211] ✅ |
| `Foot Up-Down` | [−1.802, 2.122] | **[−90.1°, +106.1°]** | ±50° | [13.1°, 77.8°] ✅ | [−0.747, 0.262] ✅ |
| `Lower Leg Twist In-Out` | [0.647, 1.892] | [58.2°, 170.3°] | ±90° | [−10.3°, 2.0°] ✅ | [−0.030, 0.038] ✅ |

用户说的「90 度」是准的 —— 实测脚外翻到了 **−120°**。

**三个对照实验把嫌疑范围压到「这一份 FBX」**：

1. **同片段左脚完全正常**（Twist 只摆动 0.5°~8.4°）；
2. **同作者同骨架的 `Walk01_Forward` 右脚也正常** ⇒ 排除「KI 的导出手法」「KI 的 avatar」；
3. **两个 FBX 的 importer 设置逐字段相同**（`animationType: 3`、`animationCompression: 0`、`resampleCurves: 1`）⇒ 排除导入精度差异。

⇒ 不是重定向配置、不是 Feng 骨架、不是本项目烘焙脚本（`q_bake_run.cs` 只替换右臂 36 条，腿一条没碰）。

**T-pose 层面的根因**（`Avatar.humanDescription.skeleton`）：

| 骨骼 | KI 的 T-pose 局部四元数 | Feng 对应骨 |
|---|---|---|
| `B-foot.R` | (−0.1, 0.9, −0.5, **0.1**) | `CC_Base_R_Foot` (0.6, −0.1, 0.1, **0.8**) |
| `B-toe.R` | (0.0, 1.0, −0.2, **0.0**) | `CC_Base_R_ToeBase` (0.2, 0.0, 0.0, **1.0**) |

KI 的足部骨骼 T-pose **w≈0**，即姿态本身接近 **180° 的奇异点**；Feng 的 w≈0.8~1.0 是常规姿态。**插值在奇异点附近会「绕远路」**，于是肌肉值被炸到 −4.0 这种量级。这是源数据与 avatar 的固有特性，**只能在曲线层面修**。

**度量上第三次踩同一个坑**：脚骨的 `transform.forward` 在 CC 骨架上**近乎垂直朝上**（基准 pitch 实测 −76.4°），所以任何「投影到水平面再求夹角」的 yaw 度量都是噪声（左右脚基准居然差 69°，−27.3° vs +41.9°）。**唯一可靠的量是 `Quaternion.Angle(基准脚旋转, 当前脚旋转)`** —— 它不依赖骨骼轴的定义。

**活体实测（左右脚总偏角之差，同一次会话内对照）**：

| 候选 | 左脚 | 右脚 | 左右差 |
|---|---|---|---|
| 原 KI `Run01_Carry` | 80.9° | **136.4°** | **55.4°** ❌ |
| 换 UAL1 `Rig\|Sprint_Loop` 底座 | 61.1° | 67.7° | 6.6° ✅ |
| **修 KI 右脚后 `Run04_KI_Carry`** | 81.3° | 98.4° | **17.2°** ✅ |

> 注：`Run04` 的 17.2° 主要来自**脚踝 pitch**（左右腿相位不同、支撑脚与摆动脚本来角度就不同），不是 yaw。yaw 那两条通道已与左脚逐位对齐。

### 四、修法：用「**同片段左脚**」校准右脚，但**要看通道性质决定锚点**

公式：`newVal(t) = anchor + (leftSpan / rightSpan) × (oldVal(t) − rightMean)`

**为什么要用同片段左脚而不是拿 Walk 当参照**：同一动作、同一时刻，跑步的左右腿在统计上应当对称，左脚就是这个片段自带的「正确参照系」。压幅度（`leftSpan/rightSpan`）后波形形状、相位完全保留。

**关键区分（第一版就踩了）——`anchor` 取谁**：

- **`Twist` 类取 `leftMean`（对齐）**：右脚均值 −2.623 本身就是错误的（= 脚外翻 78.7°），必须拉回来；
- **`Up-Down` 类取 `rightMean`（保留）**：左右均值差 0.253（= 12.7°）在跑步里只是**相位差**。第一版 `Run03_KI_Carry` 把均值也对齐了，结果**全循环最低点从 −0.142 恶化到 −0.241** —— 脚被整体压低，反而更穿地。**这正是「改了 A 指标、B 指标变差」的典型，说明判据要成对看。**

`Run04_KI_Carry`（`Tools/cs/q_bake_run5.cs`）修正结果：

| 通道 | 右脚（修正后） | 左脚（参照） |
|---|---|---|
| `Foot Twist In-Out` | [0.6°, 8.5°] | [0.5°, 8.4°] |
| `Lower Leg Twist In-Out` | [−9.7°, 2.6°] | [−10.3°, 2.0°] |
| `Foot Up-Down` | [9.7°, 74.4°]（均值保留） | [13.1°, 77.8°] |

同时把右臂统一接 `Rig|Sword_Idle`@0.35 —— 与 `Idle_Carry_A` **同源**，修掉一处不一致：旧 `Run01_Carry` 的右臂取自 `Rig|Idle_Loop`（自然下垂），待机切跑步时手臂会跳。

### 五、「跑步高出来一格」的真因：`BodyBase` 按「最深帧」标定，而 `BodyLift` **只上抬不下降**

`FootIK` 的模型是：

```
AppliedBodyOffset = BodyBase + BodyLift
need = (groundY + groundClearance) − low.y − BodyBase     // BodyLift 的输入
BodyLift = need > 0 ? 平滑后的 need : 0                    // ← 负值被丢弃
```

⇒ **「浮空」完全由静态 `BodyBase` 决定**，动态 IK 只负责「补穿地」。

**一维扫描（`q_off_scan.cs`）证明「贴地」与「不飘」在一维上不可兼得**：

| `BodyBase` | 实测最低点 | 中位（= 用户看到的飘） | 穿地帧% |
|---|---|---|---|
| 0.04 | −0.127 | **0.120** | 24.9% |
| 0.15 | −0.069 | 0.215 | 9.0% |
| 0.25 | **+0.001** ✓ | **0.313** ❌ | 0.0% |

各档「中位 − 最低 ≈ 0.31 m」几乎是常数 —— 这个差就是**动画本体鞋底高度的分布跨度**。要让最深帧不穿地，就得把整段抬起来，于是其余帧全飘。

**破局点：`BodyLift` 是平滑的，跟不上跑步的落地**。`liftSmooth = 14` ⇒ 时间常数 τ ≈ 1/14 s = **71 ms**，而跑步落地在 **≈100 ms** 内最低点突变 0.2 m —— 平滑没走完，脚已经穿过去了。扫描里 `BodyBase=0.04` 档 `BodyLift` 冲到 0.261 却仍有 −0.127 的漏穿，就是实证。

**二维扫描（`q_scan2.cs` / `q_scan3.cs`）：把 `liftSmooth` 提到 150 后，两者可以同时做到**：

| (`BodyBase`, `liftSmooth`) | 实测最低点 | 中位 | 穿地帧% | `BodyLift` 抖动 |
|---|---|---|---|---|
| (0.24, 14) 旧方案 | −0.010 | **0.164** | 0.0% | 0.0012 |
| (0.10, 150) | −0.020 ⚠ 贴边 | 0.034 | 0.0% | 0.0157 |
| **(0.12, 150) 采用** | **−0.015** ✓ | **0.048** | **0.0%** | 0.0107 |

⇒ **中位浮空 17.4 cm → 4.7 cm**（改善 12.7 cm），同时穿地帧 0%、体检两条断言全过。

> 「抖动」= 相邻帧 `BodyLift` 差分的 RMS。提平滑后它涨到 0.0107 m/帧 ≈ 0.64 m/s 的竖直速度波动 —— 但它**不是噪声**，是「跟随支撑脚落地」所必需的竖直运动；人跑步本来就有上下起伏。真实噪声要看 `LowestMeshY`，而它由 `BakeMesh` 逐顶点算出，是确定性的、无噪声。

`liftSmooth` 是**全局参数**（所有状态共用），所以必须跑全套体检确认零回归 —— 结果 Idle/Walk/Dash/Atk1-3 全部仍是 0.003~0.005 m ✓。

### 六、一个会**静默污染后续实验**的写法（值得记住）

探针脚本在结尾「还原 override」时写成了：

```csharp
if (ovr != null && runKey != null && runOrig != null) ovr[runKey] = runOrig;
```

而 `runOrig`（该槽位的原始值）**本来就是 `null`** ⇒ 条件永假 ⇒ **还原被跳过**。残留的 `Run01_Carry → Run02_Jog_Carry` 让下一个脚本读到一个「莫名其妙已被替换的槽位」，我还一度以为是别的脚本设的。

**规范：还原动作无条件执行**，只判「目标是否存在」（`ovr != null && runKey != null`）。

### 七、清理脚本的坑：`FindAssets` 看不到 FBX 内部子资产

清理未采用变体时用 `AssetDatabase.FindAssets("t:AnimationClip")` 建「现存片段名」集合，来清理 `FootIK.stateOffsets` 里的死条目 —— 结果 **`Rig|Idle_Loop` 被误判为死条目删掉了**。

原因：该 API 对 FBX 只返回 FBX 资产本身，而 `LoadAssetAtPath<AnimationClip>(fbx)` 返回 `null`（主资产是 GameObject），**UAL1 内部的 `Rig|Idle_Loop` 因此不在集合里**。

**正解**：`AssetDatabase.LoadAllAssetsAtPath(fbx)` 后逐个子资产收集。
本次因 `Rig|Idle_Loop` 与状态名 `Idle` 同值（0.0307），实际无影响，已用 `q_fix_offsets.cs` 补回显式条目。

| **ShaderLab 装饰器** | `[Header(Ink —— 墨色与阶数)] [Space(6)]` 报 `Parse error: syntax error, unexpected $undefined ... at line 27`，**而且 shader 名是空的**（看着像文件本身坏了） | 团结引擎的解析器既不接受含 `——` 的头、也不接受带引号的 `[Header("...")]`、更不接受 `[Space(6)]`。**直接删掉装饰器改 `//` 注释分组**（本轮两次改法都不通，走了三轮才定位） |
| **手写 ShadowCaster 少了 include** | `Shadows.hlsl(298): 'LerpWhiteTo': function does not exist` | `LerpWhiteTo` 在**核心包**的 `CommonMaterial.hlsl`；URP 的 `Shadows.hlsl` 只 include `Common.hlsl`。官方 shader 之所以没事，是因为它们先 include 了 `SurfaceInput.hlsl` ⇒ 手写 Pass 要显式补 `CommonMaterial.hlsl` |
| **法线重复解码** | 折痕全是错的，但不报错 | `_CameraNormalsTexture` 是 **`R8G8B8A8_SNorm`**（有符号归一化），采样出来**已经是 [−1,1]**，不能再 `*2−1`；`SampleSceneNormals` 已经处理了延迟管线的八面体分支 |
| **`=>` 表达式体函数 / 自命名采样器** | `unexpected token '='`、`Unrecognized sampler 'sampler_sourcetex'` | Unity 在 D3D11 上走 **FXC**，不认 `=>`；采样器只能用内建名（`sampler_LinearClamp`）或 `sampler_<纹理名>` |

### 三、E2「飞白墨线」的两个真缺陷（"墨线看不见 + 地上长出假纸纹"）

**首跑 ④ 段给出 `③ − ② = 0.010`** —— 即"加上墨线这一层，画面几乎没变"。而同一次截图里，**阶段 3 的地面却出现了一片本不该有的斑驳**。一张图同时暴露两个反向的错：

1. **深度项用的是一阶差分**：`Σ|d(L/R/U/D) − dC|`。**掠射角地面本身就是一条深度斜坡**，一阶差分**恒为正值** ⇒ 整片地面被判成"轮廓"，再叠上飞白噪声就成了"地上长出一片纸纹"。
   **正解 = 二阶差分（Roberts 式）**：`|dL − dR| + |dU − dD|`。平缓斜坡被减掉，只有真正跨过物体边界的"断崖"留得下来。另配一个**深度死区** `_DepthBias` 把残余噪声压掉。
2. **墨线被自己的阈值压没了**：上一版是 `smoothstep(0.05, 0.18, ink)` 之后再乘 `saturate(ink × _LineStrength)`，而飞白项先把中值削到 `lerp(1, 0.45, 0.72) = 0.60` —— 算下来普通轮廓只剩 **不到 3%** 的混合量。
   **正解**：飞白只调**浓淡**、起笔只做**软起笔**，别串两道阈值。
3. **补一项"天空剪影"**：二阶差分对**薄物体**（剑刃、发簪）会失效 —— 两侧邻域都落进天空、差值互相抵消。用"中心是实体 + 对面是天空"兜它，顺带把地平线画出来。
4. 三项用 **`max` 而不是相加**：它们描述的是**同一个边界**，相加只会把强度和噪点一起翻倍。

修完 **`③ − ② = 0.010 → 0.067`（可见度 6.7 倍）**，地面假纸纹消失。

### 四、E1 的一个着色错误：重复乘 albedo

```hlsl
// 错：paperTint 里已经含了 albedo，再乘一次等于把贴图算成 albedo²
half3 paperTint = _PaperColor.rgb * lerp(half3(1,1,1), albedo, 1.0h - _InkDensity * 0.35h);
half3 color = lerp(shadowColor, paperTint * albedo, ramp);
```
后果是**亮部整体发暗**、而且**无论怎么调色都"不像水墨"**。改正后固有色的掺入量直接由 `_InkDensity` 控制（越大越接近纯纸色 = 留白），单这一处就让 **`② − ① = 0.026 → 0.169`**。

### 五、度量在 ⑤b「白球量化实验」上**连续翻车四次**（最有价值的一节）

④ 段的对照组证明不了"量化"：着色器在同一墨阶内**仍然乘漫反射贴图**，亮度本来就会连续变化，用"全画面对比度"去证明"量化"是**错的尺子**。于是改在白球上量（无贴图、关飞白/轮廓/高光，画面里只剩量化）。四次翻车：

| # | 现象 | 真因 | 修法 |
|---|---|---|---|
| 1 | 阶数全是 1 | 主光方向是场景定的，球正面**背光** | —— |
| 2 | 配了"正对球面"的点光，阶数还是 1 | **近距离点光（0.9 m / 强度 3.5）把球打爆成纯白**：PBR 对照组平均亮度 **0.957**、单一级别占 **85%**。饱和的输入里**根本不存在可分的阶** | **受控光照**：关掉场景所有灯 + 环境光清黑 + `DynamicGI.UpdateEnvironment()`，只留一盏**顺镜头方向**的平行光 ⇒ 球面 N·L 从圆心 1.0 平滑降到边缘 0.0 |
| 3 | 一会儿过、一会儿不过 | 判据 `n80`（覆盖 80% 像素需要几个 64 桶）恰好卡在 **5/6 边界**，同一份代码重跑就翻面 | 换成 **`cover4`：前 4 种墨色覆盖了多少像素** —— 这才是"4 阶量化 = 画面只剩 4 种墨色"的直接数值形式，不经过任何二次阈值 |
| 4 | `cover4` 只有 75%，不达 90% | **`_BandSoftness = 0.06` 的软边过渡**：三个阶边界各摊开约 0.12 的亮度宽度，按球面面积积分**正好吃掉约 32% 的像素** | 探针里把柔度压到 **0.01**（软边是**美术过渡**，与"有没有量化"是两件事，必须隔离） |

**最终判据与实测**（`Tools/reports/S4_latest.txt` ⑤b）：

| 组 | 前 4 种墨色覆盖 | 最大单一墨色占比 |
|---|---|---|
| URP/Lit（PBR 对照） | **43.1%** | 12.6% |
| 水墨 2 阶 | 98.5% | 90.1% |
| **水墨 4 阶** | **92.4%** | **49.1%** |
| 水墨 8 阶 | 82.8% | 34.4% |

三条判据：① 4 阶覆盖 ≥ 90%（92.4% ✓，PBR 只有 43.1%）；② 最大单一墨色占比高于 PBR（49.1% vs 12.6%）；③ **随阶数单调**（98.5 ≥ 92.4 ≥ 82.8）。

> 这一节的方法论：**"只差一项未通过、其余全正常"要先怀疑度量本身**。四次里有三次是尺子坏了（背光 / 打爆 / 卡边界），只有第四次才是画面的真实属性（软边摊平），而它仍然不属于"量化"这个被测对象。

### 二、五条设计决策（每条都写清了「另一种写法为什么不行」）

**1. 属性叠加用加法累加，不用连乘。** `+25%` 叠两层 = `×1.50`，不是 `×1.5625`。
连乘的问题不是数学错，而是**顺序敏感 + 会爆炸**：技能一多，`×1.15 × ×1.12 × ×1.35 …` 的乘积增长极快，
且"先拿哪个技能"会改变最终数值 —— 论文里既不好解释也不好复现。加法累加让「第 N 层技能值多少」是常量，
上限（`maxDamageBonus = 3`）也才有意义。验收里特意断言了 `+25% ×2 = ×1.50` 这个**能被连乘写法判错**的数字。

**2. 加权抽样用 A-Res，不用轮盘赌。** `key = u^(1/w)` 取最大的 n 个（Efraimidis & Spirakis 2006）。
理由是轮盘赌在**候选数接近抽取数**时会退化：三选一常走到"池子里就剩 3 条"，此时轮盘赌已经抽中过的还要重抽、
期望轮次发散。A-Res 一次遍历、天然不重复、权重意义直观（权重高 → key 更靠近 1）。
实测：同稀有度内 墨锋(w=1.2) 被抽 **354** 次 vs 疾风(w=0.7) **248** 次（各 1200 轮）。

**3. 参数面板不写任何资产。** 见 §9.14；本 Sprint 的 `InkBloomFeature` 沿用同一约定，
`InkStyleRegistry.BloomRuntime` 只在内存里覆盖。

**4. 墨晕 ≠ Bloom，方向是反的。** 图形学 Bloom 是**亮部向外发光（加法）**；水墨的"晕"是**暗部往纸里渗（乘性压暗）**。
所以阈值取的是**暗度** `1 − luma`，结果 `scene * (1 − amount)`。如果照抄 Bloom 的加法，
得到的是一圈发光的边 —— 那不是墨，是霓虹。验收里把方向写成了断言：平均亮度 **0.515 → 0.412（必须变暗）**。

**5. 三选一面板用 IMGUI，且把 `InjectChoice` 做成一等公民接口。** 见 §9.14 的偏离说明（IMGUI vs `VolumeComponent`）。
这里多一条：**自动验收必须能"替玩家做选择"**。若面板只有鼠标点击路径，整个 Roguelike 循环就只能靠人测。
`InjectChoice(int index)` 与 `IsShowing` / `Options` 一起构成验收入口，测试因此能跑完一整局。

### 四、`Time.timeScale` 的单一所有权冲突（本轮最值得记住的一条）

顿帧（`HitStop`）与"奖励暂停"都要改 `Time.timeScale`，而 `HitStop` 的恢复逻辑写的是
「**写回进入它之前的值**」。于是：命中顿帧的 0.08 s 里玩家升级 → 奖励界面设 `timeScale = 0` →
顿帧倒计时结束 → 它把 `timeScale` 恢复成 **1** ⇒ **暂停被无声解除，玩家可以边选技能边被砍**。

处置：进 Reward / GameOver / 复位**之前一律先 `HitStop.ForceEnd()`**（新增接口），把顿帧当场结清。
验收里把这条也写成断言：`进奖励前先把顿帧结清（HitStop.IsActive == false）`。

配套的第二件工具是 **`WaitUnscaled`**：`timeScale = 0` 时 `Time.time` / `yield return WaitForSeconds` 全部不动，
验收协程会在暂停那一拍**原地挂死**（而且是静默挂死，看起来像"卡住了"）。所有等待一律走 `Time.unscaledTime`。

## 9.16 Sprint 6 · 一轮用户观感反馈（震动 / 移速 / 白盒 / 发灰 / 挥墨）+ 连招卡帧（2026-09-15）

这一轮用户一次提了五条观感诉求，另报一条 bug。五条听起来都是"感觉不对"，但**真因分属五个完全不同的层**
（时序 / 档位语义 / 材质 / 光照+后处理 / 程序化几何）。**把它们分开定位，是这一轮唯一重要的事** ——
"感觉不对"如果不拆成可量测的项，就只能靠反复改数值碰运气。

### 二、震屏：`Time.timeScale` 的**第三次**发作

前两次见 §9.15 四（顿帧把奖励暂停写回 1）与 §9.15 的 `WaitUnscaled`。这次轮到震屏：

```csharp
// 改之前
if (_shakeTimer > 0f) { _shakeTimer -= dt; ... }   // dt = Time.deltaTime
```

震屏是**逐帧直接写 `transform`** 的（不走 `SmoothDamp`），所以 `_shakeTimer` 减不到 0 就**每帧都在抖**。
`timeScale = 0` 时 `deltaTime == 0` ⇒ 一次命中触发的震屏会把画面抖到玩家选完技能为止。

**处置分三层，且刻意三层都留**：

| 层 | 做法 | 语义 |
|---|---|---|
| 相机内部 | 递减改用 `Time.unscaledDeltaTime` | 即使被别处改了 timeScale，也能自然衰减到 0 |
| 相机内部（兜底） | `timeScale <= 0` 时**直接把震动结清** | 暂停时画面上任何东西都不该动 —— 哪怕用 unscaled 自然衰减，玩家在 UI 上仍会看到半秒抖动 |
| 调用方（显式） | 新增 `ThirdPersonCamera.StopShake()`，由 `RunManager.TakeOverTimeScale()` 在进 Reward / 结算前主动调 | "这一局的表现反馈已经结束了"，比靠全局状态推断清楚 |

**两个必须注意的细节**：

- `StopShake()` 必须**连幅度一起清零**。只清 `_shakeTimer` 的话，残留的大幅度会把下一次较小的震动挡掉
  —— 因为 `Shake()` 第一行是"更强的不打断"判据（`if (amplitude < _shakeAmplitude && _shakeTimer > 0f) return;`）。
- `TakeOverTimeScale()` 是把 §9.15 的 `HitStop.ForceEnd()` 与 `StopShake()` **捆成一个入口**。
  凡是"要接管 timeScale"的地方一律只调它 —— 这样以后再加一个吃 timeScale 的系统，也不必去改四处调用点。

### 三、平时移动太慢：真因是**档位语义**，不是速度数值

用户说"走路太慢"，最直觉的改法是调大 `walkSpeed`。**试过了，是错的**：

- 走档片段（Feng `Walk`）原生 **0.91 m/s**（脚踝法实测，见 §9.9）。要让步态看着自然，播放倍率必须留在 1.0~1.6
  ⇒ **物理速度上限约 1.5 m/s**。
- 曾把 `walkSpeed` 提到 1.4（倍率 1.54）⇒ 步频 **2.31 步/秒**，得到的是**竞走级的小碎步**（§9.10 已回退过）。
- 而跑档片段（KI `Run01_Forward`）原生 **4.12 m/s**，取 4.0 的播放倍率是 **0.97** —— 它本来就该是默认档。

在一个 44 m 见方的场地里，以 1.25 m/s 从中心走到外墙要**十几秒**，这就是用户说的"太慢"。

**处置：Shift 的语义改成「按住 = 慢走，不按 = 跑」**（原来是不按 Shift 走、按 Shift 跑）。

| 档位 | 触发 | 速度 | 播放倍率 | 步频 |
|---|---|---|---|---|
| 默认（跑） | 不按修饰键 | 4.0 m/s | 0.97× | 3.23 步/秒 |
| 慢走 | 按住 Shift | 1.25 m/s | 1.37× | 2.06 步/秒 |

两个档位**都落在各自片段的舒适区**，没有任何滑步或碎步。"按住 Shift 慢走"也符合多数玩家的肌肉记忆（潜行 / 细走位）。
`SetInjectedMove` 的**注入路径不做 Shift 反转**（`runHeld` 与参数一一对应），验收脚本按字面理解即可。

### 四、白盒 → 水墨：新增 `InkWash/InkSurface` 与 `InkWash/InkSky`

场景四个白盒材质从 `Universal Render Pipeline/Lit` 换成自研 **`InkWash/InkSurface`**（3 Pass，带多阶量化 + 飞白）：

| 材质 | 纸白 RGB | 淡墨 RGB | 阶数 | 飞白 |
|---|---|---|---|---|
| `M_Whitebox_Wall` | (0.952, 0.947, 0.928) | (0.47, 0.492, 0.53) | 3 | 0.52 |
| `M_Whitebox_Ground` | (0.925, 0.919, 0.899) | (0.52, 0.535, 0.56) | 3 | 0.46 |
| `M_Whitebox_Pillar` | (0.905, 0.9, 0.88) | (0.44, 0.46, 0.5) | 4 | 0.55 |
| `M_Whitebox_Platform` | (0.958, 0.953, 0.934) | (0.5, 0.518, 0.552) | 3 | 0.48 |

**每个材质给不同参数**（而不是共用一份）：同一套量化阶数铺满全场景会让整幅画面像一张贴图；
墙 / 地 / 柱 / 台的纸白与飞白各差一点，"墨分五色"才有层次。

另新增 **`InkWash/InkSky`**（1 Pass），天空盒从 `Default-Skybox` 换成 `M_InkSky` ——
默认天空盒是渐变蓝，与宣纸白放在一起就是"积木玩偶放在塑料底座上"的观感来源。

### 五、发灰：四处同时按住画面，逐项松开

"发灰"不是单一参数，是**四处都在往暗处拽**，必须逐项松开：

| 项 | 改前 | 改后 | 理由 |
|---|---|---|---|
| 环境光 sky | (0.62, 0.63, 0.62) | (0.885, 0.892, 0.885) | 主光偏暗，白纸提不上去 |
| 环境光 equator | (0.5, 0.5, 0.49) | (0.815, 0.822, 0.825) | 同上，中段最影响"灰" |
| 环境光 ground | (0.3, 0.3, 0.3) | (0.64, 0.645, 0.65) | 地面反射光太黑 ⇒ 朝下的面全黑 |
| Directional Sun | 1.15 | 1.30 | 主光稍强，才有"纸白 + 墨黑"的对比 |
| Fill Light (Sky) | 0.28 | 0.45 | 补光不足 ⇒ 背光面全灰 |
| 角色 `_PaperColor` | (0.847, 0.812, 0.741) | (0.96, 0.951, 0.925) | **原值是暖灰**，不是纸白；它是"发灰"最直接的一项 |
| 宣纸 `paperStrength` | 0.45 | 0.26 | 纸纹是**乘性**的，整体压暗；降一半 |
| 宣纸 `vignette` | 0.32 | 0.14 | 原值把画面四周压灰 |
| 宣纸 `tintStrength` | 0.30 | 0.12 | 米黄着染会显脏 |
| 宣纸 `paperTint` | (0.949, 0.925, 0.867) | (0.98, 0.972, 0.95) | 同上，往中性白靠 |
| 宣纸 `inkDeepen` | 0.25 | 0.20 | **刻意保留** —— 暗部仍要沉，对比才立得住 |

**"提亮"不等于把所有东西都调亮**：`inkDeepen` 是唯一**没往亮处调**的一项。
水墨的画面张力来自"纸白 ↔ 墨黑"的跨度，把暗部也抬起来就只剩一片灰。

同批修掉一个**注释骗人**的老 bug（第 7 条诉求，自查发现）。`InkEdge.shader` 里这段注释声称：

```hlsl
// 原注释：「二阶差分（Roberts 式 |dL−dR|），能把掠射角地面的斜坡减掉」
```

**它是错的**：`|dL − dR|` 是**一阶**中心差分。在斜率 `s` 的线性斜坡上，
`dL = dC − s·h`、`dR = dC + s·h` ⇒ `|dL − dR| = 2·s·h`，**正比于斜率，一点也不为零**，
只有在"平坦平台"（`s ≈ 0`）上才为 0。后果是透视下斜率很大的**掠射角墙与地面整片被判成轮廓**，
画面上出现一道道**贯穿并指向灭点的斜线**（像工程图的三角剖分线）。

**不改成真正的二阶差分**（`|dL + dR − 2·dC|`）：拉普拉斯在**阶跃边缘的中心处过零**，
会把每条边画成**双线**（这是它的经典缺陷，靠飞白噪声遮不住）。改为**大幅抬高死区**
（`_DepthBias` 0.30 → **2.0**，`Range` 上限 1 → 6）：本场景"物体 vs 物体"的边界几乎都有法线差（走 `nEdge`）、
"物体 vs 天空"有 `sEdge`，深度项本来就只兜"同一物体自遮挡"这一小块 —— 为这点收益换来满屏斜线不值得。

> **教训**：本项目第二次被"注释撒谎"坑到（第一次见 §9.1.2 三·3 的 `PushAnimatorState`）。
> **改数值之前先核对注释与实现是否一致**；一处写着"二阶"、实现是一阶的注释，
> 会让后来的人（包括我自己）在一个错误的物理模型上做优化。

### 六、挥墨：三个假设连环被证伪之后，真凶是**三角剖分** ★

这是本轮唯一"用户只说了一句、但花掉大半时间"的问题。用户的原话是**「没有挥墨的那种效果感觉」**，
可见现象是**刀光弧线的内缘有一排等距锯齿**，像一把梳子 —— 完全没有"一笔挥出去"的感觉。

#### 1. 三个被证伪的假设（每一个都真做了实验）

| # | 假设 | 实验 | 结论 |
|---|---|---|---|
| 1 | `InkSlash.shader` 里的 `clip(a − 0.004)` 阈值线 | 早已拿掉该行 | 锯齿仍在 ⇒ **证伪** |
| 2 | 高频拉丝噪声（`_StreakScale`） | 44 → 7 | 锯齿仍在 ⇒ **证伪** |
| 3 | 背面剔除（三角形绕序交替，一半被剔掉） | 把全部三角形绕序统一 | `montage_ccw.png` 显示**锯齿不变** ⇒ **证伪** |

**第一个决定性动作：逐层关掉后处理。** 写 `a_arc_diag.cs` 逐配置抓图
（`00_all / 01_noedge / 02_nopaper / 03_nobloom / 04_nopost / 05_flat_nonoise`，后者把实例的 `_FlyingWhite` 压 0）：

> **`04_nopost`（墨线 / 宣纸 / 墨晕三层全关）锯齿依然存在 ⇒ 与后处理无关，归属几何或 Shader。**

所有配置的材质都是 `InkWash/InkSlash`、队列 3000、1 Pass、网格 84 顶点 / 108 三角。

#### 2. 从"相关"升级到"因果"：把齿数变成可控变量

`a_arc_mesh.cs` 在弧光出现的瞬间替换 `MeshFilter.sharedMesh`
（由原网格**索引空间重采样**，不重写数学 —— 避免探针自己的公式写错产出假证据）：

```
原网格剖析：verts=84 rings=3 段数=28 tris=108
  alpha 顶点色 i=中 内/中/外 = 0.12/0.998/0.12
  绕序抽样：tri0 −0.0042 / tri1 +0.006 / tri2 −0.0045 / tri3 +0.0063 / tri4 −0.0058 / tri5 +0.0076  ← 交替
```

四宫格 `montage4.png` 给出两条硬事实：

- **顶点色统一成不透明白 → 锯齿更明显** ⇒ 齿与浓淡梯度**无关**；
- **段数 28 → 200 → 齿变成 199 个** ⇒ **齿 = 网格的四边形段**。

到这里已经能判定"齿是几何自带的"，但**还看不出几何错在哪**。

#### 3. 放弃"从渲染图反推几何"，直接导出运行时网格

试过三四种把渲染图放大 / 二值化 / 边缘提取的路子，都只能得到"有一排尖齿"这个已知结论。
**换思路**：`a_arc_geom.cs` 把运行时真实网格原样导出（`v idx x y z alpha` / `t k i0 i1 i2 signedArea`），
再用 Python 在离线按**重心坐标插值**光栅化 —— 与游戏截图可逐像素对拍。

导出的**前 4 个三角形**（修复前）：

```
t 0   0 1 3   −0.004175984     t 1   0 3 4   +0.006017774
t 2   1 2 4   −0.004474693     t 3   1 4 5   +0.00631648
```

**交替的正负号就是病灶指纹**：同一圈上的 `inner_i / mid_i / inner_{i+1}` 与 `inner_i / inner_{i+1} / mid_{i+1}`
共享的是**内环的边**，而不是对角线 ⇒ 两个三角形的第三个顶点落在同一侧 ⇒
**重叠的蝴蝶结 + 四边形靠中脊侧留下三角形空洞**。段数越多，齿越密 —— 与实验 ② 完全吻合。

把线框画出来（`mesh_wire.png`）后一眼可见：**每个四边形只画出了一半，另一半是空洞**。

#### 4. 修法

| 项 | 改前 | 改后 | 为什么 |
|---|---|---|---|
| 四边形剖分 | 共享**环边**（`p0,p1,q1` + `p0,q1,q0` 的反面） | 沿**真对角线** `p0→q1`：`(p0,p1,q1)` + `(p0,q1,q0)` | 病因本身 |
| 环数 | 3 条 | **5 条**（`kU = 0/0.26/0.5/0.74/1`） | 三环的"满浓"只落在**一条线**上，屏幕上是一道细灰线；五环才让浓墨**有宽度** |
| 浓淡剖面 | 与外缘共用一个 `taper` | 独立的 `kA = 0.10/0.82/1/0.82/0.10` × `inkTaper` | 共用一条曲线 ⇒ 整笔只有正中一小段满浓度，其余发灰。真笔是**粗细很快收成尖（`sin` 保持），浓度中段一直压得住（`pow(taper, 0.6)`）** |
| 收笔下限 | 0.22 | **0.10** | 两端要真的收成尖 |
| 剖分代码结构 | 内带 / 外带**各写一段** | 四条环带**共用一个循环** | 那段分叉的写法正是 bug 的来源 —— 统一后不可能再"只改对一半" |

**这条环数演进值得单独记**（三次教训）：

- **两条环**：外缘仍是满 alpha 的几何直边 ⇒ 屏幕上一块**剪影式硬边色块**；
- **三条环**：形状对了，但"满浓"只落在**一条线**上 ⇒ 一道**细灰线**；
- **五条环**：浓淡剖面 0.10/0.82/1/0.82/0.10 ⇒ 中间是一条**有宽度**的浓墨，两侧化开，两端收尖。

#### 6. 探针自己写错的两条教训（**这一节的教训比修复本身更值得复用**）

- **`a_arc_probe3.cs` 为了拿到"不透明红"把 `SlashArcFade` 组件 `Object.Destroy` 掉 ⇒ 弧光整个不渲染了**
  （三张图的红像素数都是 **0**），于是那一轮"证据"全废。
  **要改一个逐帧被写回的字段，优先改基准来源、或接受写回；不要为了取一个瞬时值去拆组件。**
  修正版 `a_arc_probe4.cs` 只改 `_BaseColor` 的 **rgb**，alpha 留给组件管。
- **同一脚本每轮把玩家瞬移回原位 ⇒ 相机阻尼没跟上，取景全变**（角色跑到画面左下角），
  几张图**不可比**。修正版改成不瞬移。
- 附带一条环境坑：`a_arc_geom.cs` 首跑"没等到 SlashArc" —— 是**残留的 Play 会话**导致的假失败
  （本轮连跑了多个 `--runtime` 探针）。`stop` → `play` → 重跑即成功。

### 七、攻击结束后立刻再攻击卡在中间（连招）

现象：**攻击收招期间再按攻击，招式不出来，角色卡在一个中间的怪姿势**。
`a_retrigger2.cs` 逐帧追踪（三个变体：C = 后摇往 Idle 混合途中再按、D = 每 0.25 s 连点 6 下、E = 跑动中攻击后立刻再攻击）
定位到**两个入口、同一个根因**：

| 变体 | 触发路径 | 表现 |
|---|---|---|
| C | 逻辑判"取消窗口还开着" ⇒ `AdvanceCombo` ⇒ `SetTrigger(Attack2)` | 状态机正在跑 `Atk1Rec → Idle` 的退出混合，而该出边 `interruptionSource = None` ⇒ **已经开始过渡无法被打断**，触发器**挂着没人消费** |
| E | 按住前进（跑）的同一帧按攻击 | 动画正在跑 `Walk → Run` 过渡（同样 `None`）⇒ `Attack1` 被卡住；实测按下后 **12 帧仍停在 `Walk→Run`**，"按了攻击却在跑步" |

**危害不在当下，而在下一次**：残留的 `Attack2` 触发器会在**下一次**攻击播到 `Atk1Rec` 的瞬间突然生效，
动画从半途直接跳进第二段 —— 这就是用户看到的"卡在中间一个奇怪的动作"。

**三处处置**（缺一不可）：

1. **资产层**（`a_fix_fsm.cs`）：把出边的 `interruptionSource` 设为 **`Source`**
   （不是 `SourceThenDestination` —— 后者会让目标状态侧也能打断，例如 `Idle→Walk` 被 `Walk→Idle` 打断 ⇒ 原地来回抖）。
   覆盖两组：`Idle/Walk/Run/Dash` 之间的移动过渡、`Atk1Rec/Atk2Rec/Atk3 → Idle/Walk/Run/Dash` 的后摇退出。
2. **转移顺序**（`a_reorder_fsm.cs`）：Unity 的转移是**按列表顺序求值、先满足者胜**。
   原列表里移动类排在前面（`Run: [→Walk(Speed<2.5)] [→Idle(Speed<0.35)] [→Dash] [→Atk1]`），
   而 `PushAnimatorState` 写 `Speed` 用**阻尼**（`SetFloat(..., 0.10f, dt)`），攻击开始后 `Speed` 还要 0.1~0.3 s 才落到 0
   —— 这段窗口里 `Run→Walk` 一直成立，攻击触发器永远抢不到。
   重排规则：**条件里带 `Trigger` 的转移排前面，其余排后面**（稳定分区，同组内相对顺序不变）。
   用"是不是 Trigger"当判据而不是"目标是不是攻击态" —— Trigger 就是"玩家按了一下"，
   天然比"当前速度是多少"这种持续状态优先级更高；这条规则也自动覆盖了 `Dash`。
3. **代码层（第二道保险）**：新增 `_restartQueued`，并把三个攻击触发器在**回到移动态时一律 `ResetTrigger`**。

**`_restartQueued` 为什么不能复用 `_attackQueued`**（这是本轮最有价值的一条区分）：

| 字段 | 含义 | 有效期 |
|---|---|---|
| `_attackQueued` | "我还想接**下一段**连击" | 只在取消窗口打开**之前**有意义，窗口一开就消费；有效期 `attackInputBuffer` = **0.25 s** |
| `_restartQueued` | "这一段已经接不上下一段了（后摇已过 / 第 3 段按设计不可取消），我只想**再打一遍**" | 从按下一直保留到阶段回到移动态再消费 |

**复用会让玩家这次按键静默消失** —— 0.25 s 撑不过"第 3 段收招 + 后摇混合"（实测 **0.5 s 以上**）。
`TryAttack()` 因此从"接不了就 `return false`"改成三分支：①取消窗口开着 → 立刻接；
②还有下一段但窗口没开 → 进输入缓冲；③**接不了也不丢**，记成"收完重新起手"，由 `EnterLocomotion` 兑现。
**"接不上下一段时绝不能丢玩家的按键"**，是这一轮最该记住的设计约定。

## 9.17 水墨视觉大整改 —— 六病、判据 M1~M8 与《大神》式墨线轮廓（2026-09-15）★

用户第三次反映「水墨风还是有点奇怪、没有什么纹理、整体视觉效果特别差」。
前两轮都是「改完看一眼」，而"看一眼"对**整体调性**极不可靠（人眼会适应，改完那一眼永远觉得"好像好点"）。
本轮**换方法**：先写 `Docs/水墨视觉整改计划.md`（六个病 + 判据 + 执行顺序 A~H），
**每一轮改动都必须能被量出来**，改完前后各跑一次同一把尺子。

### 9.17.1 六个病（均有实测证据）

| # | 病 | 证据 |
|---|---|---|
| 1 | 明度层次塌缩成一条线，墨分五色失效 | 整幅挤在 0.58~0.85 这条 0.28 宽的窄带里 |
| 2 | 噪声被一个**饱和的**量化器吃光 | "没有纹理"的直接原因 |
| 3 | 纸纹是纯乘性的 ⇒ 加纸纹 = 整幅变灰 | 纸纤维不可能把墨**照亮** |
| 4 | 轮廓是 1px 等宽细灰线 | 读起来像制图描边，不像笔 |
| 5 | 底层贴图色相泄漏 | 画面上唯一的彩色在抢视线 |
| 6 | 没有接地与环境关系 | 东西都"浮"在纸上 |

### 9.17.2 判据（M1~M8）

| # | 指标 | 目标 | 终值（idle） |
|---|---|---|---|
| M1 | 亮度 5% 分位 | ≤0.15 —— 画面必须真的有焦墨 | **0.039** |
| M2 | 亮度 95% 分位 | ≥0.90 —— 纸白仍然要是纸白 | **0.948** |
| M3 | 明度标准差 | ≥0.20 —— 层次宽度（最强单指标） | **0.288** |
| M4 | 彩度均值 | ≤0.06 | **0.021** |
| M4b | 高彩度像素占比 | ≤0.5%（专抓破调色） | **0%** |
| M5a | 细粒能量（像素级 \|Laplacian\| **中位**） | ≥2.5× 地板 | **2.55×** |
| M5b | 笔痕能量（**4px 步长** \|Laplacian\| 中位） | ≥2.5× 地板 | 2.28× ⬜ |
| M6 | 分离度（背景均 − 主体墨 **10% 分位**） | ≥0.55 | 0.545 ⬜ |
| M7 | 墨线宽估计 | 1.8~2.6 px | **2 px** |
| M8 | 帧率（编辑器内） | ≥55 | **115.5**（1% 低 59.5） |

**四条口径设计**（否则数字会撒谎）：
1. **M1 与 M2 必须同时达标** —— 只压暗不抬纸白 = 回到"发灰"；只抬纸白不压暗 = 回到"一片白"。
   写意重墨的解法是**暗部真的暗下去、同时受光面真的亮起来**，靠对比度而不是靠整体明度。
2. **M5 与 M7 分开** —— M5 量"**面**上有没有纹理"（中位数），M7 量"**线**上有多少墨"。
   否则加粗墨线会让 M5 假性暴涨。
3. **M5 必须拆两档** —— 像素级 `|Laplacian|` 读不出笔触层
   （实测"仅笔触"14.83e-3 vs 地板 14.57e-3，根本分不开）。
4. **M6 必须用分位不用均值** —— `SkinnedMeshRenderer.bounds` 投影比真实轮廓宽 **3 倍**，
   用包围盒均值会把主体墨**稀释成负值**（一度被误读成"角色比背景还亮"）。
5. **M8 必须逐帧采集 + 热身** —— 用 `Time.time` 首尾差会把个别长帧整个抹平；
   而窗口前若不热身，上一步的 `EncodeToPNG` + 纹理销毁 + 大 GC 会落在**窗口第一帧**上，
   量出"最差单帧 2558 ms"这种**纯属探针自伤**的数。

### 9.17.3 ★ 本轮最大发现：主体墨阶塌缩成"黑剪纸"

轮廓做出来之后，**关掉和打开画面几乎一样**。追下去是**两处独立压暗的叠加**：

```
ramp ≈ lambert*0.8 + ambient*0.4 + _BandBias(-0.38) ≈ 0.02          ⇒ 落在最底一阶
color *= lerp(1, albedo, _InkDensity=0.62)，黑衫 albedo≈0.05 ⇒ 再均匀 ×0.41
⇒ 本体 L≈0.04，而轮廓墨色 L≈0.041 —— 线条和身体**同值**，等于没画
```

主体像素直方图（`Tools/cs/e_tonality.cs`）：

| 配置 | `_BandBias` | `_InkDensity` | 层次宽 p90−p10 | 五色 焦/浓/重/淡/清 % | 分离度 |
|---|---|---|---|---|---|
| 改前 | −0.38 | 0.62 | **0.11** | **66.0 / 33.3** / 0.6 / 0.1 / 0.0 | 0.71 |
| **采用** | **+0.15** | **0.62** | **0.58** | 4.4 / 26.1 / 18.4 / 38.5 / 12.6 | **0.61** |
| 过高 | +0.40 | 0.35 | 0.37 | 0.3 / 5.7 / 3.2 / 35.2 / 55.5 | 0.28 ❌ |

> **改前 99.3% 的像素挤在"焦+浓"两级** —— 这就是"黑剪纸"的量化定义。
> 同时 **"越白越好"被证伪**：继续往上推，主体分离度**崩**（0.61 → 0.28），主体糊进纸里。

**落地只改一个数**：`M_Character_Ink._BandBias: −0.38 → +0.15`（`_InkDensity` 不动，变更面最小）。

#### 设计闭合：**主体留白 + 分离度交给墨线轮廓**（＝《大神》的构造）

实测证实：本体 p50 从 **0.08 抬到 0.48**，而分离度指标**稳在 0.547 不动** ——
因为分位口径下提供"最暗值"的已经是**墨线轮廓**（0.039），不是主体。
⇒ **顺序不能反：先做轮廓，再做主体提亮**；反了会以为"提亮必然伤分离度"而不敢动。

### 9.17.4 《大神》式墨线轮廓（反向外扩壳）

```hlsl
Pass
{
    Name "InkOutline"
    Tags { "LightMode" = "SRPDefaultUnlit" }   // URP 里该批先于 UniversalForward
    Cull Front      // 只画背面 —— 外扩壳的背面正好落在物体轮廓之外
    ZWrite On
    // 顶点：posWS += nrmWS * (宽度 * 掠射加权 * 飞白遮罩)
}
```

| 《大神》特征 | 实现 |
|---|---|
| 粗重、有起收顿挫的墨线 | 外扩壳（**不需改渲染队列、不需加 RendererFeature**） |
| 轮廓**不是等宽** | `graze = saturate(1−\|dot(n,view)\|)`，`pow(graze, 0.7)` 提中段；`_OutlineFacing 0.72` ⇒ 掠过视线的边才是粗笔 |
| 长距离飞白断笔 | **物体空间**低频 Value noise（`_OutlineScale 5` ≈ 0.2 m 一格） |
| 低处积墨 | 复用接地墨渍的 `_ContactInk/_ContactHeight/_GroundY`，**不新增 uniform** |
| 屏幕空间线宽恒定 | `_OutlineWidth × (1 + 距离 × _OutlineDistScale)` |

**五个坑（都不报错）**：
1. **飞白噪声必须用物体空间**。世界空间会让图案随角色移动"流过"轮廓 ⇒ 走起来**整条线在沸腾**；
   而**静止截图完全正常**，只有录动态才看得出来。物体空间与体表是稳定映射，图案等于画在皮肤上。
2. **新增 uniform 要同步改 4 个 `UnityPerMaterial` CBUFFER**，且 SRP Batcher 要求四块
   **逐字段同序同类型** —— 不一致**不报错、不崩、画面正常**，只是 SRP Batcher **静默失效**。
   为此立了 `Tools/check_cbuffer.py` 做机器比对（手写时确实漏了：集合相同、**顺序不同**）。
3. **`Material.HasProperty` 只证明 shader 声明了它，证明不了材质设了它** ⇒ 缺了会**静默回落**到
   shader 默认值。关键属性一律**显式写进 `.mat`**，并在 `b_gate` ④ 加了"必须显式"的检查。
4. **外扩量有饱和上限**：`_OutlineWidth` 0.080 → 屏上外露带 10px，0.120 → **仍 10px**（外扩壳自交叠）。
   别用"继续加宽"救观感。
5. **剑这类细长物体要单独给更小的值**（剑 0.030 vs 角色 0.055），否则锋刃被糊成一根棒。

**宽度定标**（A/B 扫 + 看图）：

| `_OutlineWidth` | 外露带中位 | 观感 |
|---|---|---|
| 0 | —（对照组差分 **0**） | 纯本体 |
| 0.018 | 4 px | 偏细，读成制图描边 |
| 0.035 | 6 px | 干净但仍是"插画线" |
| **0.055（采用）** | **8 px** | **笔意够重，四肢仍分得开** |
| 0.080 | 10 px | 胳膊和身体开始粘连 |

### 9.17.6 度量盲区（本轮新增的方法学）

`d_metrics` 出于设计前提把**角色/敌人矩形排除**在统计之外（防止"角色变黑"被误读成"层次变好"）。
副作用：**角色身上的改动它全看不见** —— 会出现"改了一大轮、指标一个没动"的假象。
**先确认尺子能不能看见被测对象，再去改它。** 补了两把专用尺子：

| 探针 | 手法 | 自我验证 |
|---|---|---|
| `Tools/cs/e_outline.cs` | **同帧 A/B 差分**（同帧内渲「轮廓 0」与「轮廓 W」，中间不 `yield` ⇒ 姿势逐位一致） | 对照组（宽 0 渲两次）差分 = **0**；`px/米` 几何交叉验证 0.035 m 量出 0.0358 m ✅ |
| `Tools/cs/e_tonality.cs` | **品红掩码**取主体像素（比"隐藏主体再差分"干净，不会把影子算进掩码） | 末条配置重复首条做**复现性对照**，逐项吻合 |
