## 0. 一句话结论

龙的蛇形波现在弯在**垂直面（上下蜿蜒）**，应该弯在**水平面（左右蜿蜒）**。

根因：`StraightenSpineBase()`（拉直）之后，每节骨骼的**局部 Y 轴不再是"上"**
（`FromToRotation` 沿链方向带来了逐节不同的 roll），
而 `ApplySpineOffsetsRaw` 用的是**骨骼局部轴**。
⇒ 拉直之前测出的"局部 Y = 水平弯"的结论**已失效**。
改法见 §3.3。**已在真实运行代码路径上验收通过**：水平跨度 2.003 / 垂直跨度 0.190（比值 10.56），
由「上下蜿蜒」（修前 0.20）改为「左右蜿蜒」（见 §3.0）。

## 3. ✅ 已实现并验收（原唯一阻塞项）：蛇形波弯在垂直面

### 3.0 验收结果（真实运行代码路径，非设计 A/B 探针）

> ⚠️ `Tools/cs/dg_axis2.cs` **不调用生产代码**：它在 `Apply()` 里自己手搓两条写法去量，
> 所以改完再跑它，数字和改之前一模一样。要验收**生产代码**必须用下面这种探针：
> 反射拿 `_spine` / `_modelRoot`，让游戏自己跑，`InverseTransformPoint` 换到容器局部系，
> 采样若干帧量各节点的 x/y 跨度。

实测（24 节脊骨 / 362 帧，演示场条目 17 盘旋）：

| 阶段 | 水平 x 跨度 | 垂直 y 跨度 | 比值 | 结论 |
|---|---|---|---|---|
| 修前（`dg_axis2` 的设计 A/B 量） | 2.123 | **10.787** | 0.20 | 上下蜿蜒 ✗ |
| 修后（**真实代码路径**实测） | **2.003** | 0.190 | **10.56** | **左右蜿蜒 ✓** |

残留的 0.190 垂直量是**设计内**的：`hoverPitchAmplitudeDeg = 1.5` 那条正交起伏（相位错开 90°），
`0.190 / 2.003 = 9.5%`，与 `1.5 / 16 = 9.4%` 吻合 ⇒ 是垂直起伏本身，不是漏网的上下摆。

> 判据一句话：**水平/垂直远大于 1 = 左右蜿蜒 ✅**；小于 1 = 上下蜿蜒 ✗。

### 3.1 实测证据（`Tools/cs/dg_axis2.cs` → `Tools/reports/dg_axis2.txt`）

在**已拉直**的基准上，沿链 8 个相位取节点位置（`modelRoot` 局部系，x = 横向 / y = 垂直 / z = 沿体轴）：

|---|---|---|---|---|---|
| 现有 `base * Euler(0, yaw, 0)`（局部 Y） | n12 | 0.862 | **8.290** | 4.841 | **上 下** |
| 现有 `base * Euler(0, yaw, 0)`（局部 Y） | n23 | 2.123 | **10.787** | 3.727 | **上 下** |

### 3.2 根因

`StraightenSpineBase()` 用的是 `Quaternion.FromToRotation(d.normalized, fwd)` ——
**最小旋转**，它把每节的链方向对到 `fwd` 之后，**绕 `fwd` 的 roll 是不受控的**，
而且**逐节不同**（因为原生各节方向都不一样）。

于是"骨骼局部 Y"在拉直后指向了链侧方 ⇒ 绕局部 Y 转 = 身体**上下**摆。
`dg_axis` 当初测出"局部 Y = 水平弯"是在**未拉直的弯基准**上量的，**结论已过期**。

> 这是本次教训的核心：**不要用"骨骼局部轴"做几何约定**。
> 骨骼局部轴的朝向是导入链的副产物，任何一次基准重排都会把它换掉。

### 3.3 改法（可直接落地）

**核心思路**：改用**根空间（模型容器空间）的语义轴** ——
水平蛇形 = 绕容器的 `up`；垂直起伏 = 绕容器的 `right`。
这样与骨骼局部 roll 完全无关。

**① 新增字段**（与 `_baseRot` 并列，`EnemyDragon.cs:248` 附近）

```csharp
/// <summary>
/// 拉直后的基准姿态，表达为**模型容器局部系**（不是每节自己的局部系）。
/// ★ 为什么必须这样存：骨骼局部轴被 StraightenSpineBase 的 FromToRotation
///   带来了不受控的 roll，"绕局部 Y 转"实际会上下摆（实测垂直跨度 10.8 m）。
///   换成容器局部系后，绕 (0,1,0) 转就**一定**是左右摆。
/// </summary>
private readonly List<Quaternion> _baseRel = new List<Quaternion>();
```

**② 在 `StraightenSpineBase()` 末尾（`EnemyDragon.cs:407` 之后）记录**

```csharp
// 拉直后的姿态成为新基准：之后所有偏移都叠在"直线"上
for (int i = 0; i < _spine.Count; i++) _baseRot[i] = _spine[i].localRotation;

// ★ 额外记一份「相对模型容器」的基准旋转（形状描述，与容器朝向解耦）
Quaternion rootRot = _modelRoot != null ? _modelRoot.rotation : transform.rotation;
_baseRel.Clear();
for (int i = 0; i < _spine.Count; i++)
    _baseRel.Add(Quaternion.Inverse(rootRot) * _spine[i].rotation);
```

**③ 改写 `ApplySpineOffsetsRaw` 的写入式（`EnemyDragon.cs:1145-1146`）**

```csharp
// 现在（用骨骼局部轴 ⇒ 实际上下摆）：
// _spine[i].localRotation = _baseRot[i] *
//     (Quaternion.Euler(0f, yaw, 0f) * Quaternion.Euler(0f, 0f, pitch));

// 改为（用容器空间的语义轴 ⇒ 左右 / 上下各归其位）：
Quaternion rootRot = _modelRoot != null ? _modelRoot.rotation : transform.rotation;
_spine[i].rotation = rootRot
                     * Quaternion.AngleAxis(yaw,   Vector3.up)      // 水平蛇形：绕「上」→ 必然左右
                     * Quaternion.AngleAxis(pitch, Vector3.right)   // 垂直起伏：绕「右」→ 必然上下
                     * _baseRel[i];
```

> - 注意是**绝对角**写法：`yaw_i = yawMax·env·sin(phase − i·φ)` 直接作为"该节相对基准的偏航角"，
>   累加效果由链式父子关系自然产生（与原来"逐节增量的累加"等价）。
> - 用 `_spine[i].rotation`（世界）而非 `localRotation`：这样每节的角度**不受父节点影响**，
>   波形严格是 `sin(phase − i·φ)`，正是"行波"。
> - 若想少改结构，等价写法是保留 `localRotation`，但把轴换成"容器 up 在该节局部系的投影"：
>   `Vector3 axisLocal = Quaternion.Inverse(_baseRel[i]) * Vector3.up;`
>   然后 `localRotation = _baseRot[i] * Quaternion.AngleAxis(off, axisLocal);`
>   ——不过**推荐前一种**，可读性更好。

**④ 其余 4 处 `Euler(pitch, 0, 0)` 一并改**（`EnemyDragon.cs:867 / 933 / 972 / 998`）

这些是"低头 / 抬头 / 俯角"相位（`DoDiveTell`、`DoStrikeBite` 等）。它们的语义是
**绕身体横轴俯仰** ⇒ 同样改成绕容器 `Vector3.right`：

```csharp
_spine[i].rotation = rootRot * Quaternion.AngleAxis(pitch * (1f + 0.12f * k), Vector3.right) * _baseRel[i];
```

### 附：两个"看起来像代码 bug、其实是素材缺失"的坑（已定论）

**「演示场敌人条目在画面里看不到」——不是 layer/shader/相机问题。**

```yaml
# Assets/_Project/Prefabs/Enemies/Enemy_MoYan.prefab
--- !u!137 &6374850387060490837 stripped
SkinnedMeshRenderer:
  m_CorrespondingSourceObject: {fileID: 3150538496148287062, guid: 2135005f3db468a40963199158b75532, ...}
```

`SkinnedMeshRenderer` 是 **stripped** —— 数据不在本文件，靠 guid 从源 prefab 继承，而**该源 prefab 不在仓库里**。
源缺失 ⇒ Unity 把整个嵌套实例丢掉 ⇒ 敌人身上**一个渲染组件都没有**。
7 个 prefab 都有这个问题（Player / MoYan / MoGu / MoTu / MoOu / MoShan / MoGuai），
控制台那 7 条 `Nested Prefab problem` 就是它。

> ⚠️ 当初测出 `isVisible = True` 是**误判**：该属性只表示"通过了视锥剔除"，
> **不代表真的画出了像素** —— 没有网格时它照样是 True。
> 所以"layer / shader / 距离全正常"是对的，但排查方向错了。

**「演示场没烤 NavMesh」——不是没烤，是**没有几何体可烤**。**

```
场景: Assets/_Project/Scenes/Showcase.unity
烤前 NavMesh: 顶点=0 三角=0
Renderer 总数=0，其中 NavigationStatic=0     ← 关键

```

演示场里**一个 Renderer 都没有**（地面与场景几何同样在被 gitignore 的 prefab / `ThirdParty` 里，
嵌套 prefab 源缺失后被整体丢弃）。没有几何体 ⇒ NavMesh 烤出来必然是空的，

**踩坑备忘（会造成"改了没反应"的假象）**
- `exec_cs.py --runtime` 是**异步**的：进程立刻返回，探针继续跑 ⇒ 必须自己 `sleep` 等结果落盘
- `--runtime` 里**禁止阻塞调用**（`Thread.Sleep`/`Task.Wait` 被静态检查拦截）⇒ 长采样挂 `MonoBehaviour.Update`
- `--runtime` 下 `UNITY_EDITOR` **未定义** ⇒ 不能用 `AssetDatabase`，判类型用反射 + 类型名字符串
- **改 C# 默认值不生效**：prefab 里序列化了同名键 ⇒ C# 与 prefab **两处都要改**，改完 grep 复核
- `Edit` 编辑大文件会**静默丢改动** ⇒ 改完一律 grep 复核（本轮踩到 3 次）
- 一个 `.cs` 是**独立编译单元** ⇒ 不能引用另一个工具脚本里的类型；文件末尾必须至少有一条顶层语句
